Blaster is an Easy Windows box themed around *Ready Player One*. A WordPress blog comment left by its own author hands over valid RDP credentials, and a signed-but-outdated Windows Update installer sitting on the user's desktop opens a path to SYSTEM through CVE-2019-1388, a UAC bypass hidden inside the certificate-viewer dialog itself.

One housekeeping note before the walkthrough: the target VM had to be restarted partway through this engagement, and its IP changed as a result — `10.129.163.17` at the start, then `10.129.174.139`, then `10.129.152.245` by the end. It's the same machine throughout; each command below simply uses whichever address was live at that moment.

## Reconnaissance & Enumeration

The objective of this phase was to enumerate exposed services and identify the application stack worth attacking.



## Privilege Escalation — `Wade` → SYSTEM

### CVE-2019-1388 — Windows Certificate Dialog UAC Bypass

`hhupd.exe` is an old, Microsoft-signed HTML Help updater — its age is the point. When Windows' UAC consent prompt can't cleanly verify a signed binary's publisher chain (an expired certificate qualifies), it offers a link to inspect that certificate, and that link opens a certificate viewer running with the same privileges as the UAC prompt process itself: **NT AUTHORITY\SYSTEM**. From there, a second link inside the certificate viewer — the issuing CA's own URL — launches a web browser, also as SYSTEM. And a browser running as SYSTEM has a file-save dialog that can reach anywhere on the filesystem, including `C:\Windows\System32\cmd.exe`. This chain of forwarded privilege, entirely through UI elements nobody thought to lock down, is **CVE-2019-1388**, patched by Microsoft in November 2019 — a full year before this exact file was still sitting untouched on `Wade`'s desktop.

Right-clicking `hhupd.exe` and running it as administrator is the entry point:

![Right-clicking hhupd.exe and choosing "Run as administrator" from the context menu](/assets/img/THM/Blaster/cap3.png)

That raises the standard UAC consent prompt — but instead of supplying credentials, the interesting part is the link beneath the publisher's name:

![The UAC consent prompt for hhupd.exe, requesting Administrator credentials and offering to show the publisher's certificate](/assets/img/THM/Blaster/cap4.png)

Clicking **Show information about the publisher's certificate** opens the certificate viewer — running elevated, since it was spawned by the elevated UAC prompt process itself:

![The Certificate Information dialog for the signed hhupd.exe, issued to Microsoft Corporation by VeriSign](/assets/img/THM/Blaster/cap5.png)

The `Issued by` line is a live link to the issuing CA. Clicking it launches the system's default browser, pointed at that CA's page, inheriting the certificate viewer's SYSTEM privileges. From the browser's **Save As** dialog, attempting to save to its default location fails immediately — the exact confirmation the exploit is already working:

![The Save Webpage dialog failing with "Location is not available" for the SYSTEM profile's Desktop path](/assets/img/THM/Blaster/cap6.png)

The default path the dialog tried and failed to reach is the desktop for the SYSTEM account, not for `Wade` — proof this Save dialog is itself running as SYSTEM. Dismissing that error and navigating the same dialog to `C:\Windows\System32\`, then typing `C:\Windows\System32\*.*` into the file name field and pressing Enter, refreshes the view to list every file in that directory as a browsable entry inside what's still a SYSTEM-privileged dialog:

![The Save Webpage dialog browsing C:\Windows\System32\ with C:\Windows\System32\*.* entered in the file name field](/assets/img/THM/Blaster/cap7.png)

Opening `cmd.exe` from that listing launches it inheriting the dialog's own privilege level, rather than `Wade`'s — visible here already sitting in the `Administrator` desktop with `root.txt` in view:

![An elevated command prompt opened from the SYSTEM-privileged Save dialog, showing C:\Users\Administrator\Desktop and root.txt, with the flag read via "more root.txt"](/assets/img/THM/Blaster/cap8.png)

An `Administrator`-owned desktop, reachable and readable — no password ever entered, no exploit beyond a nine-year-old signed installer Windows still trusted enough to run.

## Key Takeaways

- **Personal information is password material when a site's whole theme is personal.** A blog comment left by its own author, on a post about a movie whose protagonist shares the author's real name, wasn't decoration — reading a site's content the way a human would, not just scanning it with a tool, found a working password `wpscan` never could.
- **Recon leaks identity long before login.** RDP's own pre-auth negotiation handed over the hostname, domain, and build number for free; nmap's `rdp-ntlm-info` script exists because that information was never meant to require credentials to read.
- **A signed binary isn't a safe binary — only a verifiably old one.** CVE-2019-1388 exists because Windows trusted a certificate viewer's own UI elements, links meant only to display information, to inherit whatever privilege launched them, with no separate check on where those links actually led.
- **"Location is not available" is diagnostic information, not just an error.** A save dialog's default path naming the SYSTEM profile, rather than the logged-in user's, is a free confirmation that an escalation is already working, before doing anything else with the access.
- **Built-in tools are still attacker tools.** `certutil`, PowerShell's `Invoke-WebRequest`, and a signed nine-year-old Microsoft installer did all the heavy lifting here — nothing exotic needed downloading past a static netcat binary.
- **A tool crashing isn't the same as a technique being wrong.** This Metasploit run never produced a session, but the module, the target selection, and the delivery mechanism were all correct — worth documenting the failure honestly rather than only ever writing up the runs that work.
